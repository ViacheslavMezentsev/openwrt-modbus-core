## 1. Введение

### 1.1. Соглашения

1.1.1. Номера требований и TC-NN локальны этому документу, не переиспользуются.
Ссылка вне документа включает имя пакета. ДОЛЖЕН означает обязательство после
утверждения; `[R]` — восстановлено по коду, `[N]` — новое, `[U]` — уточнение.
разделы 3–5 — нормативные; наличие тест-кейса не означает PASS.

1.1.2. Ревизия ТЗ, версия пакета и версия API ядра различаются. Изменения ведутся
в собственной истории ревизий и CHANGELOG; перенос в отдельный репозиторий
сохраняет номера. Прототипы и аппаратные логи остаются локальными.

## 2. Общее описание

### 2.1. Область и зависимости

2.1.1. Пакет музыкального школьного звонка владеет учебным календарём,
прикладными расписаниями, мелодиями, ручными/веб-сценариями и сохранением настроек.
Общий scheduler, события, подписки и вызов actions принадлежат ядру.
Постоянный процесс на каждое правило не требуется. Аудиоисполнитель может иметь
отдельный процесс; его размещение/пакетная принадлежность ещё не определены.

2.1.2. Базовая документация ядра — 1.5. Необходимый общий API регистрации пока
отсутствует; совместимость с текущим core 0.4.0 не заявляется. До реализации
нужно закрепить версию API и диапазон зависимости пакета. Названия методов
из обсуждения являются псевдокодом, а не выпущенным контрактом.

2.1.3. Исходный проект — https://github.com/ViacheslavMezentsev/schoolbell,
ревизия c4bbecd. Его cron/CGI-реализация — источник пользовательских сценариев,
не реализация этого ТЗ. Импорт старых форматов требует отдельной проверки.

## 3. Функциональные требования

### 3.1. Регистрация сценариев

3.1.1. Пакет ДОЛЖЕН при загрузке регистрировать свои источники событий по
расписаниям и обработчики через общий API ядра. `[N]`

3.1.2. Обработчик звонка ДОЛЖЕН передавать запрос воспроизведения исполнителю
действий без ожидания окончания мелодии в callback ядра. `[N]`

## 4. Требования к интерфейсам

### 4.1. Границы ответственности

4.1.1. Обращение пакета к Modbus-периферии ДОЛЖНО проходить только через ядро,
без открытия serial самим schoolbell. `[N]`

## 5. Нефункциональные требования

### 5.1. Поставка

5.1.1. Schoolbell ДОЛЖЕН поставляться отдельным устанавливаемым пакетом с
собственной историей версий и объявленной зависимостью от контракта ядра. `[N]`

## 6. Верификация

Все проверки ниже — ПЛАН, прототип и реализация отсутствуют. I — инспекция,
T — изолированный тест, A — анализ пакета. Аппаратных результатов нет.

| TC | Сценарий | Ожидаемый результат |
| --- | --- | --- |
| TC-01 | Загрузка пакета на mock API | Зарегистрированы собственные расписания/подписки; без запуска звука при загрузке |
| TC-02 | Наступление времени звонка | Один запрос audio action; callback не ждёт окончания воспроизведения |
| TC-03 | Действие с периферией | Только API ядра, прямой serial не открывается |
| TC-04 | Анализ пакета | Отдельный IPK с явной зависимостью от согласованной версии API |

## 8. Допущения и открытые вопросы

### 8.1. Допущения

8.1.1. Первый этап — локальный прототип с fake clock/audio/платой. Звук,
изменение усилителя, установка, RTC и прошивка требуют отдельных согласований.
Нет гарантий exactly-once, точности времени или ресурсов до определения критериев.

## Приложение A. Границы

ТЗ не копирует алгоритм общего scheduler и событийного runtime. Множественные
подписки — контракт ядра; выбор действий школьного звонка — контракт пакета.
Аудиособытия started/finished/failed и идентификаторы запросов ещё проектируются.
Старые скрипты не устанавливаются как реализация новых требований.
