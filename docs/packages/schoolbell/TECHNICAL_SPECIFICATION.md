## 1. Введение

### 1.1. Соглашения

1.1.1. Номера требований и TC-NN локальны этому документу, не переиспользуются.
Ссылка вне документа включает имя пакета. ДОЛЖЕН означает обязательство после
утверждения; `[R]` — восстановлено по коду, `[N]` — новое, `[U]` — уточнение.
разделы 3–5 — нормативные; наличие тест-кейса не означает PASS.

1.1.2. Ревизия ТЗ, версия пакета и версия API ядра различаются. Изменения ведутся
в собственной истории ревизий и CHANGELOG; перенос в отдельный репозиторий
сохраняет номера. Прототипы и аппаратные логи остаются локальными.

## 2. Общее описание

### 2.1. Область и зависимости

2.1.1. Schoolbell владеет календарём, аудиообработчиками, очередью и процессом
проигрывателя, медиа и настройками. Ядро предоставляет общий scheduler и публичные
события/подписки/уведомления. Schoolbell публикует результат тем же интерфейсом;
длительная обработка выполняется клиентом вне основного цикла ядра. (р.1.3)

2.1.2. Базовая документация ядра — 1.9, разделы 4.5–4.6 и 5.4. Общий API ещё отсутствует;
совместимость функционального schoolbell с core 0.4.0 не заявляется. Сигнатуры,
версия API и диапазон зависимости определяются до реализации. (р.1.4)

2.1.3. Исходный проект — https://github.com/ViacheslavMezentsev/schoolbell,
ревизия c4bbecd. Его cron/CGI-реализация — источник пользовательских сценариев,
не реализация этого ТЗ. Импорт старых форматов требует отдельной проверки.

## 3. Функциональные требования

### 3.1. Регистрация сценариев

3.1.1. Пакет ДОЛЖЕН при загрузке регистрировать свои источники событий по
расписаниям и обработчики через общий API ядра. `[N]`

3.1.2. Обработчик уведомления ДОЛЖЕН передавать запрос собственному исполнителю
schoolbell без ожидания окончания мелодии в цикле уведомления ядра; завершение
или ошибка публикуются пакетом через общий событийный интерфейс. `[N]` (р.1.3)

### 3.2. Исполнитель schoolbell

Политика относится только к клиенту schoolbell; готовая реализация пока отсутствует.

3.2.1. Отключение регистрации пакета НЕ ДОЛЖНО само по себе отменять уже
принятые запросы действий. Они остаются на исполнении по правилам соответствующего
исполнителя; отмена задаётся явным запросом. Это не гарантия успешного выполнения
или сохранности при аварии; истечение срока по п. 3.2.3 остаётся действующим. `[N]` (р.1.3)

3.2.2. Аудиоисполнитель ДОЛЖЕН запускать принятые запросы воспроизведения
последовательно в порядке приёма, без наложения мелодий на одном аудиоресурсе.
Отменённые и просроченные запросы не блокируют следующие допустимые запросы. `[N]` (р.1.3)

3.2.3. Перед разрешением запуска проигрывателя исполнитель ДОЛЖЕН проверять
актуальность запроса по пп. 3.2.5–3.2.6 после подготовки файла, не продлевая
исходный TTL. Просроченный запрос не получает разрешения; уже разрешённый запуск
не прерывается из-за истечения срока. Это граница допуска запуска, а не гарантия
времени exec или первого слышимого звука; задержки ОС измеряются по 5.2.2.
Системный механизм последней проверки определяется по 8.2.11. `[U]` (р.1.8)

3.2.4. Отмена ДОЛЖНА удалять ожидающее действие по ID только для его владельца;
повтор отмены уже отменённого действия даёт идемпотентный успех. Для активного
действия первая версия возвращает явный отказ и сохраняет занятость ресурса
до подтверждённого завершения. Остановка активного исполнителя требует
отдельного протокола и не считается реализованной этой отменой. `[N]` (р.1.3)

3.2.5. Аудиозапрос ДОЛЖЕН иметь положительный срок ожидания TTL от момента
приёма по монотонным часам; календарный запрос дополнительно имеет абсолютный
срок актуальности UTC. Старт допустим только до обоих применимых сроков;
равенство означает истечение. Коррекция UTC назад не продлевает монотонный TTL.
Ограничения относятся к старту, а не к остановке активной мелодии. `[N]` (р.1.3)

3.2.6. При недостоверном UTC календарный аудиозапрос ДОЛЖЕН ожидать восстановления
достоверности, сохраняя FIFO своего ресурса; монотонный TTL продолжает истекать.
После истечения запрос пропускается, не препятствуя следующим актуальным
запросам. Недостоверный UTC не блокирует независимые ресурсы без календарного
условия. `[N]` (р.1.3)

### 3.3. Календарь и предзвонки

3.3.1. Пакет ДОЛЖЕН поддерживать два режима: постоянное выбранное расписание дня независимо от календаря и автоматический выбор расписания по дате годового плана. `[N]` (р.1.4)

3.3.2. Пакет ДОЛЖЕН одновременно хранить не менее четырёх редактируемых рабочих расписаний и выбор «нет звонков»; тихий день не создаёт основные или предварительные звонки. `[N]` (р.1.4)

3.3.3. Строка расписания ДОЛЖНА содержать проверенные сервером HH:MM, идентификатор основной мелодии, enabled и флаг предзвонка; выключенная строка сохраняется без генерации обоих звонков. `[N]` (р.1.4)

3.3.4. Пакет ДОЛЖЕН предоставлять общий интервал предзвонка от 1 до 10 целых минут и отдельную общую мелодию предзвонка. Включённый флаг строки добавляет один предварительный момент к основному; переход часа/суток вычисляется календарно. `[N]` (р.1.4)

3.3.5. План ДОЛЖЕН задавать явный год и часовой пояс с назначением расписания допустимым датам, включая 29 февраля только в високосном году. Границы года/тихих дат и ошибки местного времени определяются пп. 3.3.9–3.3.10; недельные правила и приоритет исключений остаются по вопросу 8.2.2. `[U]` (р.1.6)

3.3.6. Клиент ДОЛЖЕН преобразовывать выбранный режим/план в регистрации общего scheduler и обновлять их при смене даты без браузера/Интернета, не перезаписывая общий cron. `[N]` (р.1.4)

3.3.7. Предпросмотр ближайших звонков ДОЛЖЕН использовать тот же вычислитель моментов, что регистрация, и показывать применяемые расписание и ревизию. `[N]` (р.1.4)

3.3.8. Пакет ДОЛЖЕН предоставлять ручную синхронизацию времени из браузера после подтверждения администратором через системный интерфейс ядра. Разные часовые пояса браузера/роутера не должны менять передаваемый момент; после коррекции регистрации сверяются по выбранной политике вопроса 8.2.3. `[N]` (р.1.4)

3.3.9. В автоматическом режиме неназначенная дата или отсутствие плана на её год ДОЛЖНЫ означать тихий день; повторение другого года запрещено. Тихий день не допускает и предварительных звонков следующего дня: такой предзвонок подавляется без отмены основного. Постоянный режим не зависит от годовых назначений. `[N]` (р.1.6)

3.3.10. При расчёте календарных моментов несуществующее или неоднозначное местное время ДОЛЖНО приводить к явному отказу всего запрошенного окна без частичного списка, нормализации или неявного выбора UTC. Преобразование использует явно заданный часовой пояс; зависимость от зоны хоста запрещена. Производственный механизм правил зоны остаётся по вопросу 8.2.2. `[N]` (р.1.6)

### 3.4. Управление расписанием

3.4.1. Оператор ДОЛЖЕН иметь операции остановки будущих автоматических звонков, возобновления и повторного применения выбранного режима без перезапуска ядра, других пакетов или общего cron. Активная мелодия не обрывается по п. 3.2.4; судьба ожидающих запросов и paused после reboot определяется вопросом 8.2.9. `[N]` (р.1.4)

3.4.2. Ручной тест короткой мелодии ДОЛЖЕН быть доступен и при остановленном расписании, выполняться собственным исполнителем по общей аудиоочереди и показывать наблюдаемый результат. Успешный exit не должен объявляться подтверждением слышимости. `[N]` (р.1.4)

3.4.3. Пакет ДОЛЖЕН различать черновик, сохранённую и активную ревизии; сохранение не должно неявно активировать расписание. Применение допускается после проверки целостности и подтверждения нового поколения регистрации; неверная замена сохраняет действующую. `[N]` (р.1.4)

3.4.4. Редактор ДОЛЖЕН позволять добавлять, удалять и очищать строки, изменять несколько расписаний без потери правок при переходах и сохранять их с последующим чтением. Конфликт параллельных редакторов должен отклоняться явно без молчаливого затирания. `[N]` (р.1.4)

3.4.5. Менеджер ДОЛЖЕН поддерживать создание, копирование и удаление целых расписаний с проверкой ссылок планов; удаление используемого расписания отклоняется. Эта возможность расширяет оригинал, где add/delete были заглушками. `[N]` (р.1.4)

### 3.5. Замена медиа и восстановление

3.5.1. Пакет ДОЛЖЕН предоставлять загрузку/замену пользовательской мелодии с проверкой фактического размера, допустимости MP3 и совместимости проигрывателя до изменения действующей медиатеки. Лимиты и способ проверки определяются по вопросу 8.2.5. `[N]` (р.1.4)

3.5.2. Медиатека ДОЛЖНА различать стабильный ID и ревизию содержимого, не перезаписывать играющий файл и не удалять версии, необходимые сохранённым планам, очереди, активному процессу или откату. Ревизия фиксируется при приёме заявки по 3.5.7–3.5.9. `[U]` (р.1.8)

3.5.3. Изменение медиа/плана ДОЛЖНО учитывать пик временного хранения, действующей версии и отката плюс системный запас; обрыв загрузки, неверный файл или нехватка места не должны изменять активный комплект. `[N]` (р.1.4)

3.5.4. Backup/restore ДОЛЖЕН сохранять согласованный набор настроек, расписаний, плана и необходимых пользовательских медиа с версиями схем. Восстановление проверяет совместимость/полноту/место до применения; частичный архив отклоняется, обновление не должно молча заменять пользовательские данные. `[N]` (р.1.4)

3.5.5. Schoolbell ДОЛЖЕН владеть схемой настроек/расписаний/плана, семантической валидацией, миграциями и активацией при использовании общего механизма core 6.6 (базовый контракт ТЗ 1.16, не версия API). Импорт проверяет календарь и ссылки на media ID/revision до активации; ошибка сохраняет старую конфигурацию. Конкретная схема остаётся открытой. `[N]` (р.1.5)

3.5.6. Schoolbell ДОЛЖЕН различать шаблон партии с переносимыми планами/настройками и backup конкретного устройства по 3.5.4. Шаблон не переносит уникальные адреса/секреты/аппаратные привязки; локальные зависимости и мелодии проверяются. Подготовка импорта не запускает звук и не меняет активные регистрации; активация выполняется явно по согласованному контракту пакета. `[N]` (р.1.5)

3.5.7. Приём заявки ДОЛЖЕН фиксировать и удерживать конкретную существующую
ревизию мелодии до подтверждения приёма; отказ допуска освобождает временное
удержание. Отсутствующая ревизия отклоняется, без подстановки текущей версии
того же ID. `[N]` (р.1.8)

3.5.8. Замена мелодии ДОЛЖНА создавать новую неизменяемую ревизию; ожидающие
и активные заявки сохраняют прежнюю. Перед запуском адаптер получает проверенный
файл удерживаемой ревизии с защитой от подмены между проверкой и использованием;
конкретный механизм определяется по 8.2.11. `[N]` (р.1.8)

3.5.9. Ссылка заявки на медиа ДОЛЖНА освобождаться после её отмены/expiry,
подтверждённого отказа без процесса либо подтверждённого завершения процесса.
При неопределённом исходе ссылка сохраняется; освобождение ссылки не удаляет
ревизию, удерживаемую планом, другой заявкой, backup или откатом. `[N]` (р.1.8)

3.5.10. Пакет ДОЛЖЕН хранить пользовательские мелодии и каталог в отдельной постоянной области данных schoolbell; обновление пакета не перезаписывает их. Штатные мелодии остаются ресурсами пакета; временные runtime-данные не заменяют постоянное хранилище. Пути закреплены в 3.5.30. `[U]` (р.1.18)

3.5.11. При недоступности настроенного постоянного хранилища пакет ДОЛЖЕН сообщать об ошибке и блокировать автоматические звонки, не создавая вместо него пустую медиатеку. Поддержка внешнего накопителя отложена; это правило распространяется на неё при реализации. `[N]` (р.1.17)

3.5.12. Каталог ДОЛЖЕН описывать каждую неизменяемую ревизию стабильным ID мелодии, идентификатором ревизии, фактическим размером, SHA-256 и проверенными параметрами аудио. Пользовательское имя хранится отдельно и не используется как путь. Поля и хеш-ревизии определены в 3.5.28–3.5.29; оставшиеся границы полей — 8.2.12. `[U]` (р.1.18)

3.5.13. Сохранение ДОЛЖНО публиковать согласованный комплект каталога, настроек и ссылок расписаний/планов на точные ревизии. Все необходимые файлы должны существовать и пройти проверку до публикации; смешивание частей разных комплектов запрещено. Поколения публикации остаются служебными метаданными вне пользовательских настроек. `[N]` (р.1.17)

3.5.14. Загрузка ДОЛЖНА проходить ограниченный потоковый приём, проверку MP3 и совместимости, сохранение новой ревизии и подготовку комплекта до публикации. Размещение всего загружаемого MP3 в RAM не допускается; пределы заданы в 5.3, конкретный валидатор остаётся по 8.2.12. `[U]` (р.1.18)

3.5.15. До приёма загрузки пакет ДОЛЖЕН проверять пиковое место для новой ревизии, временных данных, метаданных, действующего комплекта, удерживаемых ревизий и отката плюс системный запас. Фактический размер ограничивается во время приёма; ошибки места обрабатываются и после предварительной проверки. Квоты и запас заданы в 5.3; метод измерения — 8.2.12. `[U]` (р.1.18)

3.5.16. Менеджер медиатеки ДОЛЖЕН разрешать не более одной изменяющей операции одновременно, включая замену ссылок, публикацию, восстановление и удаление. Конкурентная операция не должна терять уже сохранённые изменения; конкретный API допуска определяется по 8.2.12. `[N]` (р.1.17)

3.5.17. Публикация новой ревизии мелодии НЕ ДОЛЖНА автоматически менять сохранённые планы и расписания. Отдельное действие замены в выбранных расписаниях показывает затронутые ссылки и публикует их согласованно; ранее принятые заявки сохраняют прежнюю ревизию по 3.5.7–3.5.9. `[N]` (р.1.17)

3.5.18. Ответ об успешном сохранении ДОЛЖЕН выдаваться только после подтверждения постоянной записи файлов, метаданных и публикации комплекта. Протокол обязан учитывать синхронизацию файлов и соответствующих каталогов; одного rename недостаточно. Порядок фиксации задан в 3.5.34–3.5.36; точные аварийные переходы и поддерживаемые файловые системы остаются по 8.2.12. `[U]` (р.1.18)

3.5.19. При ошибке в фазе фиксации, когда прежний либо новый результат ещё нельзя установить, пакет ДОЛЖЕН сообщать «исход требует проверки» и сверять постоянное состояние до новых изменений. Потеря ответа об успехе не должна приводить к слепому повтору публикации или запуску звука. Формат результата и сверки определяется по 8.2.12. `[N]` (р.1.17)

3.5.20. При запуске восстановление ДОЛЖНО проверять опубликованный комплект, целостность и полноту необходимых ему файлов и ссылок. Незавершённые загрузки и неопубликованные комплекты не активируются; повтор восстановления не должен менять уже установленный согласованный результат. `[N]` (р.1.17)

3.5.21. При повреждении текущего комплекта восстановление ДОЛЖНО проверять предыдущий сохранённый комплект целиком, без подстановки отдельных его файлов в текущий. Исправный предыдущий комплект доступен для просмотра; автоматические звонки остаются приостановленными до явного подтверждения пользователя и проверки готовности исполнения. `[N]` (р.1.17)

3.5.22. При отсутствии исправного текущего и предыдущего комплекта пакет ДОЛЖЕН переходить в диагностируемый режим восстановления без автоматического создания пустого плана и без автоматических звонков. Доступность хранилища и ошибки проверки должны различаться в диагностике. `[N]` (р.1.17)

3.5.23. После перезагрузки пакет НЕ ДОЛЖЕН автоматически повторять старые заявки и догонять пропущенные звонки. Допуск будущих событий требует проверенного комплекта, достоверного времени и готового исполнителя; пауза после отката по 3.5.21 сохраняется. `[N]` (р.1.17)

3.5.24. После аварии только службы пакет ДОЛЖЕН до новых запусков и удаления потенциально удерживаемых файлов исключить исполнение старого проигрывателя по контракту 3.6.16. Неопределённость сохраняет блокировку; отсутствие Lua-ссылок не доказывает отсутствия процесса. `[N]` (р.1.17)

3.5.25. Удаление ревизии ДОЛЖНО допускаться только после восстановления и проверки ссылок всех сохранённых планов, действующего комплекта, отката, незавершённого backup и живых удержаний. При неопределённых ссылках удаление запрещено; незавершённая очистка не должна повреждать сохраняемый комплект. `[N]` (р.1.17)

3.5.26. Пакет ДОЛЖЕН по умолчанию сохранять один предыдущий согласованный комплект и необходимые ему ревизии для отката. Это не внешний backup; общие неизменяемые файлы могут использоваться несколькими комплектами без дублирования. Замена предыдущего комплекта допускается лишь после подтверждённой публикации нового и проверки остальных ссылок. `[N]` (р.1.17)

3.5.27. Публикация, восстановление и очистка НЕ ДОЛЖНЫ сами запускать звук. Гарантии восстановления после питания должны проверяться отдельно на целевом носителе и файловой системе; host-модель отказов не является подтверждением аппаратной долговечности. `[N]` (р.1.17)

3.5.28. Каталог ДОЛЖЕН использовать строгий JSON с отказом повторяющихся ключей и неизвестных полей, разбираемый штатным строгим JSON-декодером. Запись мелодии содержит id, name, revisions; запись ревизии — revision, source, size_bytes, audio; audio содержит format, duration_ms, sample_rate_hz, channels. Произвольные пути в этих записях запрещены. Оболочка каталога и точные границы полей уточняются по 8.2.12. `[N]` (р.1.18)

3.5.29. Поле revision ДОЛЖНО равняться SHA-256 точного содержимого файла в виде 64 шестнадцатеричных символов; отдельный дублирующий хеш ревизии не требуется. Source принимает bundled либо user; format — mp3. Размер и параметры аудио определяются проверяющим модулем, а не доверяются браузеру. Ссылки расписания содержат точную пару id/revision; одинаковое содержимое допускает общий неизменяемый файл. `[N]` (р.1.18)

3.5.30. Постоянное хранилище ДОЛЖНО использовать корень /etc/modbus-schoolbell/data с objects для пользовательских MP3, snapshots для неизменяемых комплектов, staging для подготовки, current.json для текущего/предыдущего комплекта и recovery.json для восстановления. Штатные файлы остаются в /usr/share/modbus-schoolbell/melodies. Изменяемые части транзакции находятся на одной файловой системе; пути вычисляет пакет. `[N]` (р.1.18)

3.5.31. Снимок ДОЛЖЕН связывать каталог, настройки, расписания и планы целиком. Служебное описание перечисляет фиксированные имена файлов, их размеры и SHA-256. Выбор отдельных частей разных снимков запрещён. Единственная версия внутреннего формата хранится в служебном описании, не в пользовательских настройках; точные имена/поля определяются по 8.2.12. `[N]` (р.1.18)

3.5.32. Указатель current.json ДОЛЖЕН описывать текущий и предыдущий снимки, хеши их служебных описаний и целое служебное поколение, не зависящее от RTC. Точные поля, диапазон поколения, представление отсутствующего предыдущего снимка и проверка самого указателя определяются по 8.2.12. `[N]` (р.1.18)

3.5.33. Перед изменением менеджер ДОЛЖЕН получить исключительное владение и сверить ожидаемое поколение с текущим. Несовпадение возвращает conflict без публикации и без потери чужих изменений; конкретные поля запроса определяются по 8.2.12. `[N]` (р.1.18)

3.5.34. До замены current.json менеджер ДОЛЖЕН завершить ограниченный приём и проверку MP3, сохранить и синхронизировать неизменяемый объект и его каталог, затем подготовить и проверить полный снимок и синхронизировать его файлы и каталоги. Неподготовленный снимок публиковать запрещено. `[N]` (р.1.18)

3.5.35. Перед публикацией нового указателя менеджер ДОЛЖЕН сохранить проверенную копию прежнего current.json в recovery.json и подтвердить её постоянную запись. Это подготовка пути восстановления, а не публикация нового снимка. Первичная инициализация без прежнего указателя и безопасная замена recovery.json уточняются по 8.2.12. `[N]` (р.1.18)

3.5.36. Менеджер ДОЛЖЕН публиковать новый указатель через временный файл: новый текущий снимок и прежний текущий как предыдущий, запись и синхронизация временного файла, rename поверх current.json, затем синхронизация родительского каталога. Успех допустим только после подтверждения всей последовательности; rename сам по себе не подтверждает долговечность. `[N]` (р.1.18)

3.5.37. Результат изменения ДОЛЖЕН различать saved (постоянная фиксация подтверждена), rejected (изменение не опубликовано), conflict (изменилось исходное поколение) и needs_recovery (исход фиксации нельзя установить). Ошибка после возможной публикации не должна выдавать rejected без доказательства отсутствия публикации. `[N]` (р.1.18)

3.5.38. Операция ДОЛЖНА иметь собственный ID, сохраняемый в описании снимка. После потери ответа клиент сначала сверяет результат по ID; неизвестный или уже очищенный ID не является доказательством отказа. Формат ID, запрос сверки и срок доступности результата определяются по 8.2.12. `[N]` (р.1.18)

3.5.39. Восстановление ДОЛЖНО проверять current.json и весь выбранный комплект; при повреждении использовать проверенные сведения recovery.json для поиска прежнего. Автоматический выбор каталога по наиболее новому имени или времени запрещён. При недостоверности сведений — режим восстановления; при fallback — пауза по 3.5.21. `[N]` (р.1.18)

3.5.40. Расчёт места ДОЛЖЕН учитывать временное сосуществование нового, текущего и прежнего откатного поколений. Файлы, удерживаемые recovery.json, не удаляются. После подтверждённой фиксации и безопасной очистки остаются текущий и один предыдущий комплект; остальные ссылки по 3.5.25 сохраняют нужные объекты. Порядок обновления recovery.json перед очисткой уточняется по 8.2.12. `[N]` (р.1.18)

3.5.41. Очистка ДОЛЖНА выполняться отдельно после фиксации и не быть условием выдачи saved. Ошибка очистки не отменяет уже подтверждённый коммит; оставшиеся файлы продолжают учитываться в квотах и пике места. Очистка не запускает звук. `[N]` (р.1.18)

3.5.42. Current.json и recovery.json ДОЛЖНЫ иметь поля generation, current, previous, checksum; ссылка имеет snapshot (32 lowercase hex) и sha256 (64 lowercase hex). Previous допускает null. Поколение — целое 1..2147483647 без wrap; идентификатор снимка равен operation ID и не переиспользуется для существующего каталога. `[N]` (р.1.19)

3.5.43. Checksum указателя ДОЛЖЕН вычисляться как SHA-256 последовательности строк с LF после каждой, включая последнюю: schoolbell-pointer, generation десятичными цифрами, current snapshot, current sha256, previous snapshot, previous sha256. Для null previous последние две строки равны -. Это проверка повреждения, не подпись. `[N]` (р.1.19)

3.5.44. Snapshot.json ДОЛЖЕН содержать storage_version=1, operation_id, generation, files; files — ровно четыре записи name/size_bytes/sha256 для catalog.json, settings.json, schedules.json и plans.json без повторов. Содержимое файлов проверяется целиком; hash описания задаётся указателем. `[N]` (р.1.19)

3.5.45. Первичное создание ДОЛЖНО быть явной операцией с ожидаемым поколением 0 при отсутствии указателей и пустых объектах/снимках. При прерывании подготовки неопубликованное не активируется; при возможной публикации проверяется фактически сохранившийся указатель/комплект без слепого повтора. Само отсутствие указателя не разрешает переинициализацию. `[N]` (р.1.19)

3.5.46. После подтверждённой публикации очистка ДОЛЖНА сначала заменить recovery проверенной копией нового current через временную запись, синхронизацию, rename и синхронизацию каталогов. Только после этого допускается удаление более старых комплектов/объектов по проверенным ссылкам. Прерывание до этого сохраняет дополнительное удержание recovery. `[N]` (р.1.19)

3.5.47. Восстановление ДОЛЖНО использовать только проверенные указатели и полные комплекты: current, его previous при повреждении выбранного комплекта, затем current/previous сохранённого recovery. Fallback остаётся paused; при отсутствии проверенного кандидата — recovery_required. Поиск по новейшему имени/mtime запрещён; завершение процесса не считается испытанием питания. `[N]` (р.1.19)

### 3.6. Системный адаптер проигрывателя

3.6.1. Schoolbell ДОЛЖЕН иметь единственного владельца очереди и запускаемых
дочерних процессов для каждого аудиоресурса; адаптер не создаёт аудио-API ядра.
`[N]` (р.1.8)

3.6.2. Первый backend ДОЛЖЕН запускать madplay с согласованным профилем
`--no-tty-control -a 0 -R 48000 -o /dev/dsp`, системным вызовом с отдельными
аргументами и доверенным executable, без shell-команды из пользовательских строк.
Путь мелодии получается из удерживаемой ревизии; ресурсы и зависимости поставки
проверяются отдельно по 5.1.3. `[N]` (р.1.8)

3.6.3. Адаптер ДОЛЖЕН различать приём заявки, фазу launching с занятым ресурсом,
подтверждённый запуск программы и её завершение; наличие PID не является
подтверждением успешного запуска. Формат асинхронного подтверждения определяется
по 8.2.11; ожидание не блокирует рабочий цикл. `[N]` (р.1.8)

3.6.4. Адаптер ДОЛЖЕН получать статус завершения своего дочернего процесса
неблокирующим waitpid(..., WNOHANG), различая обычный exit, его код и завершение
сигналом. Статус связывается с конкретной попыткой запуска и владельцем;
исчезновение PID, его повторное использование и текст журнала не заменяют
такое подтверждение. `[N]` (р.1.8)

3.6.5. При неопределённом результате запуска/наблюдения адаптер ДОЛЖЕН удерживать
аудиоресурс до подтверждения отсутствия возможного проигрывателя или его
завершения, без автоматического повторного запуска этой заявки.
`[N]` (р.1.8)

3.6.6. Таймаут подтверждения запуска ДОЛЖЕН учитываться отдельно от TTL заявки;
его истечение означает неопределённость, а не освобождение ресурса, успешный
запуск или разрешение повтора. Начальное значение — 2000 мс по монотонным
часам от разрешения запуска, настраиваемое отдельно от TTL; это исходная
настройка для проверки, не измеренная норма задержки. `[U]` (р.1.9)

3.6.7. Результат исполнения ДОЛЖЕН различать отказ до запуска, обычный выход
с кодом, завершение сигналом и неизвестный исход; успешные запуск/exit
не объявляются подтверждением слышимости. Быстрый exit не теряется между
фазами запуска и наблюдения. `[N]` (р.1.8)

3.6.8. Первая версия ДОЛЖНА направлять stdout/stderr проигрывателя в /dev/null,
сохраняя ноль байт текстового вывода и структурированную диагностику: этап,
errno, код выхода/сигнал и причину неопределённости. Канал ошибок запуска
по 3.6.12 является отдельным служебным каналом. `[U]` (р.1.9)

3.6.9. После аварии владельца новый экземпляр ДОЛЖЕН блокировать новые
запуски на ресурсе, пока не исключён оставшийся старый проигрыватель.
Один PID-файл не является доказательством владения или завершения; механизм
восстановления определяется и проверяется до интеграции по 8.2.11.
`[N]` (р.1.8)

3.6.10. Восстановление НЕ ДОЛЖНО автоматически воспроизводить заявку
с неизвестным прошлым исходом; отсутствие сохранённого результата не означает,
что звука не было. Exactly-once и сохранение очереди после reboot этим
контрактом не вводятся; политика расписания/paused остаётся по 8.2.3/8.2.9.
`[N]` (р.1.8)

3.6.11. Системные операции ДОЛЖНЫ выполняться отдельным нативным модулем
schoolbell для Lua 5.1; после fork ребёнок выполняет только нативную подготовку
дескрипторов и execve с отдельными аргументами, без возврата в Lua.
Модуль входит в зависимости пакета, а не аудио-API ядра. `[N]` (р.1.9)

3.6.12. Ошибки подготовки/exec ДОЛЖНЫ передаваться по отдельному каналу
с CLOEXEC как этап и errno; родитель читает его неблокирующе и сопоставляет
со статусом ребёнка. EOF сам по себе не доказывает успешный exec:
при недостаточных данных подтверждение запуска остаётся неизвестным.
`[N]` (р.1.9)

3.6.13. Владение ресурсом ДОЛЖНО обеспечиваться flock(LOCK_EX | LOCK_NB)
на неизменяемом в течение работы lock-файле текущей загрузки. Дескриптор
наследуется проигрывателем через exec. Нельзя удалять/заменять lock-файл
или явно снимать общую блокировку, пока возможен старый проигрыватель.
`[N]` (р.1.9)

3.6.14. Допуск конкретной сборки madplay ДОЛЖЕН включать проверку сохранения
унаследованного lock-дескриптора до завершения и чтения мелодии из stdin.
При провале любого условия соответствующий механизм не считается пригодным:
до интеграции требуется отдельно согласовать замену. `[N]` (р.1.9)

3.6.15. Подготовка медиа ДОЛЖНА открывать удерживаемую ревизию относительно
доверенного каталога, проверять компоненты пути без перехода по symlink и
тип файла через fstat; ребёнок получает уже открытый файл как stdin.
Дескриптор защищает идентичность файла, а неизменяемость его содержимого
обеспечивает менеджер опубликованных ревизий. `[N]` (р.1.9)

3.6.16. После аварии сборка неиспользуемых ревизий ДОЛЖНА оставаться запрещённой
до восстановления ссылок и исключения старого проигрывателя. Получение блокировки
ресурса позволяет принимать новые запуски при выполнении остальных проверок,
но не восстанавливает неизвестный результат прежней заявки. `[N]` (р.1.9)

3.6.17. Внутренний API ДОЛЖЕН предоставлять begin(request, media_handle, permit),
poll(handle) и release(handle). Begin после подготовки проверяет permit
непосредственно перед разрешением создания ребёнка и возвращает launching,
не ожидая exec/окончания мелодии. Отказ до возможного создания процесса
может возвращать ошибку без handle; возможный процесс требует сохраняемого
handle для наблюдения, а не неучтённого отказа. `[N]` (р.1.9)

3.6.18. Poll ДОЛЖЕН возвращать снимок launching/running/terminal/uncertain,
отдельное подтверждение запуска и итог not_started/exit/signal/unknown при его
наличии. Номер сигнала не преобразуется в условный exit 128+signal.
Быстрый terminal допустим без ранее наблюдавшегося running. `[N]` (р.1.9)

3.6.19. Handle ДОЛЖЕН различать поколение экземпляра и номер попытки;
PID не заменяет эту идентичность. Повторный poll сохраняет итог до release,
разрешённого лишь после подтверждённого завершения либо отказа без процесса.
Release не является kill/stop и не разрешает освободить uncertain.
`[N]` (р.1.9)

3.6.20. Poll ДОЛЖЕН выполнять один неблокирующий проход наблюдения за вызов,
без ожидания и циклов до готовности. Автоматических повторов запуска — ноль.
Бюджеты системных вызовов подготовки и наблюдения определяются отдельно;
транспортный лимит 4 syscall/endpoint к player не применяется. `[N]` (р.1.9)

3.6.21. API ДОЛЖЕН возвращать begin: handle, err; poll: snapshot, err;
release: ok, err. Handle — непрозрачный нативный объект, не конструируемый
из PID. Снимок-копия содержит generation (строка), attempt_id (целое),
state (launching/running/terminal/uncertain), exec_status
(pending/confirmed/failed/unknown), launch_timeout и cleanup_pending (булевы).
Outcome при наличии: not_started/exit/signal/unknown; exit_code 0..255 только
для exit, signal только для signal, error только при ошибке. Остальные
неприменимые поля отсутствуют. `[N]` (р.1.10)

3.6.22. Структурированная ошибка ДОЛЖНА содержать code и stage из закрытых
наборов приложения G; errno присутствует только для ошибки системного вызова.
Ожидаемый EAGAIN чтения и отсутствие завершения waitpid не являются ошибкой.
При возможном ребёнке ошибка не заменяет сохранённый handle.
`[N]` (р.1.10)

3.6.23. Подтверждение exec ДОЛЖНО опираться на совпадение идентичности
открытого /proc/<pid>/exe с удерживаемым проверенным executable по fstat
для своего ещё не собранного ребёнка. Сравнение строки пути и EOF канала
недостаточны. После получения терминального статуса обращения к /proc
по этому PID запрещены; только адаптер собирает статусы своих детей.
`[N]` (р.1.10)

3.6.24. Адаптер ДОЛЖЕН сохранять подтверждение exec отдельно от завершения:
сообщённая ошибка exec означает failed; ранний exit/signal без наблюдения
executable допускает unknown при terminal. Недоступность /proc не заменяет
доказательство: до таймаута подтверждение pending, затем unknown.
Terminal исключает дальнейшее исполнение попытки, но не доказывает слышимость.
`[N]` (р.1.10)

3.6.25. Служебная ошибка ребёнка ДОЛЖНА передаваться одним кадром 16 байт:
magic[4], version[1], kind[1], stage[2], errno[4], reserved[4], с явно закреплённым
порядком байтов, без сырой C-структуры. Частичный кадр накапливается между poll;
неверный, лишний или оборванный кадр означает protocol_error. Ошибка передачи
кадра не считается успешным запуском. Константы/кодировка заданы в 3.6.29–3.6.30
и приложении H. `[U]` (р.1.11)

3.6.26. Нативные обёртки ДОЛЖНЫ ограничивать число системных операций:
подготовка родителя в begin — 64, ребёнка до exec — 64, один poll — 8,
отдельный проход cleanup/release — 8. Неуспешные попытки входят в бюджет.
Работа загрузчика и player после exec исключена; эти числа не гарантируют
время выполнения вызова. `[N]` (р.1.10)

3.6.27. Один poll ДОЛЖЕН делать не более одного read служебного канала,
не более 16 байт, без скрытых циклов повторов. Уже подтверждённый exec
не проверяется повторно. Часы, read, waitpid, проверка executable и закрытие
временных FD учитываются внутри бюджета poll. `[N]` (р.1.10)

3.6.28. До fork адаптер ДОЛЖЕН резервировать учёт ребёнка и очистки;
нехватка бюджета подготовки отвергает запуск до fork. Незавершённая очистка
продолжается отдельными ограниченными проходами с cleanup_pending=true,
с сохранением занятой записи до завершения. Исчерпание бюджета не разрешает
терять handle, дескриптор или автоматически повторять запуск.
`[N]` (р.1.10)

3.6.29. Кодек ДОЛЖЕН использовать ровно 16 байт, magic ASCII SBPE
(53 42 50 45 hex), version=1, kind=1 (ошибка системной операции ребёнка),
big-endian для всех многобайтовых беззнаковых чисел и reserved=0.
Номера stage заданы в приложении H; в кадре ребёнка допустимы только
stdio=5, exec=8, cleanup=10, errno=1..4095. Неизвестные значения, неверные
этапы/errno/reserved отклоняются как protocol_error без угадывания формата.
`[N]` (р.1.11)

3.6.30. Ребёнок ДОЛЖЕН отправлять не более одного кадра ошибки и завершать
ветку ошибки; код его выхода не заменяет кадр. Внутренняя ошибка без системного
errno не кодируется выдуманным errno: отсутствие достоверного кадра сохраняет
неопределённость подтверждения запуска по 3.6.24. `[N]` (р.1.11)

3.6.31. Поколение экземпляра ДОЛЖНО создаваться из 16 байт системного
генератора случайных данных и представляться 32 строчными hex-символами,
оставаясь неизменным до уничтожения экземпляра. Недоступность источника
отклоняет создание без подстановки PID/времени; тестовый источник подменяется.
Поколение не является секретом или авторизацией; нативный handle дополнительно
привязан к своему экземпляру. `[N]` (р.1.11)

3.6.32. Attempt_id ДОЛЖЕН быть целым в диапазоне 1..4294967295, возрастать
без повторного использования в экземпляре и без перехода через ноль.
Пропуски после отказа подготовки допустимы; исчерпание даёт limit для новых
попыток, не прекращая обслуживания существующих. `[N]` (р.1.11)

3.6.33. Конфигурация и результаты ДОЛЖНЫ проверяться по диапазонам приложения H:
таймаут 100..60000 мс, ресурсы 1..4, записи 1..128, ID ресурса 1..64 ASCII
[A-Za-z0-9_-], exit_code 0..255, положительный signal, допустимый на target,
монотонные миллисекунды 0..2^53-1. Переполнение дедлайна, дроби, NaN,
бесконечности и числовые строки отвергаются без округления/ограничения к границе.
`[N]` (р.1.11)

3.6.34. Первая версия ДОЛЖНА фиксировать при создании экземпляра таймаут,
набор ресурсов и лимит записей, со значениями по умолчанию 2000 мс и 128 записей.
Для каждого ресурса допускается не более одной активной попытки, включая
launching/uncertain; терминальные записи учитываются до release.
Бюджеты 64/64/8/8, read до 16 байт, ноль повторов и ноль байт stdout/stderr

доверенному профилю, не произвольным полям заявки. `[N]` (р.1.11)

при старте; работоспособность проверяется без сети и старого /tmp после reboot.

### 5.3. Начальный профиль медиатеки MR3020

5.3.1. Медиатека ДОЛЖНА ограничивать один каталог 32 логическими мелодиями и 64 ревизиями суммарно. Размер catalog.json не превышает 65536 байт; сумма всех JSON-файлов одного снимка, включая служебное описание, не превышает 262144 байт. `[N]` (р.1.18)

5.3.2. Пакет ДОЛЖЕН ограничивать один пользовательский MP3 524288 байтами и длительностью 60000 мс. Суммарный объём пользовательских MP3, включая старые удерживаемые файлы и незавершённую загрузку, не превышает 2097152 байт. Общий объект считается по физическому файлу, ссылки на него не умножают его размер. Метаданные и запас проверяются дополнительно, а не вычитаются из обязанности учёта пика. `[N]` (р.1.18)

5.3.3. Потоковый буфер загрузки ДОЛЖЕН быть ограничен 16384 байтами; одновременно допускается одна загрузка/изменяющая операция. Этот предел не является пределом всей Lua RAM, памяти парсера JSON или валидатора MP3. `[N]` (р.1.18)

5.3.4. После расчётного пика изменений ДОЛЖЕН оставаться свободный запас не меньше max(524288 байт, 10% ёмкости постоянного раздела). В пик входят файлы, метаданные, временные данные и откат; учитываются фактически доступное место и ошибки ENOSPC после предварительной проверки. Квоты — верхние пределы, не обещание наличия места. Метод измерения доступности/ёмкости и округления процента уточняется по 8.2.12. `[N]` (р.1.18)

5.3.5. До рабочего подключения ДОЛЖНЫ быть проверены RAM разбора/валидации, пределы FD и пригодность выбранной ФС к протоколу фиксации. Предел 16 lifetime публикаций native-прототипа не является квотой постоянной медиатеки; его адаптация должна сохранять живые удержания. Принятые квоты не являются измеренным бюджетом роутера или аппаратной гарантией питания. `[N]` (р.1.18)

## Приложение A. Границы

ТЗ не копирует алгоритм общего scheduler и событийного runtime. Множественные
подписки — контракт ядра; выбор действий школьного звонка — контракт пакета.
Аудиособытия started/finished/failed и идентификаторы запросов ещё проектируются.
Старые скрипты не устанавливаются как реализация новых требований.

## Приложение D. Изолированная очередь (информативно, р.1.7)

## Приложение F. Системные механизмы и API (информативно, р.1.9)

[PLAYER_SYSTEM_API](PLAYER_SYSTEM_API.md) описывает принятые решения.
API модели р.1.7 не изменён. CLOEXEC/EOF не заменяет доказательство exec;
подтверждение запуска и наблюдаемый статус завершения независимы.
После завершения сигналом exec может остаться неизвестным, но доказанное
отсутствие процесса позволяет завершить владение ресурсом без повторного звука.

flock защищает взаимодействующие экземпляры schoolbell, а не произвольные

FD конкретным madplay — условие пригодности, не уже подтверждённый факт.
Открытый файл не защищает содержимое от записи: опубликованные ревизии неизменяемы.

Исходные настройки: launch timeout 2000 мс (настраиваемый), ноль повторов,
ноль байт stdout/stderr, один неблокирующий проход poll. Это не измеренные
нормы CPU/RAM/latency. Подготовка файлов может иметь задержку ОС; begin
не обещает жёсткое реальное время и не ждёт exec/проигрывания.
Новые TC-50–55 не выполнялись; код, IPK, ядро и роутер не изменены.


## Приложение G. Результаты и бюджеты (информативно, р.1.10)

[PLAYER_RESULTS](PLAYER_RESULTS.md) содержит согласованные поля и правила.
Закрытый набор code для 3.6.22:
invalid_argument, invalid_handle, stale_handle, busy, limit, media_invalid,
permit_denied, clock_error, spawn_failed, exec_failed, observe_failed,
protocol_error, launch_timeout, not_terminal, cleanup_failed.
Закрытый набор stage:

проверку PID после reap либо позволять другому обработчику собирать этих детей.

Считаются системные операции нативных обёрток, включая ошибки и явные повторы;
бюджет cleanup не добавляется скрыто к 8 операциям одного poll.
Выделение памяти/время файлового I/O не получают гарантии задержки из этих квот.
Обязательна возможность завершить уже начатую очистку последующими проходами.
Реализация, новые исполняемые тесты, target-проверки и звук отсутствуют.

## Приложение I. Кодек и модель API (информативно, р.1.12)

[PLAYER_MODEL](PLAYER_MODEL.md) описывает подменяемую границу и ограничения.
player_codec.lua реализует SBPE/v1 без системных операций.
player_model.lua хранит состояния и вызывает только переданные функции.
Подготовка и cleanup задаются тестовыми процедурами, вызывающими примитивы
через ограниченный счётчик. Child_setup — отдельный симулятор бюджета ребёнка,
не fork/exec. Подмены обязаны не скрывать несколько системных операций за одной.

Generation проверяется на подменяемых 16 байтах; handle — таблица с приватной
проверкой идентичности, не native userdata. Counter отдельно тестируется у
верхней границы. Signal проверяется переданным чистым платформенным предикатом.
Модель не является защитой от злонамеренного callback и не прерывает зависший Lua.

Begin моделирует только request.resource и доверенный media_handle. Существующая
playback_queue.lua не изменена и не подключена. Медиакаталог, владение FD,
блокировка и доказательство exec имитируются, не проверяются на ОС.
При возможном fork с потерянным PID handle остаётся uncertain; модель не
выдумывает PID и не освобождает ресурс. Recovery такого случая впереди.

Сначала известный exit позволяет terminal, затем ещё может дочитываться кадр.
Release до конца канала отклоняется; окончательный результат после EOF/ошибки
протокола стабилен. Cleanup выполняется явно и ограниченно; отказ begin может
вернуть терминальный handle для оставшейся очистки. Её операции при begin
входят в оставшийся бюджет 64, не добавляют скрытый бюджет.

Тесты TC-66/67 подтверждают только модель. Нет native module, реальных процессов,
звука, ядра, IPK-изменений или обращения к роутеру. Свойства madplay,
системные часы/random и атомарность медиахранилища остаются отдельными задачами.


## Приложение J. Изолированный Linux-адаптер (информативно, р.1.13)

[LINUX_PLAYER](LINUX_PLAYER.md) описывает C API и условия использования.
Реализация в packages/schoolbell/native/player.c, без подключения Lua/очереди,
ядра или IPK. Используется отдельная доверенная тестовая программа вместо
madplay. Профиль программы задаётся конструктором, не заявкой пользователя.

Host-механизмы: getrandom(GRND_NONBLOCK), CLOCK_MONOTONIC, fork/execve через
удерживаемый executable FD, CLOEXEC error pipe, /proc executable identity,
waitpid(WNOHANG), flock и файл на stdin. До fork перечисляются унаследованные
FD через /proc/self/fd: максимум 32, иначе отказ до запуска. Ребёнок закрывает
лишние FD по списку; его путь не возвращается в Lua и не выделяет память.
Однопоточный процесс, стандартные FD 0/1/2 открыты, SIGCHLD по умолчанию,
нет стороннего reaper или открытия FD в обработчике сигнала — условия C-границы.

C-результат имеет enum/фиксированные поля и errno=0 для отсутствия ошибки;
преобразование в Lua-снимок с отсутствующими неприменимыми полями предстоит.
C handle проверяет owner/slot/attempt, не является публичным credential;
поколение — 16 случайных байт в hex. Полный атомарный медиаменеджер отсутствует:
caller удерживает неизменяемый regular file, адаптер переоткрывает его через FD
с проверкой identity и независимым смещением. Доверенный lock-каталог передан
дескриптором; его жизненный цикл и неизменность inode обеспечивает владелец.

Подготовка родителя укладывается в 64 операции с резервом очистки;
poll и release — не более 8, чтение канала одно до 16 байт.
Статический путь ребёнка ограничен списком 32 FD и имеет запас до 64 операций.
Это не предел времени выполнения ОС. Измерения на MR3020 не проводились.

TC-68/69 проверяют наследование lock-FD тестовым ребёнком, не madplay.
Нельзя выдавать этот результат за готовность target ABI, свойства madplay,
автономную поставку, восстановление медиатеки или слышимость. При ECHILD
C backend сохраняет uncertain и запрещает release; административное recovery
этого случая не реализовано. Никаких сигналов stop адаптер не посылает.


## Приложение K. Lua-привязка Linux player (информативно, р.1.14)

[LUA_PLAYER](LUA_PLAYER.md) описывает отдельный модуль schoolbell.player_linux,
new(options) и методы begin/poll/release/pending/close через двоеточие.
Результаты соответствуют 3.6.21–3.6.24; третий stats.calls диагностический.
FD и argv доверенные, медиаменеджер и очередь не подключены.

Userdata выделяются и удерживаются registry до fork; handle удерживает владельца.
Успешный release снимает удержание. Потерянная Lua-ссылка восстанавливается
через pending, в том числе после ошибки Lua-памяти при выдаче результата begin.
Ошибка permit защищена pcall и означает отказ до fork; callback чистый/ограниченный,
не yield и не меняет FD. Повторный вход блокируется. Ребёнок не выполняет Lua.

GC пустого владельца закрывает C backend. Владелец обязан обслужить и освободить
все handles, затем close до lua_close. Завершение VM с живыми записями не является
реализованным recovery: неопределённые ресурсы остаются до выхода процесса.
Нельзя применять debug/registry к приватным объектам; это не sandbox.

TC-70 проверяет host Lua 5.1 и тестовый ребёнок, не madplay, target ABI/ресурсы,
медиаревизии, очередь или работу ядра. Предыдущие приложения описывают этапы;
отсутствовавшая в р.1.13 Lua-привязка реализована здесь только изолированно.


## Приложение L. Очередь с Linux player (информативно, р.1.15)

[QUEUE_LINUX](QUEUE_LINUX.md) описывает schoolbell.queue_player:
отдельный пустой native экземпляр, доверенный resolver точной ревизии в FD,
тот же набор ресурсов, что у очереди. Исходный файл удерживается host-владельцем;
production admission при submit и управление медиаревизиями не реализованы.

Begin означает starting, не started. Native running с confirmed exec даёт
started; terminal сначала проходит release. До окончания cleanup очередь
сохраняет finishing и занятость ресурса. Signal — отдельное поле при failed,
не искусственный exit_code. Неподтверждённый exec или ошибка наблюдения не
превращаются в успех только по exit=0. Старый fake-player API совместим.

Потерянный результат begin сверяется с pending при исключительном владении;
пока handle не найден, новые старты других ресурсов откладываются (deferred),
без повторного запуска заявки. Потеря release допускает stale_handle только
после собственного исключения release; терминальный снимок сохранён заранее.
Несколько неучтённых handles сохраняют uncertain.

За шаг на ресурс не более одного poll, одного release и одного следующего
begin: их собственные бюджеты 8/8/64 складываются, это не общий бюджет 8 на step.
Resolver/часы/GC остаются доверенными ограниченными callbacks, не real-time.
Неопределённость не освобождает ресурс по времени. Close не отменяет очередь:
caller сначала завершает/отменяет queued и обслуживает active.

Нет восстановления очереди после аварии VM/процесса или произвольного OOM
в step, persistent ack/replay, active stop, UI/core API, target/madplay/звука.
TC-71 — host-композиция с fixture, не полная приёмка системного пакета.

## Приложение M. Удержание ревизии (информативно, р.1.16)

## Приложение N. Постоянная медиатека (информативно, р.1.17)

[MEDIA_PERSISTENCE](MEDIA_PERSISTENCE.md) — памятка принятой политики.
Новые 3.5.10–3.5.27 и TC-73–82 описывают целевое поведение, не реализацию.
media_linux хранит каталог только в памяти; 16 lifetime публикаций и 128 leases
остаются защитными пределами текущего host-прототипа, не квотами постоянной
медиатеки. Нужны дисковый каталог, проверка файлов/ссылок, транзакция публикации,
восстановление и безопасная очистка; интеграция общего механизма core 6.6 ещё
предстоит. Общий storage API ядра этой ревизией не меняется.

Согласованные параметры: одна изменяющая операция одновременно, по умолчанию
один предыдущий согласованный комплект; ноль автоматических повторов старых
заявок/догоняющих звонков после перезагрузки. Размеры MP3, квоты RAM/носителя,
точные форматы и протокол фиксации не назначены (8.2.12).
Откат данных не означает разрешения звука: после fallback требуется подтверждение
и обычные проверки времени/исполнителя. Внешний накопитель отложен.
Эта ветка не меняет код, исполняемые тесты, UI, IPK, звук или роутер.

## Приложение O. Формат, квоты и фиксация (информативно, р.1.18)

[MEDIA_FORMAT](MEDIA_FORMAT.md) описывает принятый первый профиль и значения
раздела 5.3. Прежнее приложение N отражает этап 1.17: его открытые вопросы о путях,
квотах и порядке публикации частично решены здесь. TC-83–90 плановые.
Реализация media_linux остаётся только памятью/FD; нет дискового каталога,
валидатора MP3, транзакции или восстановления. Следующий шаг — точные поля
служебных указателей и аварийные переходы по 8.2.12; реализация ещё не разрешена.
Корень и квоты относятся к schoolbell, не меняют общий storage API ядра.
Ветка меняет только документы; UI, IPK, код, звук и роутер не изменены.

## Приложение P. Изолированный менеджер (информативно, р.1.19)

[MEDIA_MANAGER](MEDIA_MANAGER.md) описывает API, backend и границы.
Поддержан prepared user-object режим; schedules/plans — проверяемые списки
зависимостей, не рабочий формат календаря. MP3-валидатор отсутствует, известный
файл передаётся доверенным caller. Только 16 КиБ на каждый JSON из-за штатного
строгого decoder; будущий предел catalog 64 КиБ не достигнут. Обход — до 512
записей каталога. Нужна дальнейшая интеграция queue/native leases и всех владельцев
планов/backup. Без ownership_safe новые запуски менеджера закрыты для работы.

Host-матрица прерывает отдельный Lua-процесс в 25 точках; это не сбой ядра/питания.
На target используются только новые изолированные каталоги, без madplay/звука,
установки, перезапуска core/demo или изменения настроек. Подтверждение аппаратной
долговечности отложено. Исторические TC-73–90 получают лишь частичное покрытие
TC-91/92; полная приёмка и все численные границы не заявляются проверенными.

Изолированный target-результат TC-92: /tmp и новый постоянный каталог на MR3020, по 25 точек прерывания; контрольные хеши и PID/starttime core/demo сохранены. Стенд удалён. Это не проверка отключения питания или установленного schoolbell runtime.


## Приложение Q. Диагностическая страница (информативно)

Постоянная ручная страница /cgi-bin/luci/admin/schoolbell; зависимости уже
установленного стенда: LuCI/nixio/madplay/USB audio. Это не автономный IPK.
Фиксированный test.mp3: 13104 байта, около 3,3 секунды; madplay -a 0 -R 48000.
100 ожиданий по 100 мс, затем SIGKILL собственного unreaped child и ещё
20 ожиданий по 100 мс. Это ограничение количества вызовов, не realtime-гарантия.
mkdir-блокировка в /tmp остаётся при неизвестном исходе; её нельзя снимать
без проверки живых процессов. Закрытие браузера не является командой STOP.
При аварии LuCI фиксированный короткий процесс может доиграть; блокировка
сохраняется. Этот компромисс разрешён только для ручного теста, не расписаний.
Нельзя одновременно запускать madplay вручную или production worker:
блокировка координирует только этот диагностический путь.


## Приложение R. Редактор расписаний (информативно)

Отдельный `/etc/schoolbell-editor` (0700): current.json — приватная контрольная
копия с полями data/checksum; previous.json — предыдущее подтверждённое
содержимое. Это служебное хранение редактора, не формат settings.json,
пакетного импорта, backup или production-снимка медиатеки. В пользовательском
data только schedules, pre_minutes, pre_media; отдельные версии не добавляются.
Ревизия HTTP — SHA256 канонического data, отсутствие первого сохранения — empty.
Переход A→B→A считается тем же содержимым; это не номер активации.
Годовые планы и ссылки из них пока отсутствуют; полное требование 3.4.5 остаётся
частично реализованным. Только test.mp3 — явно ограниченный этап, не полный паритет.

Тело формы ограничено 49152 байт до разбора; data — 12288, checkpoint — 16384.
Предзвонок 1–10 минут по календарной модели. Пик учитывает две временные записи
по 16384 и ещё 16384 байт на выделение/метаданные сверх уже занятых файлов;
после пика остаётся запас 5.3.4. ENOSPC проверяется и после предварительной оценки.
Никаких фоновых записей при редактировании: запись только кнопкой сохранения.
Ошибки checksum/отсутствие current при наличии previous блокируют запись;
автоматического fallback с активацией нет. Остаточный next никогда не
становится current при чтении. Lock освобождается ОС при завершении процесса.
Успешный fsync на целевой ФС не доказывает поведение при физическом отключении питания.


## Приложение S. Годовые планы редактора (информативно)

Необязательное поле plans: массив до 8 объектов {year, schedule_ids, days}.
year — целое 1–9999, без повторов. schedule_ids — уникальная палитра до
16 существующих ID; days — ASCII-строка ровно 365/366 символов от 1 января.
Точка означает тихий день, A–P — индекс 1–16 палитры. Иные коды и отсутствующие
элементы палитры отвергаются. Такой формат позволяет хранить весь год в прежнем
лимите 12 КиБ даже с длинными ID. Все квоты действуют совместно.
Перед проверкой календарного модуля компактные назначения разворачиваются в
его существующую карту YYYY-MM-DD→schedule ID. Это не изменение API ядра.

Preview использует постоянное нулевое смещение только как координату арифметики
местных часов; UTC/epoch не возвращаются. Реальные tzdb/gap/fold и clock-quality
проверяются перед будущей активацией, не заменяются этой координатой.
Существующие расписания читаются без миграционной записи. Старый код редактора
не понимает plans: после первого нового сохранения откат требует совместимой
версии либо осознанного восстановления согласованной копии. Новые планы нельзя
молча удалять ради downgrade.

Уточнение UI по отзыву владельца: основное назначение дат — раскраска выбранным расписанием (левая кнопка и протягивание; на сенсорном экране нажатия), диапазоны — дополнительные инструменты. Проверка включает сохранение раскрашенных дат после reload. Отключённая кнопка без правок не означает ожидание; запрос ограничен 15 секундами, неопределённое сохранение требует сверки без автоповтора.

Плашка дежурного показывает режим и состояние черновика, версии установленного пакета/ядра и отдельную ревизию тестового UI. Пока нет активного исполнителя, следующий звонок обозначается как не запланированный; отсчёт по черновику запрещён. Отсутствующие метаданные версии обозначаются явно.
