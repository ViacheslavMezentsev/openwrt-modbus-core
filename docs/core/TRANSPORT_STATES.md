# Изолированные состояния транспорта

[English](TRANSPORT_STATES.en.md) · [Принятый контракт](TRANSPORT_CONTRACT.md)

`python3 scripts/test_transport_states.py` — 37 детерминированных тестов.
Они входят в `make all` и `make ci-core`. Код модели:
[scripts/transport_states.py](../../scripts/transport_states.py).
Тесты: [scripts/test_transport_states.py](../../scripts/test_transport_states.py).

Это исполняемая модель принятого контракта, как предыдущая модель раундов:
Python используется только на хосте и не добавляет зависимость роутеру.
Нет socket/serial, sleep, часов ОС, UCI, Lua/backend, группировки или
интеграции с modbusd. Композиция с очередями/раундами описана ниже. Файлы не входят в IPK. Существующий runtime
не изменён. Тест модели не означает готовность драйвера или аппаратный PASS.

## Управление опытом

Наблюдения valid/last_success разделены по логическому устройству, максимум 32;
это не реализация runtime-кэша или TTL.

Один экземпляр `Transport` моделирует одну линию/точку TCP с одной принятой
операцией. Состояния: idle, queued, setup, send, tx_completion, receive, retry,
quarantine, desynchronized. Backoff выражен `ready_at`/`retry_at`.

- `tick(ms)` задаёт монотонное время, обслуживает сроки и разрешённый повтор;
  обратный ход, дроби и bool отклоняются. UTC отсутствует по конструкции.
- `admit(Request, expiry)` фиксирует Dop. `begin()` — отдельное решение будущего
  планировщика. Модель не выбирает следующую операцию и не создаёт очередь.
- `setup_done(generation)` завершает моделируемую подготовку. `wire` содержит
  фактические байты запроса для fake backend. `tx(n, generation)` сообщает число
  принятых TX байтов: 0 соответствует EAGAIN, частичный write не меняет Da.
- `tx_complete(generation)` подтверждает внешний факт окончания TX. Без него
  при ошибке RTU требуется manual даже после записи всего кадра. Модель не
  вызывает tcdrain и не доказывает, когда USB действительно передал байты.
- `receive(bytes, generation)` подаёт не более 512 байт за событие. TCP пустой
  read — EOF; для RTU пустой ввод не событие. Ошибку backend задаёт `io_error`.
- `cancel()` сохраняет неопределённость возможной записи и восстановление линии.
  `drain_results()` возвращает единственный терминальный результат; до его
  получения следующая операция не принимается. Это ограниченный слот модели,
  не замена будущей очереди доставки событий.

TCP callback требует текущую generation. Закрытие сразу инвалидирует старые
callback, даже до нового connect. Сначала проверяется дедлайн, затем байты;
соединение, закрытое проверкой срока, уже не принимает текущий callback.

RTU начинает с неизвестной синхронизации. `confirm_sync(evidence)` записывает
внешнее подтверждение восстановления, а не выполняет reset. Для bounded нужна
ссылка `timing_profile`, однако строка в тесте — синтетическое допущение, не
проверка достоверности аппаратного профиля. После hotplug/restart новый экземпляр
тоже требует подтверждения. Автоматический bounded startup пока не моделируется.
Последний байт на границе B ещё отбрасывается; освобождение происходит строго
после B и межкадровой тишины. Целые мс округляют t3.5 вверх до 4/2/2/2/2 мс.

Часы между событиями продвигает только тест. Каждый метод делает конечную работу;
отдельные состояния не реализуют общий цикл обслуживания; его ограниченная
композиция описана ниже.

## Область байтовой модели

FC01/02/03/04: unit, диапазон адресов, количество, MBAP/CRC, FC и точная длина
данных. FC06 — проба исходов записи и echo; этот этап не расширяет allowlist
действующего ядра. Другие записи и загрузчик карт не реализованы. `safe_read`
приходит от доверенного тестового запроса; будущий loader обязан брать его из карты.
Для успешного RTU-ответа ожидается уже подтверждённый TX completion.

| Критерии | Что проверено в модели | Что ещё требуется |
| --- | --- | --- |
| TC-111 | Dop/Da/setup, равенство срока, части TX/RX, expiry до отправки | Настоящие часы/backend и общая очередь |
| TC-112 | 0/3 retries, setup failure, unsafe read, exceptions, отсутствие replay записи | Производственный adapter и карта |
| TC-113 | Поздний неразличимый RTU-ответ, manual и независимый сосед | Реальная линия и reconnect |
| TC-114 | Карантин/B, нарушение B, partial/неподтверждённый TX, startup, expiry | Аппаратный профиль и bounded startup |
| TC-115 | Все разрезы короткого ответа, coalescing, Length/ID/Unit/FC, RX cap, wrap/generation | Настоящий socket, backpressure ОС |
| TC-120 | not_sent/confirmed/unknown, отмена, ровно один результат | Readback и путь команд runtime |
| TC-121 | Округление пауз, ограничение ожидания TX | Wire timing и USB-адаптер |

TC-116/122 остаются плановыми: UCI, совместимость и горячая привязка отсутствуют.
TC-117–119 частично проверяются композицией ниже; grouping ещё отсутствует.
Предыдущие 16 тестов rounds_model продолжают проверять только свою абстрактную модель.

## Композиция очередей и раундов (р.1.21)

[transport_scheduler.py](../../scripts/transport_scheduler.py) использует те же
состояния, не дублируя байтовый обмен. [15 тестов](../../scripts/test_transport_scheduler.py)
запускаются командой `python3 scripts/test_transport_scheduler.py` и в make all/ci-core.

`enqueue` сохраняет время поступления и минимальный срок актуальности. При
передаче в Transport `admitted_at` сохраняет этот срок и start результата.
FIFO ограничена 32 ожидающими на транспорт (настройка 1..128), active отдельно.
Периодический план допускает одну ожидающую операцию сверх active: повторное
поступление объединяется без продления старого срока. Изменение параметров
ожидающего плана отклоняется. Это устранение повторов опроса, не grouping адресов.
Перед выбором проверяются все элементы очереди, включая истёкшие не в начале.

`step(now, events)` принимает максимум одно событие на транспорт. RTU-участники
фиксируются при старте раунда; готовые результаты возвращаются немедленно, следующий
раунд начинается после всех терминальных исходов. Retry остаётся внутри операции.
Карантин после выдачи результата больше не держит барьер. Не готовые порты не входят
в новый раунд. TCP начинает следующий запрос независимо от RTU; FIFO сохраняет
последовательность записи и следующего за ней чтения.

Порядок портов циклически сдвигается. Счётчик реальных изменений `state` проверяет
предел 8 на транспорт за проход; для вызовов оставляется запас переходов. RX+TX
ограничены 512 байтами через одно событие. Непринятое событие остаётся у вызывающего
fake backend; `Pass.consumed` сообщает, что обработано. `Pass.results` передаётся
потребителю без накопления истории в scheduler. За проход может истечь до
7×128 ожидающих операций; это конечная модельная граница, не оценка RAM роутера.

`post_ipc` создаёт синтетическую работу: очередь до 128 единиц, до 8 за проход.
Это тест обслуживания на каждом проходе, не выбранный wire-протокол или квота IPC.
`next_wait` ограничивает ожидание ближайшим сроком и quantum, а без работы возвращает
None для ожидания внешнего события. CPU/RSS, задержки Lua/ОС и реальный IPC не измерены.

Проверены TC-117: 10/20/500 мс, позднее присоединение и retry; TC-118: независимый
TCP, поворот порядка и ограниченные порции/IPC; TC-119: FIFO, очередь, coalescing,
срок от enqueue и истечение не в начале. Полное покрытие этих TC требует grouping,
производственного backend, IPC и отдельной аппаратной проверки.

Следующий этап — безопасное объединение чтений после выбора карты диапазонов;
затем Lua/backend с fake I/O, UCI и однопортовая интеграция. Роутер не изменяется.
