# Событийный API: принятый профиль v1

[English](EVENT_API.en.md) · [ТЗ ядра 1.10](TECHNICAL_SPECIFICATION.md)

Это проект принятого профиля перед реализацией, не выпущенный API core 0.4.0.
Нормативные пункты: core 4.5.17–4.5.24. Квоты, точные ошибки/типы всех полей,
codec и SDK-сигнатуры фиксируются до реализации; примеры ниже иллюстративны.

## Соединение и сообщения

Локальный Unix stream, `<runtime_dir>/events-v1.sock`, socket 0600 в защищённом
каталоге. UTF-8 JSON object + LF; hello согласует api=1 и owner. Один канал на
owner; второй получает owner_busy. Первый профиль доверяет локальным пакетам
администратора: owner — логическое владение, не sandbox между root-процессами.
Веб-пользователь работает через backend пакета, а не напрямую с socket.

| Операция | Основные поля запроса | Смысл ответа |
| --- | --- | --- |
| hello | api, owner | api, instance_id, session_id, limits |
| status | request_id | Своя revision/generation, состояние и ограниченные счётчики ошибок |
| replace | request_id, expected_generation, revision, definitions[], subscriptions[] | Подтверждённое поколение полного набора либо отказ без изменения старого |
| unregister | request_id, expected_generation | Новый пустой набор; старая команда не удаляет новую регистрацию |
| publish | request_id, topic, schema_version, payload, correlation_id? | accepted + event_id либо отказ до принятия |
| ack | request_id, instance_id, event_id, subscription_id, registration_generation | Учёт получения адаптером, не результата действия |

Definition содержит topic/schema_version; subscription — id/topic. Пакет
публикует только собственные объявленные `/packages/<owner>/...`; ядро владеет
`/core` и `/devices`. Подписки точные, без wildcard, могут ждать ещё не объявленный
тип. Два subscription_id одного topic получают отдельные уведомления.

Envelope: instance_id, event_id, topic, schema_version, publisher, mono,
utc либо null, clock_valid, payload; уведомление также содержит subscription_id
и registration_generation. Instance меняется при каждом старте ядра, event ID
не равен seq JSONL. Request ID коррелирует команду/ответ; correlation ID связывает
результат с исходным событием. Форматы идентификаторов ещё уточняются.

## Регистрация и доставка

Replace валидирует всё до применения. Та же revision и структурно то же
содержимое возвращают прежнее generation; та же revision с другим содержимым
даёт конфликт. Новая revision требует актуального expected_generation.
Snapshot действует до конца dispatch; уведомление старого generation может
быть получено уже после ответа на replace. Клиент различает поколения.

Регистрации принадлежат сессии. При разрыве они снимаются по границе snapshot,
ожидающие доставки очищаются; принятые клиентом действия этим не отменяются.
После reconnect клиент сверяет instance/generation и восстанавливает набор явно.
Календарные moments появятся отдельным расширением scheduler, не входят в P01.

Доставка live, без автоматического replay после reconnect/reboot. Одна логическая
отправка в сессии; partial write продолжает её, а не создаёт вторую. Accepted
означает принятие в очередь, ack — получение, отдельное событие клиента — результат.
Потерянный ответ publish означает неопределённость: SDK не повторяет его молча.
Exactly-once и сохранность очередей после питания не обещаются.

Общая очередь заполнена — busy до accepted и без event_id. Очередь получателя
переполнена — отключение только этого клиента и счётчик диагностики; нельзя
обещать сообщение overflow по уже переполненному каналу. Другие клиенты работают.
Pending ack ограничены временем/числом; их истечение не запускает replay.

## Адаптер клиента

Один процесс пакета обслуживает несколько callback. Каждый получает собственную
копию payload; исключение отключает только его до явного успешного reload.
Его неподтверждённые публикации отбрасываются, сторонние прикладные эффекты не
откатываются. Reconnect сам по себе не исправляет отключённый callback.
Звук, очередь мелодий и результаты принадлежат schoolbell, методов play/stop
в ядре нет. Длительная работа клиента не блокирует другие пакеты или опрос.

## Следующие проверки

TC-61–66: handshake, namespace, атомарная/повторная регистрация, поколения,
разрыв, неопределённый publish, overflow/ack, framing и ограниченная работа.
Ограничения frame до decode, глубины/элементов JSON, finite numbers, UTF-8,
различения пустого object/array проверяются новым кодеком. Числа из исследовательских
моделей не являются согласованным бюджетом MR3020.

Синхронный RTU и длинный sleep в существующем modbusd ещё ограничивают IPC.
ТЗ 6.2.4–6.2.7 требует настраиваемых ограниченных повторов безопасных чтений
и обслуживания IPC во время ожиданий. ТЗ 4.7 задаёт объединение совместимых
чтений одного unit/FC без неизвестных адресов и просрочки. Эти функции ещё
не реализованы; таймаут 500 мс (100–2000) уже существует, retry count — нет.
