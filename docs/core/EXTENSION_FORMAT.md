# Формат расширения и пользовательских настроек

[English](EXTENSION_FORMAT.en.md) · [ТЗ ядра](TECHNICAL_SPECIFICATION.md)

Принятый профиль core 1.17; реализация отсутствует.

| Файл в исходниках расширения | Назначение |
| --- | --- |
| package.json | name, displayName, publisher, version, engines, main, contributes по применимости |
| settings.schema.json | Правила пользовательских настроек; подмножество схем ещё выбирается |
| data/ | Планы и другие прикладные документы |
| media/ | Поставляемые ресурсы |

Пользовательский settings.json хранится отдельно в /etc/<package-id>/settings.json,
а не внутри каталога обновляемого кода. Содержит только значения, например:

```json
{
  "enabled": true,
  "volume": 70,
  "activePlan": "school-week",
  "outputDevice": "school-speaker"
}
```

Это пример будущей схемы schoolbell, не утверждение существующего API/полей.
Нет обязательной оболочки payload или служебных версий в этом файле. Сложные
планы и медиа хранятся отдельно, ссылки проверяет пакет.

Идентичность расширения — publisher.name; связь с именем IPK явная. version —
версия расширения, engines — совместимость с API ядра, main — точка входа,
contributes — объявленные возможности/настройки. Семантика зависимостей и
полномочий специфична для OpenWrt и требует отдельного профиля. Не копируем
Node.js/npm/VSIX и не разрешаем scripts самим фактом присутствия package.json.

API в контексте пакета:
- load() → настройки и непрозрачный token;
- prepareImport(source) → проверенный кандидат и изменения;
- save(candidate, token) → сохранение либо конфликт;
- export(kind) → template или backup.

Это семантика, не окончательные сигнатуры и коды ошибок. Импорт не выполняет код
из файла; миграции принадлежат установленному пакету. Подготовка не активирует
действия; сохранение и применение остаются различимыми по контракту пакета.
Токен защищает от потери конкурентных изменений и не хранится в settings.json.

Служебное хранилище содержит отметку успешно применённой версии и данные
восстановления. Экспортный manifest содержит ID расширения и версию создателя;
вид template/backup различается явно. Совместимость задаёт пакет, а не сравнение
номеров само по себе. Одиночный JSON без manifest требует явного контекста импорта
и выбранной политики происхождения; нельзя угадывать нужную миграцию.

Независимая версия формата данных допускается при отдельной необходимости,
а не автоматически для каждого файла. Численные лимиты, точные поля manifest,
секреты, доверие установке, архив, fsync/recovery и атомарность ещё открыты.
Шаблон партии не переносит уникальные привязки и секреты; backup имеет отдельную
политику. Новый профиль не отменяет требования сохранности данных core 6.6.

Источники именования: [VS Code manifest](https://code.visualstudio.com/api/references/extension-manifest)
и [settings](https://code.visualstudio.com/docs/configure/settings).
Заимствуется разделение описания расширения и пользовательских значений.

ТЗ 1.18: минимальный package.json, вычисляемый manifest комплекта и допуск по составу/совместимости/доверию/ресурсам. Декларативная установка без произвольных hooks расширения; доверенные IPK и runtime permissions требуют отдельной политики. TC-104–110 плановые; реализации нет.
