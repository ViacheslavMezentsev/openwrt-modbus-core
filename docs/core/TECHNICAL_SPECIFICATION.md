## 1. Введение

### 1.1. Назначение

1.1.1. Документ описывает ядро и его USB-протокол стенда. Требования к устанавливаемым пакетам ведутся отдельно. Статус остаётся черновиком. (р.1.5)

### 1.2. Область применения

1.2.1. Область: core 0.4.0 и контракт карты прошивки v2. Demo и schoolbell имеют собственные ТЗ. Общие события, подписки и scheduler относятся к развитию ядра; прикладные действия принадлежат клиентам; её API ещё не реализован; принятые правила жизненного цикла заданы в разделе 4.5, сигнатуры API остаются открытыми. RTC, RS-485 и общие выходные политики требуют отдельного согласования. (р.1.8)

### 1.3. Метод формирования

1.3.1. Поведение восстановлено из файлов базового коммита и штатных тестов. Исторические аппаратные результаты в CHANGELOG не являются повторной проверкой в этой ревизии. Старые ненормативные проектные заметки не имеют приоритета над согласованными требованиями.

1.3.2. Целевой реализацией этой редакции считается существующий стенд, без новых команд DO/PWM. Расхождение документа с кодом рассматривается как дефект одного из них и разрешается пересмотром ревизии; известные ограничения перечислены в приложении C. Утверждение документа выполняет владелец.

### 1.4. Термины

| Термин | Определение |
| :--- | :--- |
| Топик | Именованный поток публикаций; не отдельный процесс и не ROS middleware |
| Sample | Полная общая выборка DI/AI/DO/AO одного устройства |
| Baseline | Исходный системный снимок без воспроизведения накопленных нажатий |
| Readback | Чтение coil после записи; подтверждает программную уставку, не физическое свечение |
| Актуальность | Признак последнего успешного опроса и возраст данных, не гарантия работоспособности оборудования |
| AO | В этом прототипе уставка PWM; не аналоговый ЦАП |
| Доверенный обработчик | Lua-код администратора; ограничения движка не являются защитой от враждебного кода |

### 1.5. Источники

1.5.1. Структура документа основана на [embedded-tech-spec](https://github.com/ViacheslavMezentsev/demo-stm32-skills/tree/main/embedded-tech-spec). Контракт USB RTU описан по реализации `rtu.lua`, `serial_rtu.lua` и скетчу; полная сертификация соответствия стандарту Modbus не заявляется.

### 1.6. Соглашения документа

1.6.1. ДОЛЖЕН/ДОЛЖНА/ДОЛЖНО/ДОЛЖНЫ обозначают обязательное требование после утверждения; СЛЕДУЕТ означает рекомендацию; МОЖЕТ означает допустимую возможность.

1.6.2. Номера требований `X.Y.Z` и тестов `TC-NN` постоянны. Новые пункты получают свободные номера; исключённые остаются с пометкой «исключено». Номера вопросов находятся в подразделе 9.2.

1.6.3. Происхождение: `[R]` восстановлено по коду; `[N]` новое требование; `[U]` уточнение существующего поведения. Маркер `[R]` сам по себе не означает аппаратный PASS.

1.6.4. Разделы 1–2 и приложения информативные; разделы 3–6 — нормативные. Раздел 7 задаёт проверки, раздел 8 связывает их с требованиями, раздел 9 фиксирует допущения.

1.6.5. Ссылки из кода оформляются по приложению B. В текущем этапе код не размечается массово: точками входа служит матрица.

1.6.6. Ревизии имеют формат `M.m`: минорная растёт при согласовательном цикле, мажорная при утверждении либо смене архитектуры. Для следующих ревизий добавляются история, блок изменений (новейший сверху), пометки изменённых пунктов и обновления тестов, матрицы, констант и вопросов. Закрытые вопросы остаются с решением. Статусы: «черновик для согласования», «на согласовании», «утверждено».

## 2. Общее описание

### 2.1. Контекст

2.1.1. `modbusd` работает под procd, получает настройки UCI, пишет кэш и журнал в RAM. CLI, CGI и demo читают эти данные. При профиле BluePill ядро обращается к USB CDC платы как Modbus master.

### 2.2. Функции

2.2.1. Профиль `none` обеспечивает ядро и demo без платы. Профиль `bluepill` добавляет общие выборки. Флаг `system_events` добавляет счётчик кнопки, системный LED и доверенные Lua-обработчики.

### 2.3. Роли

| Роль | Взаимодействие |
| :--- | :--- |
| Администратор | UCI, доверенные Lua-файлы, установка IPK, согласование аппаратных испытаний |
| Пользователь стенда | PA0, наблюдение PB2 и CLI |
| Ядро | Единственный штатный владелец USB RTU |
| Demo/CLI/CGI | Потребители файлов кэша и событий, без serial-доступа |
| Разработчик | Локальная сборка, тесты, документация; push/land выполняет владелец |

### 2.4. Границы

2.4.1. Система не гарантирует доставку каждого события, exactly-once при потере питания, реальное время, безопасное отключение выходов при обрыве или изоляцию недоверенных сценариев. USB CDC не заменяет электрический RS-485.

### 2.5. Платформа

2.5.1. Прошивка собирается для F103C8 с 64 КиБ Flash, из которых 8 КиБ заняты Maple bootloader; бюджет приложения 56 КиБ. Сборка использует FQBN `STMicroelectronics:stm32:GenF1:pnum=BLUEPILL_F103C8,usb=CDCgen,opt=oslto,upload_method=dfu2Method`. Версия Arduino CLI не закреплена скриптом; фактическую версию записывают в локальном протоколе сборки.

2.5.2. Lua использует динамическую память. Верхние границы общей RAM, CPU и задержки реакции пока не согласованы. Пакеты ядра скриптовые, сборка OpenWrt/SDK не требуется.

## 3. Модель данных и протокол

### 3.1. Адресация и карта v2 (нормативная)

3.1.1. Кэш ДОЛЖЕН представлять значения как `devices[unit][kind][address]`, где `unit` и нулевой `address` являются строковыми ключами, а `kind` для BluePill равен `di`, `ai`, `do` или `ao`. `[R]`

3.1.2. Общий опрос ДОЛЖЕН читать блоки от адреса 0: FC02/2 DI, FC04/5 AI, FC01/2 DO, FC03/1 AO. `[R]`

3.1.3. Прошивка ДОЛЖНА предоставлять регистры по таблице ниже. Значения 32 бит передаются старшим словом первым. `[R]`

| Область / адрес | Содержание | Тип / единица |
| :--- | :--- | :--- |
| DI 0, 1 | PB12, PB13; логическая единица при LOW, INPUT_PULLUP | bool |
| Coil 0, 1 | PC13 active-low, PB0 active-high | bool |
| IR 0, 1 | PA2, PA1 | АЦП, 0..4095 |
| IR 2, 3 | Соответствующий raw × 3300 / 4095 с целочисленным усечением | мВ, номинальная оценка |
| IR 4 | Младшие 16 бит `millis()/1000` | с, не постоянные часы |
| HR 0 | Уставка PWM PA8 | uint16; физическое применение ограничено 4095 |
| Coil 256 | PB2, системный LED active-high | bool |
| DI 256 / IR 259 | Подавленное по дребезгу состояние PA0 | bool / 0 либо 1 |
| IR 256, 257, 258 | Сигнатура `0x5741`, версия `2`, возможности `3` | uint16 |
| IR 260, 261 | Счётчик нажатий, high/low | uint32, по модулю 2^32 |
| IR 262, 263 | `millis()`, high/low | uint32, мс, по модулю 2^32 |

3.1.4. Системный опрос ДОЛЖЕН отклонять карту, если любое из значений сигнатуры, версии или возможностей отличается от `0x5741`, `2`, `3` соответственно. `[R]`

### 3.2. Кадры USB RTU (нормативные)

3.2.1. Формирование запросов чтения ДОЛЖНО отклонять unit вне 1..247, функцию вне 1..4, адрес вне 0..65535, количество вне 1..2000 бит или 1..125 слов и выход блока за 65536 адресов. Параметры должны быть целыми числами. Это границы кодировщика; транспорт ограничен отдельно в п. 6.1.3. `[R]`

3.2.2. Кодировщик ДОЛЖЕН добавлять CRC с начальным значением `0xFFFF`, отражённым полиномом `0xA001` и младшим байтом результата первым; поля адреса и количества передаются старшим байтом первым. Контрольный запрос unit=1, FC02, start=0, count=2: `01 02 00 00 00 02 F9 CB`. `[R]`

3.2.3. Декодер чтения ДОЛЖЕН отвергать ответ с неверными CRC, unit, функцией, числом байтов либо полной длиной и возвращать Modbus exception как ошибку, а не выборку. `[R]`

3.2.4. FC05 ДОЛЖНА кодировать boolean в `FF 00`/`00 00` и признавать успешным только точное эхо запроса; исключение, короткий, лишний или повреждённый ответ является ошибкой. `[R]`

## 4. Функциональные требования: жизненный цикл и API

### 4.1. Запуск и общий опрос

4.1.1. Ядро ДОЛЖНО завершаться без опроса, если UCI `enabled` отличается от строки `1`. `[R]`

4.1.2. При `profile=none` ядро ДОЛЖНО публиковать heartbeat без открытия serial-порта. `[R]`

4.1.3. BluePill ДОЛЖЕН публиковать `device_sample` и обновлять общие регистры кэша только после успешного чтения всех блоков из п. 3.1.2. Это согласованная программная выборка, не одновременное измерение каналов. `[R]`

4.1.4. При неуспешном общем опросе ядро ДОЛЖНО отмечать `meta.data_valid=false` и `transport_status=offline`, сохраняя предыдущие значения; при успешном - `true`, `online` и время `last_success`. Метаданные характеризуют общий опрос, а не мгновенный статус каждого системного запроса. `[R]`

4.1.5. При включённых системных событиях ядро ДОЛЖНО выполнять общий и системный опрос последовательно через одно открытое соединение; при ошибке закрывать его и откладывать новую попытку не менее чем на 1 с. `[R]`

### 4.2. Системная кнопка и LED

4.2.1. PA0 ДОЛЖЕН использоваться как системная кнопка active-high с INPUT_PULLDOWN и подавлением дребезга 30 мс; удержание не увеличивает счётчик повторно, исходное удержание при старте не считается новым нажатием. `[R]`

4.2.2. Скетч НЕ ДОЛЖЕН локально переключать PB2 по PA0: состояние PB2 определяется системной coil 256, исходно false. `[R]`

4.2.3. Первый системный снимок после запуска или восстановления соединения ДОЛЖЕН быть baseline с нулевым `presses_delta`, без повторения накопленных нажатий. `[R]`

4.2.4. Ядро ДОЛЖНО вычислять приращения счётчика и uptime по модулю 2^32; при `dt > 60000 мс` либо `delta > floor(dt/60 мс)+1` принимать снимок как новый baseline с delta=0. Это эвристика сброса, не идентификатор загрузки MCU. `[R]`

4.2.5. Штатный обработчик ДОЛЖЕН запрашивать инверсию последнего актуального LED только при valid, не-baseline событии кнопки с нечётным `presses_delta`; чётное приращение, отпускание и удержание не создают команду. `[R]`

4.2.6. Ядро ДОЛЖНО признавать команду LED успешной только после успешной FC05 и совпадения последующего FC01 readback с целевым значением. `[R]`

4.2.7. При ошибке выполнения команды, включая неоднозначную потерю ответа, ядро ДОЛЖНО публиковать неуспех, инвалидировать системные данные и отбросить очередь без автоматического повторения команд. `[R]`

### 4.3. Пользовательские Lua-обработчики

4.3.1. Движок ДОЛЖЕН загружать при старте файлы `handlers.d/*.lua` с именами из букв, цифр, `_`, `-` в порядке сортировки; файл возвращает `{topic=string, handle=function}`. Несовместимая спецификация отклоняется с диагностикой. `[R]`

4.3.2. `ctx.topics()` ДОЛЖЕН возвращать отсортированные имена наблюдавшихся движком топиков, а `ctx.get(name)` - копию последнего payload с монотонным `age` в секундах либо nil для неизвестного имени. `[R]`

4.3.3. `ctx.set` ДОЛЖЕН разрешать только boolean-запись `/devices/<unit>/system/led` при valid снимке LED возрастом не более 1 с; остальные адресаты, типы и устаревшие состояния отклоняются. `[R]`

4.3.4. Ошибка callback ДОЛЖНА отменять команды этого вызова и отключать обработчик до перезапуска с публикацией `/core/handler_errors`; уже загруженные исправные обработчики не отключаются. `[R]`

### 4.4. Публикации и диагностика

4.4.1. Система ДОЛЖНА предоставлять `/core/heartbeat`; профиль BluePill добавляет `/devices/<unit>/sample` и `/status`; системный режим добавляет `/system/button`, `/system/led`, `/system/commands` в пространстве устройства и `/core/handler_errors`. `[R]`

4.4.3. CLI ДОЛЖЕН предоставлять `modbus topics`, `modbus echo TOPIC [--count N] [--duration SECONDS]`, `modbus hz TOPIC [--duration SECONDS]` без serial-доступа; echo/hz следуют только новым публикациям после запуска команды. `[R]`

Replace проверяет полный набор definitions/subscriptions и expected_generation; повтор той же revision с тем же содержимым возвращает прежнее generation, иное содержимое той же revision отклоняется. Unregister со старым generation не должен удалять новый набор. Операции/поля описаны в памятке EVENT_API.md; дополнительные детали кодека остаются в 9.2.11. `[N]` (р.1.10)

4.5.20. Ядро ДОЛЖНО разрешать публикацию только объявленных типов собственного /packages/<owner>/ пространства; /core и /devices зарезервированы. Подписки v1 используют точное совпадение topic; разные subscription_id одного клиента получают отдельные уведомления одного события, в том числе после регистрации до появления типа. `[N]` (р.1.10)

4.5.21. Каждое уведомление ДОЛЖНО содержать instance_id, event_id, subscription_id и registration_generation вместе с topic/schema_version/publisher, payload и сведениями о времени. Новый запуск ядра получает новый instance_id; event_id не подменяется seq JSONL. Уведомление старого снимка может прийти после replace и должно оставаться различимым по generation. `[N]` (р.1.10)

4.5.22. Доставка v1 ДОЛЖНА быть live без автоматического replay после reconnect/reboot: не более одной логической отправки уведомления в сессии, без повторной доставки из-за отсутствия ack. Продолжение partial write не является повторной доставкой. Accepted означает принятие в ограниченную очередь, ack — получение адаптером, прикладной результат публикует клиент. SDK не повторяет publish с потерянным ответом автоматически; исход обозначается неопределённым. `[N]` (р.1.10)

4.5.23. Переполнение общей очереди ДОЛЖНО давать busy до accepted, без назначения event_id; переполнение исходящей очереди одного клиента отключает только его канал с диагностическим счётчиком. Остальные клиенты продолжают обслуживаться; доставка сообщения overflow по переполненному каналу не гарантируется. Pending ack ограничиваются по числу и монотонному сроку без replay. `[N]` (р.1.10)

4.5.24. Приёмник ДОЛЖЕН ограничивать frame по байтам до decode, глубину/элементы JSON и объём работы на проход; partial read/write, EAGAIN, EINTR и EOF обрабатываются раздельно. Слишком большой/некорректный UTF-8/слишком глубокий frame закрывает только его канал. Payload допускает только ограниченные JSON-объекты с конечными числами и корректным UTF-8; объект и массив различаются. Численные квоты и строгие правила кодека утверждаются по 9.2.11 до реализации. `[N]` (р.1.10)

### 4.6. Общий scheduler

4.6.1. Scheduler ДОЛЖЕН формировать публичные события в зарегистрированные клиентом моменты без открытого браузера и доступа в Интернет. Он не должен интерпретировать школьные расписания, мелодии или календарные исключения пакета. `[N]` (р.1.9)

4.6.2. Набор моментов клиента ДОЛЖЕН заменяться и отключаться по правилам регистрации п. 4.5.1, 4.5.6; неверная замена сохраняет прежний набор. Отключение одного владельца не должно затрагивать расписания других клиентов или общий cron системы. `[N]` (р.1.9)

4.6.3. Scheduler ДОЛЖЕН предоставлять клиенту наблюдаемые сведения о достоверности календарного времени и его коррекции для сверки регистраций. Поведение при скачке часов, пропущенном моменте и новом экземпляре ядра должно быть определено до реализации по вопросу 9.2.15; произвольный replay и exactly-once не предполагаются. `[N]` (р.1.9)

### 4.7. Объединение запросов чтения

4.7.1. Планировщик чтений ДОЛЖЕН объединять совместимые запланированные диапазоны одного транспорта и unit с одинаковой функцией FC01/02/03/04 в один запрос, если объединение сохраняет согласованные сроки актуальности/приоритет. Разные функции или устройства не смешиваются; специально ожидать будущий запрос ценой просрочки уже готового запрещается. `[N]` (р.1.10)

4.7.2. Объединённый диапазон ДОЛЖЕН состоять только из объявленных допустимых для совместного чтения адресов без побочных эффектов. По умолчанию объединяются перекрывающиеся/смежные диапазоны; промежуток допустим только при явно разрешённых адресах и настроенном пределе разрыва. Неизвестные и запрещённые участки карты не читаются для экономии запросов. `[N]` (р.1.10)

4.7.3. Размер объединённого запроса ДОЛЖЕН соблюдать минимум ограничений функции, транспорта и устройства, границы адресного пространства; превышающий диапазон разбивается. Ограничение ответа 256 байт по п. 6.1.3 сохраняется. Адреса/количества проверяются как целые, дубликаты чтений не требуют повторного запроса. `[N]` (р.1.10)

4.7.4. Один успешный ответ ДОЛЖЕН раскладываться по исходным потребителям с общей отметкой получения, без утраты смысла их valid/age. Ошибка группы не должна публиковать частичную выборку как успешную; прежние значения остаются явно невалидными по контракту потребителя. Запись и её подтверждающий readback не объединяются с обычным опросом через границу операции записи. `[N]` (р.1.10)

### 4.8. Многопортовый обмен раундами

Область этого подраздела — прямые порты ядра, включая Serial Monster.
Планирование внутри автономного шлюза определяется 4.9.2. (р.1.15)

4.8.1. Ядро ДОЛЖНО поддерживать несколько независимых последовательных транспортов с устойчивым логическим идентификатором порта, параметрами линии и привязкой устройств. Идентичность Modbus-устройства определяется парой (порт, unit), поэтому одинаковые unit на разных линиях не смешиваются в запросах, кэше, командах и событиях. Формат конфигурации и публичной адресации остаётся в 9.2.19. `[N]` (р.1.13)

4.8.2. Ядро ДОЛЖНО сохранять единственного владельца каждого физического порта и не более одной незавершённой RTU-транзакции на нём; буфер, очередь, состояние ошибки и дедлайны отдельны для каждого транспорта. Конфигурация, направляющая два логических транспорта на один физический порт, отклоняется до обмена. `[N]` (р.1.13)

4.8.3. В начале раунда планировщик ДОЛЖЕН зафиксировать конечный набор участников: не более одного готового запроса на каждый доступный порт после группировки по 4.7. Пустой или находящийся в reconnect/backoff порт не задерживает набор; поступившие позднее запросы относятся к последующим раундам. Выбор запросов обеспечивает отсутствие голодания при конечной нагрузке; конкретная дисциплина определяется в 9.2.20. `[N]` (р.1.13)

4.8.4. Параметры линии ДОЛЖНЫ применяться на свободном порту до передачи запроса; изменение скорости/формата во время транзакции запрещено. Начальный целевой профиль — настраиваемая скорость и 8N1; существующий профиль BluePill сохраняет ограничения 5.1.2. Передача учитывает межкадровую паузу RTU; численные правила и границы перенастройки определяются до реализации по 9.2.20. `[N]` (р.1.13)

4.8.5. Запуск запросов участников раунда ДОЛЖЕН допускать перекрытие времени их обмена: ожидание ответа одного порта не предшествует запуску остальных готовых портов. Точная синхронность начала передачи не требуется. Открытие, настройка и восстановление одного порта не должны создавать неограниченное ожидание для остальных. `[N]` (р.1.13)

4.8.6. Во время раунда ядро ДОЛЖНО принимать и проверять ответы по мере готовности каждого порта, обслуживая частичные чтения/записи и временную неготовность без активного бесконечного опроса. Достоверный результат становится доступен потребителям без ожидания самого медленного порта, с собственными valid и временем получения по 4.7.4. Раунд не является атомарным снимком всех устройств. `[N]` (р.1.13)

4.8.7. Следующий раунд ДОЛЖЕН начинаться только после терминального результата каждого участника текущего: успеха, окончательной ошибки либо исчерпания срока. Разрешённые попытки безопасного чтения относятся к той же операции текущего раунда и ограничены 6.2.4–6.2.6. После завершения своей операции быстрый порт не начинает новый запрос до общего барьера. Пустой набор не создаёт активного бесконечного цикла. `[N]` (р.1.13)

4.8.8. Ошибка или отключение участника ДОЛЖНЫ завершать либо ограниченно повторять только его операцию, не отменяя успешные ответы соседей. Монотонные сроки, запрет автоматического повтора записи, политика поздних ответов и граница write/readback по 4.7.4, 6.2.4–6.2.6 сохраняются отдельно для каждой линии. Повторное подключение не восстанавливает достоверность старого кэша без нового успешного обмена. `[N]` (р.1.13)

4.8.9. Цикл ожидания раунда ДОЛЖЕН оставлять ограниченный бюджет обслуживания событий/публичного IPC по 6.2.7, не создавая второго владельца serial. Получение готового ответа и проверка дедлайна не откладываются до завершения всех соседей; количественный бюджет остаётся в 9.2.20. `[N]` (р.1.13)

4.8.10. Реализация ДОЛЖНА сохранять существующую однопортовую конфигурацию, файловый контракт demo и поведение системных обработчиков. Расширение идентичности на несколько портов не должно создавать неоднозначные legacy-топики; правила многопортовой адресации согласуются до интеграции по 9.2.19. `[N]` (р.1.13)

4.8.11. Число портов, размеры очередей/буферов и объём работы за проход ДОЛЖНЫ иметь конечные проверяемые пределы с наблюдаемым отказом при превышении, а параметры попыток и общего срока — проверяться до обмена. Значения и суммарный бюджет RAM/FD выбираются по измерениям в 9.2.20, не выводятся из наличия трёх USB-интерфейсов. `[N]` (р.1.13)

4.8.12. Диагностика ДОЛЖНА различать длительность раунда, результат и возраст данных каждого устройства, состояние каждого транспорта и задержку обслуживания событий. Ошибка одной линии не должна маркировать все линии исправными либо скрывать успех соседней; численные гарантии задержки/ресурсов требуют отдельного согласования. `[N]` (р.1.13)

### 4.9. Логические устройства и автономные шлюзы

4.9.1. Ядро ДОЛЖНО адресовать устройство устойчивым логическим ID, отделённым от IP, имени tty и физической линии. Привязка задаёт точку подключения и внешний Unit ID; смена подключения не меняет логический ID. Синтаксис ID и миграция legacy cache/topics остаются в 9.2.19. `[N]` (р.1.15)

4.9.2. Система ДОЛЖНА различать прямой режим (ядро владеет RTU, включая Serial Monster) и автономный шлюз (плата владеет нижестоящими линиями). Раунды 4.8 относятся к прямому режиму; шлюз самостоятельно планирует линии без обязательного общего барьера. Пакеты работают через ядро и не открывают его физические транспорты. `[N]` (р.1.15)

4.9.3. Автономный шлюз ДОЛЖЕН поддерживать явную таблицу маршрутов: внешний Unit ID в области входной точки → выходная линия и внутренний Unit ID. Первый TCP-профиль имеет одну точку подключения с уникальными внешними Unit ID. Неизвестный маршрут отклоняется без рассылки по линиям; точные коды ошибок задаются до реализации в 9.2.22. `[N]` (р.1.15)

4.9.4. Шлюз ДОЛЖЕН сохранять разделение устройств с одинаковым внутренним Unit ID на разных линиях, преобразуя адреса запроса/ответа согласно маршруту и проверяя целостность выходного кадра. Одинаковый ID двух устройств на одной физической линии не поддерживается как различимая адресация. `[N]` (р.1.15)

4.9.5. Каждый порт шлюза ДОЛЖЕН иметь явную роль: disabled, modbus-client (инициирует запросы вниз), modbus-server (принимает запросы сверху), monitor (без передачи), bridge (передача по маршруту) либо debug. Несовместимые роли на одной линии запрещены; monitor/bridge являются отдельными будущими этапами, а не реализованными возможностями первого шлюза. `[N]` (р.1.15)

4.9.6. Выходная RS-485-линия ДОЛЖНА иметь одного владельца передачи и ограниченную очередь, общую для всех входных клиентов/маршрутов, с не более одной незавершённой RTU-транзакцией. Превышение лимита возвращает наблюдаемый отказ; сбой одной линии не отменяет успешные операции независимых линий. Политика поздних ответов 9.2.17 требуется и внутри шлюза. `[N]` (р.1.15)

4.9.7. Настройка маршрутов/ролей ДОЛЖНА проверять неоднозначность, недоступные порты, конфликты владения и петли до атомарной активации. Шлюз сохраняет действующую конфигурацию локально для работы без роутера; ошибочный импорт сохраняет прежнюю. Семантика переключения при активных транзакциях и интерфейс управления остаются в 9.2.22. `[N]` (р.1.15)

4.9.8. Шлюз ДОЛЖЕН предоставлять настраиваемые ограничения по маршруту: разрешённые Unit ID, функции, диапазоны регистров, разрешение записи и частота запросов, с диагностикой отклонений. Неоднозначная/неподдерживаемая настройка отвергается; точный формат, начальные политики и квоты согласуются до реализации по 9.2.22. Произвольное преобразование байтов не входит в первый профиль. `[N]` (р.1.15)

## 5. Требования к интерфейсам

### 5.1. Настройка и доступ

5.1.1. Поставляемая конфигурация ДОЛЖНА оставлять `profile=none`, пустой `device` и `system_events=0`, чтобы установка пакета сама не начинала обмен с платой. `[R]`

5.1.2. USB-транспорт BluePill ДОЛЖЕН принимать только путь `/dev/ttyACM<number>`, скорость `115200` и parity `N`, устанавливая raw 8N1 без flow control; несовместимые настройки отклоняются. Скорость по умолчанию UCI 9600 не является настройкой профиля BluePill. `[R]`

5.1.3. Сборка IPK ДОЛЖНА включать UCI-файл и штатный `button-led.lua` в список conffiles для обработки изменений администратором через opkg. `[R]`

5.1.4. CGI `modbus-core-status` ДОЛЖЕН предоставлять JSON-состояние ядра из стандартного runtime-каталога без Modbus-запросов. Часть demo перенесена в его ТЗ, требование 4.1.1. `[U]` (р.1.5)

### 5.2. Прошивка и сборка

5.2.1. Serial прошивки ДОЛЖЕН использоваться исключительно для Modbus-кадров, без отладочного текстового вывода. `[R]`

5.2.2. Скрипт сборки прошивки ДОЛЖЕН проверять STM32 Core 3.0.0 и modbus-esp8266 4.1.0 до компиляции в два потока. `[R]`

5.2.3. Скрипт ДОЛЖЕН отклонять образ с VMA/LMA векторов, отличными от `0x08002000`, или размером BIN вне 1..57344 байт; сборка не выполняет прошивку платы. `[R]`

### 5.3. Приём установочного файла

5.3.1. Будущий интерфейс загрузки ДОЛЖЕН до передачи файла запрашивать у
службы установки оценку по объявленному размеру и доступному временному
пространству; при недостатке места или неизвестном допустимом бюджете передача
не начинается. Эта предварительная проверка не заменяет проверку комплекта. `[N]` (р.1.8)

5.3.2. Приёмник ДОЛЖЕН ограничивать фактически принятые байты серверным
бюджетом, независимо от заявленного размера и интерфейса клиента; при превышении,
обрыве или утрате резерва загрузка прекращается и собственные временные файлы
освобождаются без изменения действующей установки. `[N]` (р.1.8)

### 5.4. Системное время

5.4.1. Системный интерфейс времени ДОЛЖЕН возвращать время роутера, часовой пояс и состояние достоверности источника; отсутствие достоверного источника не должно отображаться как подтверждённая синхронизация. `[N]` (р.1.9)

5.4.2. Системный механизм установки времени ДОЛЖЕН принимать только авторизованный проверенный однозначный момент времени, без исполнения переданных клиентом shell-команд; коррекция должна быть наблюдаема scheduler и клиентами. Его размещение и интеграция с NTP/RTC остаются в вопросе 9.2.16; прикладной аудио API не добавляется. `[N]` (р.1.9)

### 5.5. Modbus TCP и сетевое подключение

5.5.1. Ядро ДОЛЖНО предоставлять клиентский Modbus TCP-транспорт наряду с RTU: адрес/порт точки подключения и Unit ID задаются явно. RNDIS, Ethernet и Wi-Fi не меняют прикладной контракт TCP. Первый профиль ограничивается одной незавершённой операцией на TCP-соединение; собственный Modbus TCP-сервер роутера не входит в этот этап. `[N]` (р.1.15)

5.5.2. TCP-транспорт ДОЛЖЕН разбирать границы сообщений по протоколу, поддерживать фрагменты и несколько сообщений в одном чтении, проверять длину/идентификатор транзакции/Unit ID/функцию и принадлежность текущему соединению. Неограниченный буфер запрещён; старый или неожиданный ответ не завершает новую операцию. Точные пределы, управление ID и дедлайны согласуются по 9.2.23. `[N]` (р.1.15)

5.5.3. Общие операции чтения/записи ДОЛЖНЫ сохранять семантику результата, valid/age и неизвестного исхода записи при смене RTU/TCP. Разрыв TCP не означает, что отправленная запись не исполнена; автоматическое повторение такой записи запрещено. Профили восстановления RTU и TCP разделены; наличие TCP transaction ID не даёт exactly-once исполнения. `[N]` (р.1.15)

## 6. Нефункциональные требования

### 6.1. Ресурсы

6.1.1. Движок ДОЛЖЕН ограничивать число загруженных обработчиков восемью, источник одного файла 32768 байт, очередь восемью командами и исполнение загрузки/callback приблизительно 30000 Lua-инструкциями; бинарный Lua chunk отклоняется. Это не жёсткий лимит RAM или времени C-функций. `[R]`

6.1.2. При изначально не превышающих лимит сегментах и длине каждой JSONL-записи вместе с переводом строки не более лимита журнал ДОЛЖЕН ротироваться перед превышением лимита активного файла, сохраняя только активный и `.1`; лимит по умолчанию 65536 байт на файл, минимум 1024 байт. Случай новой одиночной записи сверх лимита рассмотрен в п. 9.2.2; legacy-сегменты и снижение лимита — в п. 6.1.5–6.1.7. `[U]` (р.1.3)

6.1.3. Serial-транспорт ДОЛЖЕН отклонять ответ расчётной длиной более 256 байт. `[R]`

6.1.4. `events.record` ДОЛЖЕН отвергать сериализованную JSONL-запись, включая завершающий LF, если её длина превышает лимит сегмента, возвращая `false, "event exceeds log size limit"` до ротации и записи; активный журнал, архив, seq и реестр топиков сохраняются без изменений. Равенство лимиту допускается. JSON не обрезается. Ошибка передаётся вызывающему коду: штатный `modbusd:publish` при ошибке persistence завершает выполнение, а не продолжает обработку неопубликованного события. `[N]` (р.1.1)

6.1.5. Изменение лимита через `set_max_log_bytes` НЕ ДОЛЖНО само по себе изменять файлы журнала, seq или реестра; очистка откладывается до допустимой записи, вызывающей ротацию. Отказ новой oversized-записи сохраняет файлы по п. 6.1.4 даже при старых oversized-сегментах. `[U]` (р.1.3)

6.1.6. Если активный сегмент превышает текущий лимит, при следующей допустимой записи писатель ДОЛЖЕН удалить старый архив и активный сегмент целиком, затем записать новое событие с очередным seq. Потеря старой истории согласована; строки не перепаковываются. Требование предполагает успешные операции ФС; ошибки удаления/записи остаются в вопросе 9.2.8. `[U]` (р.1.3)

6.1.7. Oversized-архив ДОЛЖЕН сохраняться побайтно, пока допустимые записи помещаются в активный сегмент; при штатной ротации активного сегмента архив заменяется этим сегментом. Немедленная граница размера архива после уменьшения лимита не гарантируется. `[U]` (р.1.3)

### 6.2. Время

6.2.1. Ядро ДОЛЖНО ограничивать `system_poll_ms` диапазоном 100..1000 мс (по умолчанию 200 мс) и `request_timeout_ms` диапазоном 100..2000 мс (по умолчанию 500 мс). Системный интервал является паузой между итерациями, а не предельным временем реакции. `[R]`

6.2.2. Выполнение очереди НЕ ДОЛЖНО отправлять команду возрастом более 1 с; просрочка обрабатывается как неуспех команды. `[R]`

6.2.3. Тайм-аут обмена, возраст снимков и статистика hz ДОЛЖНЫ опираться на монотонное время, а не на календарное `ts`. Обработка `stty` и открытия устройства не входит в дедлайн обмена. `[R]`

6.2.4. Транспорт ДОЛЖЕН сохранять настраиваемый таймаут одной попытки request_timeout_ms по п. 6.2.1 и предоставлять отдельное настраиваемое неотрицательное целое число дополнительных повторов чтения: 0 означает одну попытку, R — максимум 1+R. Общее время операции, пауза перед повтором и допустимый максимум R ограничиваются проверяемой конфигурацией; конкретные значения/имена новых настроек остаются в 9.2.17. `[N]` (р.1.10)

6.2.5. Автоматические повторы ДОЛЖНЫ применяться только к разрешённым безопасным чтениям и согласованным временным ошибкам. Неверная конфигурация/адрес, несовместимая карта и постоянный Modbus exception не должны вызывать цикл повторов. Команды записи, включая FC05 с потерянным подтверждением, автоматически не повторяются: п. 4.2.7 остаётся действующим. `[N]` (р.1.10)

6.2.6. Операция чтения ДОЛЖНА завершаться ошибкой при исчерпании попыток или общего монотонного срока, в зависимости от того, что наступит раньше. Следующая попытка не начинается после истечения срока актуальности запроса; новый запрос не должен принимать поздний ответ прежней попытки как достоверный без предусмотренной политики синхронизации RTU. Эта политика и классы повторяемых ошибок определяются до реализации по 9.2.17. `[N]` (р.1.10)

6.2.7. Ожидание ответа и паузы повторов ДОЛЖНЫ позволять ограниченное обслуживание публичного IPC независимо от профиля платы. Один транспорт выполняет не более одной незавершённой RTU-транзакции; обслуживание IPC не открывает второй serial и не запускает параллельный опрос. Увеличение числа повторов не должно превращаться в неограниченный монолитный цикл, блокирующий остальных клиентов; численные задержки требуют измерений. `[N]` (р.1.10)

### 6.4. Автономная установка и целостность системы

Служба принятия решения об установке относится к системе ядра; её размещение
отдельно от modbusd и формат комплекта ещё проектируются. Это целевые требования,
не описание возможностей существующего opkg или текущих скриптов. (р.1.8)

6.4.1. Комплект расширения ДОЛЖЕН содержать проверяемый manifest с версиями
расширения и API, архитектурой/ABI, транзитивными зависимостями, перечнем файлов
и контрольными суммами, местами постоянного хранения, ресурсами временных стадий
потребностью RAM при старте/работе и порядком запуска после загрузки системы. Неопределённые обязательные данные
означают отказ допуска до изменения установленной системы. `[N]` (р.1.8)

6.4.2. Ответственность за дополнительные зависимости ДОЛЖЕН нести пакет:
возможно распространяемые зависимости включаются в автономный комплект как
частные файлы или совместимые IPK. Каждая оставшаяся зависимость должна быть
явно объявлена и подтверждена как установленная в постоянном хранилище;
отсутствие сети не может быть скрытым условием успешной установки/запуска. `[N]` (р.1.8)

6.4.3. Служба установки ДОЛЖНА до запуска установочных скриптов и изменения системы
проверить целостность содержимого,
совместимость полного набора зависимостей и точный ABI модулей ядра; повреждённый,
неполный или несовместимый комплект отклоняется без force-обходов. Проверка
контрольной суммы не доказывает доверенность автора; механизм доверия открыт. `[N]` (р.1.8)

6.4.4. Прогноз ДОЛЖЕН отдельно учитывать пиковую потребность каждой файловой
системы и RAM: загрузку, распаковку, новые файлы/метаданные, временные копии,
сохранение действующей версии/настроек для отката, RAM запуска/работы расширения
и рабочий запас системы.
Размер сжатого IPK или Installed-Size сам по себе недостаточен; места на разных
разделах не суммируются как взаимозаменяемые, пути одного раздела учитываются вместе. `[N]` (р.1.8)

6.4.5. Служба ДОЛЖНА отказывать, если для любой стадии свободный бюджет меньше
прогнозируемого пика плюс настроенный запас, либо оценка не может быть достоверно
получена. Размеры запасов, учёт сжатой ФС, RAM и inode задаются проверяемой политикой,
а не вымышленным универсальным числом. `[N]` (р.1.8)

6.4.6. Служба ДОЛЖНА повторно проверять доступные ресурсы перед изменениями и
защищать бюджет от конкурирующих управляемых установок/загрузок; потеря бюджета
или ошибка записи прекращает операцию с диагностикой. Предварительная оценка
не разрешает игнорировать последующий ENOSPC. `[N]` (р.1.8)

6.4.7. Активация ДОЛЖНА происходить только после проверки полностью размещённого
комплекта; при отказе сохраняются действующее ядро, конфигурация и доступ к
управлению. До разрушительного шага должен быть подготовлен локальный путь
восстановления без сети; незавершённая установка после сбоя питания не считается

6.4.8. Допуск ДОЛЖЕН отклонять расширение, которому для заявленного запуска
после reboot нужны невосстановимые файлы из /tmp, кэша загрузок или недоступной
сети. Исполняемые файлы, библиотеки, необходимые медиа и настройки размещаются
постоянно; временные данные создаются при запуске с учётом бюджета RAM. `[N]` (р.1.8)

6.4.9. Установка/откат/удаление ДОЛЖНЫ учитывать владение файлами и зависимости
других пакетов; приватная библиотека не подменяет системную молча, общая зависимость
не удаляется, пока нужна другим потребителям. Конфликт, требующий замены системного
компонента, отклоняется до отдельного согласованного плана обновления. `[N]` (р.1.8)

6.4.10. Приёмка автономной поставки ДОЛЖНА включать запуск в целевом окружении
без сети и прежнего содержимого /tmp после перезагрузки, проверку функций пакета

произвольных ошибок пакета. Аппаратная перезагрузка согласуется отдельно. `[N]` (р.1.8)

### 6.6. Хранение и импорт пользовательских настроек

6.6.1. Общий механизм ДОЛЖЕН предоставлять пакетам сохранение, загрузку, экспорт и подготовку импорта конфигурации; схема пользовательских настроек, семантическая валидация, миграции и активация принадлежат пакету. Общий код не интерпретирует расписания, аудиодействия или карту конкретного устройства. Семантика API определена в 6.6.14; точные типы и ошибки остаются в 9.2.26. `[N]` (р.1.17)

6.6.2. Пользовательская конфигурация ДОЛЖНА храниться постоянно отдельно от заводских ресурсов и временного состояния: целевой путь /etc/<package-id>/settings.json, factory resources — /usr/share/<package-id>/, runtime — /tmp/<package-id>/. Пользовательские медиа размещаются в явно выбранном постоянном каталоге с проверкой ФС и места; отсутствие носителя не должно приводить к скрытой записи в другой каталог. Частая телеметрия/очереди не сохраняются как конфигурация во Flash. `[N]` (р.1.17)

6.6.3. settings.json ДОЛЖЕН содержать только пользовательские значения без общей оболочки payload, package_id, format_version, schema_version или config_revision. Пакет определяется доверенным контекстом API/каталогом; правила значений описываются отдельно в settings.schema.json. Служебные метаданные и происхождение импорта отделены по 6.6.13; отсутствие версий в пользовательском файле не отменяет проверку совместимости. `[U]` (р.1.17)

6.6.4. Импорт ДОЛЖЕН проходить ограниченный разбор без исполнения загруженного кода, проверку контекста пакета, метаданных экспорта (если импортируется комплект) и лимитов, пакетную валидацию/миграцию и проверку ссылок до изменения действующих данных. Путь назначения выбирает установленный пакет, не загруженный JSON. Лимиты размера/глубины/количества элементов и политика неоднозначного JSON определяются до реализации. `[N]` (р.1.17)

6.6.5. Подготовка импорта ДОЛЖНА выдавать проверяемый результат и перечень изменений отдельно от явной активации. Неуспешная подготовка сохраняет действующие данные и поведение; подготовка не запускает звук, регистрацию новых расписаний, команды оборудованию или изменение сети. Активация выполняется по контракту пакета и не даёт полномочий менять чужую конфигурацию. `[N]` (р.1.16)

6.6.6. Сохранение/активация ДОЛЖНЫ исключать применение частичного состояния: временные файлы записываются на нужной ФС, ошибки записи/закрытия учитываются, доступен проверенный путь восстановления. При сбое не допускается молчаливый переход к заводским настройкам или смесь старых/новых файлов. Протокол долговечности, фиксации ревизии, конкуренции и восстановления после питания определяется до реализации по 9.2.26; rename одного файла не считается доказательством устойчивости комплекта. `[N]` (р.1.16)

6.6.7. Шаблон партии ДОЛЖЕН содержать только переносимые настройки, исключая секреты, сетевые адреса конкретного устройства и идентификаторы оборудования. Локальные привязки к логическим устройствам проверяются/задаются на получателе; неподходящие привязки не активируются автоматически. 6.6.8. Backup конкретного устройства ДОЛЖЕН отличаться от шаблона партии и сохранять согласованный набор конфигурации/версий и manifest пользовательских файлов. Включение секретов, защита экспорта и перенос уникальных привязок определяются явной политикой до реализации; backup не считается автоматически допустимым шаблоном. Восстановление проверяет полноту/совместимость/место до активации. `[N]` (р.1.16)

6.6.9. Медиа ДОЛЖНЫ храниться отдельно от обычного JSON конфигурации; пакет проверяет ссылки на media ID/revision. Перенос файлов выполняется отдельным ограниченным комплектом с проверкой целостности и допустимых путей, без выхода за область пакета. Необходимая отсутствующая мелодия/данные делают импорт непригодным к активации. `[N]` (р.1.16)

6.6.10. Миграции ДОЛЖНЫ исполняться установленным кодом пакета на подготовленной копии с повторной валидацией результата, не кодом из импорта. Обновление IPK не должно молча перезаписывать пользовательские настройки; несовместимый downgrade/restore отклоняется до активации. conffiles не заменяет согласованный backup и восстановление. `[N]` (р.1.16)

6.6.11. Расширение ДОЛЖНО иметь package.json с полями name, displayName, publisher, version, engines, main и contributes по применимости. Идентичность расширения — publisher.name, соответствие имени IPK задаётся явно; version обозначает версию расширения, engines — совместимость с API ядра. Заимствуется именование, а не выполнение Node.js/npm/VSIX. Зависимости/полномочия требуют собственного проверяемого профиля OpenWrt до реализации. `[N]` (р.1.17)

6.6.12. Расширение ДОЛЖНО отделять settings.schema.json от пользовательского settings.json, прикладные документы (планы/расписания) — от простых настроек, медиа — от JSON. Пакет владеет схемой/миграциями; используемое подмножество схем и defaults определяется в 9.2.26. Factory schema и ресурсы не перезаписываются импортом пользователя. `[N]` (р.1.17)

6.6.13. Система ДОЛЖНА хранить отметку последней успешно применённой версии и данные восстановления вне пользовательских настроек; manifest экспорта содержит идентичность расширения и версию создателя. Пакет явно определяет поддерживаемые исходные версии/миграции и проверяет результат, не считая совпадение/порядок версий достаточным доказательством совместимости. Независимая версия формата прикладных данных вводится только при обоснованной необходимости. `[N]` (р.1.17)

6.6.14. API ДОЛЖЕН работать в контексте расширения: load возвращает настройки и непрозрачный токен состояния; prepareImport — проверенный кандидат и изменения без активации; save(candidate, token) сохраняет либо возвращает конфликт, если исходное состояние изменилось; export(kind) различает template и backup. Проверка токена и фиксация защищаются от конкурентной перезаписи; пакетный контракт активации и правила восстановления 6.6.5/6.6.6 сохраняются. Токен не является редактируемым полем settings.json. `[N]` (р.1.17)

### 7.3. Порядок приёмки

Сначала выполняются инспекция и локальные тесты, затем согласованные аппаратные проверки. `make all` не запускает сборку Arduino или живые тесты. Изолированный `scripts/test-handlers-router.sh` также требует разрешения использовать роутер, но не открывает рабочий tty. Lifecycle-тесты и отключение USB требуют отдельного согласования и восстановления настроек. Непокрытые сценарии не получают PASS на основании сходного теста.

## 9. Допущения и открытые вопросы

### 9.1. Допущения

9.1.1. Администратор и Lua-файлы доверенные; к управлению роутером нет доступа недоверенных пользователей. Система не обеспечивает криптографическую аутентификацию USB Modbus.

9.1.2. Прототип испытывается без опасных исполнительных нагрузок. Нулевые стартовые уставки не являются согласованной политикой fail-safe; физическое состояние выводов до `setup()` не нормировано.

9.1.3. Файлы runtime находятся на исправном доступном для записи tmpfs. Атомарный rename отдельных файлов не даёт транзакционности между кэшем, журналом, seq и реестром топиков.

## Приложение H. Изолированный реестр (информативно)

`event_registry.lua` — внутренний чистый Lua-модуль, не сервер и не новый
вариант старого JSONL events.lua. Он входит в IPK, но modbusd его не вызывает.
Конструктор требует явные конечные квоты sessions/definitions/subscriptions;
это ограничения количества объектов, не измеренный RAM-бюджет роутера.

Внутренний API: open(owner), status(handle), replace(handle, expected_generation,
revision, spec), unregister(handle, expected_generation), close(handle),
can_publish(handle, topic, schema_version), snapshot(topic).
Дескриптор сессии — непрозрачная Lua-таблица, проверяемая по идентичности;
session_id уникален в пределах экземпляра реестра. Поколение начинается с 0,
растёт при замене/снятии; повтор снятия уже пустого набора с прежним или текущим
generation возвращает текущее состояние без увеличения. Будущий generation
отклоняется; после установки новой revision старый unregister снова отвергается.
Закрытый дескриптор не действует на новое подключение того же owner.

Внутренний профиль данных: owner/revision/subscription ID и сегменты topic —
ASCII `[a-zA-Z0-9_-]`, длина 1–64; topic — абсолютный путь до 256 байт без
пустых сегментов; schema_version — положительное целое. Счётчики/числа не выше
2^53−1, исчерпание отклоняется вместо wrap. Списки плотные, без неизвестных
полей и metatable. Эти ограничения реализации не утверждают окончательный
wire codec/payload и не закрывают вопрос 9.2.11.

Списки нормализуются по topic/id; перестановка элементов не меняет revision.
Входные таблицы, status и каждый snapshot не содержат общих изменяемых ссылок
на внутреннее состояние. Старый snapshot переживает replace/close; будущая
доставка должна учитывать закрытый канал, не перенаправляя его новому session_id.
Снимок упорядочен по owner/id, но это не обещание порядка исполнения клиентов.
Публикация, event ID, payload, byte queues, ack, codec, IPC, scheduler и audio
не реализованы данным модулем; автоматические повторы RTU также не добавлялись.

## Приложение J. Многопортовые раунды (информативно)

Ревизия 1.13 содержит только требования. modbusd/serial_rtu, прошивка, UCI и
контракты пакетов не изменены; TC-74–83 ещё не реализованы и не пройдены.
Модель: сбор готовых запросов и группировка → настройка свободных линий →
запуск по одному запросу на порт → приём/разбор по готовности → завершение
всех участников или их сроков → следующий раунд. Барьер не задерживает публикацию
уже готового результата. Успех отдельных ответов не даёт атомарного общего sample.

раунда около 500 мс вместо последовательных 530 мс; реальные накладные расходы,

запросом. Независимый запуск следующего запроса без барьера не принят как режим.
Наличие нескольких потоков ОС не требуется контрактом: допустим один цикл poll
с отдельным состоянием портов. Владелец Modbus остаётся на роутере; Serial Monster
передаёт байты, внешние устройства формируют ответы. Debug UART не становится
Modbus-портом автоматически. USB CDC не заменяет RS-485-трансиверы.

Отдельные последовательные ветки после push/CI/land владельца:
1. Эта редакция требований и критериев.
2. Программный стенд/модель с управляемыми часами и ошибками; разрешение нужных
   деталей 9.2.17/19/20 до соответствующей реализации, без подключения к modbusd.
3. Реализация состояний транспортов и раундов, затем интеграция конфигурации,
   диагностики и совместимости; объём каждой ветки согласуется отдельно.
4. После отдельного разрешения — обновление ядра и однопортовая регрессия
   на действующей BluePill; позднее — многопортовый стенд с внешними ответчиками.

Обнаружение интерфейсов шлюза не доказывает передачу по UART/RS-485. Результаты
прошлых опытов здесь не объявляются повторной проверкой. Замена плат, установка,
запись выходов и длительные прогоны требуют отдельного согласования.

## Приложение K. Программная модель раундов (информативно)

Модель запускается `python3 scripts/test_rounds_model.py` (Python 3.8+).
`Port` содержит синтетическую физическую идентичность и момент доступности;
`Request` — ID, логический порт, unit, момент готовности, таймаут, задержку
и абстрактный исход ok/error/disconnect. None вместо задержки означает молчание.
Входные операции считаются уже сгруппированными. Выход: виртуальная длительность,
трасса enqueue/start/result/barrier/service, результаты и valid/last_success
по (порт, unit). Входы не изменяются; повторный запуск детерминирован.

Допущения модели, не defaults будущего транспорта: 1–3 порта, FIFO очереди,
мгновенный старт и нулевые расходы настройки/передачи, timeout при равенстве
задержки дедлайну. Quantum задаёт моменты условного обслуживания событий.
Queue limit ограничивает ожидающие операции отдельно от активной; max_requests
и max_steps ограничивают размер опыта/работу, превышение наблюдаемо. Это не
согласованные производственные квоты или гарантия RAM. В sequential baseline
за раз активна одна операция, порты выбираются в порядке входного списка.

Модель перескакивает между событиями виртуального времени, не ждёт реальных часов.
Пустой опыт завершает работу без итераций. Пока есть будущая работа, сервисные
моменты моделируются периодически; при исчерпании бюджета шагов опыт явно падает.
Результат публикуется до общего барьера; новые запросы не расширяют текущий раунд.
Отказ обновления снимает valid, сохраняя прежний last_success. Disconnect —
абстрактный окончательный исход операции, а не реализация reconnect/backoff;
начальная недоступность задаётся available_at. Механизм повторов отсутствует.

## Приложение N. Формат расширения и настроек (информативно)

Ревизия 1.17 заменяет требование общей JSON-оболочки из 1.16; история не удалена.
Ревизия конфигурации, служебная схема и поколения не становятся полями пользователя.
Хеш состояния — возможный token, не выбранная реализация. Точный протокол атомарной
фиксации и восстановления ещё открыт; обсуждавшееся дерево generations не утверждено.
Предложенные ранее 256 КиБ также не стали согласованной квотой.

Расширения используют собственный профиль OpenWrt: заимствование имён VS Code
не означает совместимость пакетов, выполнение npm scripts или доверие manifest.
Допуск установки по 6.4/6.5 остаётся обязательным; минимальный формат поставки,
политика hooks и полномочий требуют отдельной конкретизации. Текущий IPK и код
не изменены; TC-101–103 плановые. Указание engines не назначает ещё не выпущенную
версию API ядра. Версии ТЗ не используются как engines.
