## 1. Введение

### 1.1. Назначение

1.1.1. Документ описывает ядро и его USB-протокол стенда. Требования к устанавливаемым пакетам ведутся отдельно. Статус остаётся черновиком. (р.1.5)

### 1.2. Область применения

1.2.1. Область: core 0.4.0 и контракт карты прошивки v2. Demo и schoolbell имеют собственные ТЗ. Общие события, подписки и scheduler относятся к развитию ядра; прикладные действия принадлежат клиентам; её API ещё не реализован; принятые правила жизненного цикла заданы в разделе 4.5, сигнатуры API остаются открытыми. RTC, RS-485 и общие выходные политики требуют отдельного согласования. (р.1.8)

### 1.3. Метод формирования

1.3.1. Поведение восстановлено из файлов базового коммита и штатных тестов. Исторические аппаратные результаты в CHANGELOG не являются повторной проверкой в этой ревизии. Старые ненормативные проектные заметки не имеют приоритета над согласованными требованиями.

1.3.2. Целевой реализацией этой редакции считается существующий стенд, без новых команд DO/PWM. Расхождение документа с кодом рассматривается как дефект одного из них и разрешается пересмотром ревизии; известные ограничения перечислены в приложении C. Утверждение документа выполняет владелец.

### 1.4. Термины

| Термин | Определение |
| :--- | :--- |
| Топик | Именованный поток публикаций; не отдельный процесс и не ROS middleware |
| Sample | Полная общая выборка DI/AI/DO/AO одного устройства |
| Baseline | Исходный системный снимок без воспроизведения накопленных нажатий |
| Readback | Чтение coil после записи; подтверждает программную уставку, не физическое свечение |
| Актуальность | Признак последнего успешного опроса и возраст данных, не гарантия работоспособности оборудования |
| AO | В этом прототипе уставка PWM; не аналоговый ЦАП |
| Доверенный обработчик | Lua-код администратора; ограничения движка не являются защитой от враждебного кода |

### 1.5. Источники

1.5.1. Структура документа основана на [embedded-tech-spec](https://github.com/ViacheslavMezentsev/demo-stm32-skills/tree/main/embedded-tech-spec). Контракт USB RTU описан по реализации `rtu.lua`, `serial_rtu.lua` и скетчу; полная сертификация соответствия стандарту Modbus не заявляется.

### 1.6. Соглашения документа

1.6.1. ДОЛЖЕН/ДОЛЖНА/ДОЛЖНО/ДОЛЖНЫ обозначают обязательное требование после утверждения; СЛЕДУЕТ означает рекомендацию; МОЖЕТ означает допустимую возможность.

1.6.2. Номера требований `X.Y.Z` и тестов `TC-NN` постоянны. Новые пункты получают свободные номера; исключённые остаются с пометкой «исключено». Номера вопросов находятся в подразделе 9.2.

1.6.3. Происхождение: `[R]` восстановлено по коду; `[N]` новое требование; `[U]` уточнение существующего поведения. Маркер `[R]` сам по себе не означает аппаратный PASS.

1.6.4. Разделы 1–2 и приложения информативные; разделы 3–6 — нормативные. Раздел 7 задаёт проверки, раздел 8 связывает их с требованиями, раздел 9 фиксирует допущения.

1.6.5. Ссылки из кода оформляются по приложению B. В текущем этапе код не размечается массово: точками входа служит матрица.

1.6.6. Ревизии имеют формат `M.m`: минорная растёт при согласовательном цикле, мажорная при утверждении либо смене архитектуры. Статусы: «черновик для согласования», «на согласовании», «утверждено».

## 2. Общее описание

### 2.1. Контекст

2.1.1. `modbusd` работает под procd, получает настройки UCI, пишет кэш и журнал в RAM. CLI, CGI и demo читают эти данные. При профиле BluePill ядро обращается к USB CDC платы как Modbus master.

### 2.2. Функции

2.2.1. Профиль `none` обеспечивает ядро и demo без платы. Профиль `bluepill` добавляет общие выборки. Флаг `system_events` добавляет счётчик кнопки, системный LED и доверенные Lua-обработчики.

### 2.3. Роли

| Роль | Взаимодействие |
| :--- | :--- |
| Администратор | UCI, доверенные Lua-файлы, установка IPK, согласование аппаратных испытаний |
| Пользователь стенда | PA0, наблюдение PB2 и CLI |
| Ядро | Единственный штатный владелец USB RTU |
| Demo/CLI/CGI | Потребители файлов кэша и событий, без serial-доступа |
| Разработчик | Локальная сборка, тесты, документация; push/land выполняет владелец |

### 2.4. Границы

2.4.1. Система не гарантирует доставку каждого события, exactly-once при потере питания, реальное время, безопасное отключение выходов при обрыве или изоляцию недоверенных сценариев. USB CDC не заменяет электрический RS-485.

### 2.5. Платформа

2.5.1. Прошивка собирается для F103C8 с 64 КиБ Flash, из которых 8 КиБ заняты Maple bootloader; бюджет приложения 56 КиБ. Сборка использует FQBN `STMicroelectronics:stm32:GenF1:pnum=BLUEPILL_F103C8,usb=CDCgen,opt=oslto,upload_method=dfu2Method`. Версия Arduino CLI не закреплена скриптом; фактическую версию записывают в локальном протоколе сборки.

2.5.2. Lua использует динамическую память. Верхние границы общей RAM, CPU и задержки реакции пока не согласованы. Пакеты ядра скриптовые, сборка OpenWrt/SDK не требуется.

## 3. Модель данных и протокол

### 3.1. Адресация и карта v2 (нормативная)

3.1.1. Кэш ДОЛЖЕН представлять значения как `devices[unit][kind][address]`, где `unit` и нулевой `address` являются строковыми ключами, а `kind` для BluePill равен `di`, `ai`, `do` или `ao`. `[R]`

3.1.2. Общий опрос ДОЛЖЕН читать блоки от адреса 0: FC02/2 DI, FC04/5 AI, FC01/2 DO, FC03/1 AO. `[R]`

3.1.3. Прошивка ДОЛЖНА предоставлять регистры по таблице ниже. Значения 32 бит передаются старшим словом первым. `[R]`

| Область / адрес | Содержание | Тип / единица |
| :--- | :--- | :--- |
| DI 0, 1 | PB12, PB13; логическая единица при LOW, INPUT_PULLUP | bool |
| Coil 0, 1 | PC13 active-low, PB0 active-high | bool |
| IR 0, 1 | PA2, PA1 | АЦП, 0..4095 |
| IR 2, 3 | Соответствующий raw × 3300 / 4095 с целочисленным усечением | мВ, номинальная оценка |
| IR 4 | Младшие 16 бит `millis()/1000` | с, не постоянные часы |
| HR 0 | Уставка PWM PA8 | uint16; физическое применение ограничено 4095 |
| Coil 256 | PB2, системный LED active-high | bool |
| DI 256 / IR 259 | Подавленное по дребезгу состояние PA0 | bool / 0 либо 1 |
| IR 256, 257, 258 | Сигнатура `0x5741`, версия `2`, возможности `3` | uint16 |
| IR 260, 261 | Счётчик нажатий, high/low | uint32, по модулю 2^32 |
| IR 262, 263 | `millis()`, high/low | uint32, мс, по модулю 2^32 |

3.1.4. Системный опрос ДОЛЖЕН отклонять карту, если любое из значений сигнатуры, версии или возможностей отличается от `0x5741`, `2`, `3` соответственно. `[R]`

### 3.2. Кадры USB RTU (нормативные)

3.2.1. Формирование запросов чтения ДОЛЖНО отклонять unit вне 1..247, функцию вне 1..4, адрес вне 0..65535, количество вне 1..2000 бит или 1..125 слов и выход блока за 65536 адресов. Параметры должны быть целыми числами. Это границы кодировщика; транспорт ограничен отдельно в п. 6.1.3. `[R]`

3.2.2. Кодировщик ДОЛЖЕН добавлять CRC с начальным значением `0xFFFF`, отражённым полиномом `0xA001` и младшим байтом результата первым; поля адреса и количества передаются старшим байтом первым. Контрольный запрос unit=1, FC02, start=0, count=2: `01 02 00 00 00 02 F9 CB`. `[R]`

3.2.3. Декодер чтения ДОЛЖЕН отвергать ответ с неверными CRC, unit, функцией, числом байтов либо полной длиной и возвращать Modbus exception как ошибку, а не выборку. `[R]`

3.2.4. FC05 ДОЛЖНА кодировать boolean в `FF 00`/`00 00` и признавать успешным только точное эхо запроса; исключение, короткий, лишний или повреждённый ответ является ошибкой. `[R]`

## 4. Функциональные требования: жизненный цикл и API

### 4.1. Запуск и общий опрос

4.1.1. Ядро ДОЛЖНО завершаться без опроса, если UCI `enabled` отличается от строки `1`. `[R]`

4.1.2. При `profile=none` ядро ДОЛЖНО публиковать heartbeat без открытия serial-порта. `[R]`

4.1.3. BluePill ДОЛЖЕН публиковать `device_sample` и обновлять общие регистры кэша только после успешного чтения всех блоков из п. 3.1.2. Это согласованная программная выборка, не одновременное измерение каналов. `[R]`

4.1.4. При неуспешном общем опросе ядро ДОЛЖНО отмечать `meta.data_valid=false` и `transport_status=offline`, сохраняя предыдущие значения; при успешном - `true`, `online` и время `last_success`. Метаданные характеризуют общий опрос, а не мгновенный статус каждого системного запроса. `[R]`

4.1.5. При включённых системных событиях ядро ДОЛЖНО выполнять общий и системный опрос последовательно через одно открытое соединение; при ошибке закрывать его и откладывать новую попытку не менее чем на 1 с. `[R]`

### 4.2. Системная кнопка и LED

4.2.1. PA0 ДОЛЖЕН использоваться как системная кнопка active-high с INPUT_PULLDOWN и подавлением дребезга 30 мс; удержание не увеличивает счётчик повторно, исходное удержание при старте не считается новым нажатием. `[R]`

4.2.2. Скетч НЕ ДОЛЖЕН локально переключать PB2 по PA0: состояние PB2 определяется системной coil 256, исходно false. `[R]`

4.2.3. Первый системный снимок после запуска или восстановления соединения ДОЛЖЕН быть baseline с нулевым `presses_delta`, без повторения накопленных нажатий. `[R]`

4.2.4. Ядро ДОЛЖНО вычислять приращения счётчика и uptime по модулю 2^32; при `dt > 60000 мс` либо `delta > floor(dt/60 мс)+1` принимать снимок как новый baseline с delta=0. Это эвристика сброса, не идентификатор загрузки MCU. `[R]`

4.2.5. Штатный обработчик ДОЛЖЕН запрашивать инверсию последнего актуального LED только при valid, не-baseline событии кнопки с нечётным `presses_delta`; чётное приращение, отпускание и удержание не создают команду. `[R]`

4.2.6. Ядро ДОЛЖНО признавать команду LED успешной только после успешной FC05 и совпадения последующего FC01 readback с целевым значением. `[R]`

4.2.7. При ошибке выполнения команды, включая неоднозначную потерю ответа, ядро ДОЛЖНО публиковать неуспех, инвалидировать системные данные и отбросить очередь без автоматического повторения команд. `[R]`

4.5.16. Публичный интерфейс ДОЛЖЕН иметь конечные квоты клиентов, регистраций, сообщений и байтов буферов; отказ или переполнение должны быть наблюдаемы и не останавливать обслуживание исправных клиентов и Modbus. Значения и политика доставки при переполнении определяются до реализации по вопросу 9.2.11. `[N]` (р.1.9)

4.5.17. Первый публичный API ДОЛЖЕН использовать локальный AF_UNIX/SOCK_STREAM, UTF-8 JSON-объекты с LF и согласование api=1 через hello. Endpoint events-v1.sock находится в защищённом runtime_dir с правами socket 0600; неподдерживаемая версия отклоняется до регистрации. Профиль предназначен для доверенных локальных пакетов; owner не является изоляцией root-процессов. `[N]` (р.1.10)

4.5.18. Ядро ДОЛЖНО разрешать один управляющий канал на owner, отклоняя второй как owner_busy. Регистрации принадлежат сессии: при разрыве канал и его ожидающие доставки очищаются, регистрации снимаются по границе п. 4.5.6. Клиент явно восстанавливает их после сверки instance/generation; принятые им действия ядро не отменяет. `[N]` (р.1.10)

4.5.19. API ДОЛЖЕН предоставлять hello, status, replace, unregister, publish и ack. Replace проверяет полный набор definitions/subscriptions и expected_generation; повтор той же revision с тем же содержимым возвращает прежнее generation, иное содержимое той же revision отклоняется. Unregister со старым generation не должен удалять новый набор. Операции/поля описаны в памятке EVENT_API.md; дополнительные детали кодека остаются в 9.2.11. `[N]` (р.1.10)

4.5.20. Ядро ДОЛЖНО разрешать публикацию только объявленных типов собственного /packages/<owner>/ пространства; /core и /devices зарезервированы. Подписки v1 используют точное совпадение topic; разные subscription_id одного клиента получают отдельные уведомления одного события, в том числе после регистрации до появления типа. `[N]` (р.1.10)

4.5.21. Каждое уведомление ДОЛЖНО содержать instance_id, event_id, subscription_id и registration_generation вместе с topic/schema_version/publisher, payload и сведениями о времени. Новый запуск ядра получает новый instance_id; event_id не подменяется seq JSONL. Уведомление старого снимка может прийти после replace и должно оставаться различимым по generation. `[N]` (р.1.10)

4.5.22. Доставка v1 ДОЛЖНА быть live без автоматического replay после reconnect/reboot: не более одной логической отправки уведомления в сессии, без повторной доставки из-за отсутствия ack. Продолжение partial write не является повторной доставкой. Accepted означает принятие в ограниченную очередь, ack — получение адаптером, прикладной результат публикует клиент. SDK не повторяет publish с потерянным ответом автоматически; исход обозначается неопределённым. `[N]` (р.1.10)

4.5.23. Переполнение общей очереди ДОЛЖНО давать busy до accepted, без назначения event_id; переполнение исходящей очереди одного клиента отключает только его канал с диагностическим счётчиком. Остальные клиенты продолжают обслуживаться; доставка сообщения overflow по переполненному каналу не гарантируется. Pending ack ограничиваются по числу и монотонному сроку без replay. `[N]` (р.1.10)

4.5.24. Приёмник ДОЛЖЕН ограничивать frame по байтам до decode, глубину/элементы JSON и объём работы на проход; partial read/write, EAGAIN, EINTR и EOF обрабатываются раздельно. Слишком большой/некорректный UTF-8/слишком глубокий frame закрывает только его канал. Payload допускает только ограниченные JSON-объекты с конечными числами и корректным UTF-8; объект и массив различаются. Численные квоты и строгие правила кодека утверждаются по 9.2.11 до реализации. `[N]` (р.1.10)

### 4.6. Общий scheduler

4.6.1. Scheduler ДОЛЖЕН формировать публичные события в зарегистрированные клиентом моменты без открытого браузера и доступа в Интернет. Он не должен интерпретировать школьные расписания, мелодии или календарные исключения пакета. `[N]` (р.1.9)

4.6.2. Набор моментов клиента ДОЛЖЕН заменяться и отключаться по правилам регистрации п. 4.5.1, 4.5.6; неверная замена сохраняет прежний набор. Отключение одного владельца не должно затрагивать расписания других клиентов или общий cron системы. `[N]` (р.1.9)

4.6.3. Scheduler ДОЛЖЕН предоставлять клиенту наблюдаемые сведения о достоверности календарного времени и его коррекции для сверки регистраций. Поведение при скачке часов, пропущенном моменте и новом экземпляре ядра должно быть определено до реализации по вопросу 9.2.15; произвольный replay и exactly-once не предполагаются. `[N]` (р.1.9)

### 4.7. Объединение запросов чтения

4.7.1. Планировщик чтений ДОЛЖЕН объединять совместимые запланированные диапазоны одного транспорта и unit с одинаковой функцией FC01/02/03/04 в один запрос, если объединение сохраняет согласованные сроки актуальности/приоритет. Разные функции или устройства не смешиваются; специально ожидать будущий запрос ценой просрочки уже готового запрещается. `[N]` (р.1.10)

4.7.2. Объединённый диапазон ДОЛЖЕН состоять только из объявленных допустимых для совместного чтения адресов без побочных эффектов. По умолчанию объединяются перекрывающиеся/смежные диапазоны; промежуток допустим только при явно разрешённых адресах и настроенном пределе разрыва. Неизвестные и запрещённые участки карты не читаются для экономии запросов. `[N]` (р.1.10)

4.7.3. Размер объединённого запроса ДОЛЖЕН соблюдать минимум ограничений функции, транспорта и устройства, границы адресного пространства; превышающий диапазон разбивается. Ограничение ответа 256 байт по п. 6.1.3 сохраняется. Адреса/количества проверяются как целые, дубликаты чтений не требуют повторного запроса. `[N]` (р.1.10)

4.7.4. Один успешный ответ ДОЛЖЕН раскладываться по исходным потребителям с общей отметкой получения, без утраты смысла их valid/age. Ошибка группы не должна публиковать частичную выборку как успешную; прежние значения остаются явно невалидными по контракту потребителя. Запись и её подтверждающий readback не объединяются с обычным опросом через границу операции записи. `[N]` (р.1.10)

5.2.3. Скрипт ДОЛЖЕН отклонять образ с VMA/LMA векторов, отличными от `0x08002000`, или размером BIN вне 1..57344 байт; сборка не выполняет прошивку платы. `[R]`

## 6. Нефункциональные требования

### 6.1. Ресурсы

6.1.1. Движок ДОЛЖЕН ограничивать число загруженных обработчиков восемью, источник одного файла 32768 байт, очередь восемью командами и исполнение загрузки/callback приблизительно 30000 Lua-инструкциями; бинарный Lua chunk отклоняется. Это не жёсткий лимит RAM или времени C-функций. `[R]`

6.1.2. При изначально не превышающих лимит сегментах и длине каждой JSONL-записи вместе с переводом строки не более лимита журнал ДОЛЖЕН ротироваться перед превышением лимита активного файла, сохраняя только активный и `.1`; лимит по умолчанию 65536 байт на файл, минимум 1024 байт. Случай новой одиночной записи сверх лимита рассмотрен в п. 9.2.2; legacy-сегменты и снижение лимита — в п. 6.1.5–6.1.7. `[U]` (р.1.3)

6.1.3. Serial-транспорт ДОЛЖЕН отклонять ответ расчётной длиной более 256 байт. `[R]`

6.1.4. `events.record` ДОЛЖЕН отвергать сериализованную JSONL-запись, включая завершающий LF, если её длина превышает лимит сегмента, возвращая `false, "event exceeds log size limit"` до ротации и записи; активный журнал, архив, seq и реестр топиков сохраняются без изменений. Равенство лимиту допускается. JSON не обрезается. Ошибка передаётся вызывающему коду: штатный `modbusd:publish` при ошибке persistence завершает выполнение, а не продолжает обработку неопубликованного события. `[N]` (р.1.1)

6.1.5. Изменение лимита через `set_max_log_bytes` НЕ ДОЛЖНО само по себе изменять файлы журнала, seq или реестра; очистка откладывается до допустимой записи, вызывающей ротацию. Отказ новой oversized-записи сохраняет файлы по п. 6.1.4 даже при старых oversized-сегментах. `[U]` (р.1.3)

6.1.6. Если активный сегмент превышает текущий лимит, при следующей допустимой записи писатель ДОЛЖЕН удалить старый архив и активный сегмент целиком, затем записать новое событие с очередным seq. Потеря старой истории согласована; строки не перепаковываются. Требование предполагает успешные операции ФС; ошибки удаления/записи остаются в вопросе 9.2.8. `[U]` (р.1.3)

6.1.7. Oversized-архив ДОЛЖЕН сохраняться побайтно, пока допустимые записи помещаются в активный сегмент; при штатной ротации активного сегмента архив заменяется этим сегментом. Немедленная граница размера архива после уменьшения лимита не гарантируется. `[U]` (р.1.3)

### 6.2. Время

6.2.1. Ядро ДОЛЖНО ограничивать `system_poll_ms` диапазоном 100..1000 мс (по умолчанию 200 мс) и `request_timeout_ms` диапазоном 100..2000 мс (по умолчанию 500 мс). Системный интервал является паузой между итерациями, а не предельным временем реакции. `[R]`

6.2.2. Выполнение очереди НЕ ДОЛЖНО отправлять команду возрастом более 1 с; просрочка обрабатывается как неуспех команды. `[R]`

6.2.3. Тайм-аут обмена, возраст снимков и статистика hz ДОЛЖНЫ опираться на монотонное время, а не на календарное `ts`. Обработка `stty` и открытия устройства не входит в дедлайн обмена. `[R]`

6.2.4. Транспорт ДОЛЖЕН сохранять настраиваемый таймаут одной попытки request_timeout_ms по п. 6.2.1 и предоставлять отдельное настраиваемое неотрицательное целое число дополнительных повторов чтения: 0 означает одну попытку, R — максимум 1+R. Общее время операции, пауза перед повтором и допустимый максимум R ограничиваются проверяемой конфигурацией; конкретные значения/имена новых настроек остаются в 9.2.17. `[N]` (р.1.10)

6.2.5. Автоматические повторы ДОЛЖНЫ применяться только к разрешённым безопасным чтениям и согласованным временным ошибкам. Неверная конфигурация/адрес, несовместимая карта и постоянный Modbus exception не должны вызывать цикл повторов. Команды записи, включая FC05 с потерянным подтверждением, автоматически не повторяются: п. 4.2.7 остаётся действующим. `[N]` (р.1.10)

6.2.6. Операция чтения ДОЛЖНА завершаться ошибкой при исчерпании попыток или общего монотонного срока, в зависимости от того, что наступит раньше. Следующая попытка не начинается после истечения срока актуальности запроса; новый запрос не должен принимать поздний ответ прежней попытки как достоверный без предусмотренной политики синхронизации RTU. Эта политика и классы повторяемых ошибок определяются до реализации по 9.2.17. `[N]` (р.1.10)

6.2.7. Ожидание ответа и паузы повторов ДОЛЖНЫ позволять ограниченное обслуживание публичного IPC независимо от профиля платы. Один транспорт выполняет не более одной незавершённой RTU-транзакции; обслуживание IPC не открывает второй serial и не запускает параллельный опрос. Увеличение числа повторов не должно превращаться в неограниченный монолитный цикл, блокирующий остальных клиентов; численные задержки требуют измерений. `[N]` (р.1.10)

### 6.3. Эксплуатация и сопровождение

6.3.1. IPK ядра ДОЛЖЕН собираться `make all` без OpenWrt SDK и компиляции исходников OpenWrt. `[U]` (р.1.5)

6.3.2. Штатный рабочий runtime-каталог ДОЛЖЕН быть `/tmp/modbus`, чтобы журнал и кэш не записывались регулярно во Flash роутера. Администраторская смена каталога меняет это свойство. `[R]`

### 6.4. Автономная установка и целостность системы

Служба принятия решения об установке относится к системе ядра; её размещение
отдельно от modbusd и формат комплекта ещё проектируются. Это целевые требования,
не описание возможностей существующего opkg или текущих скриптов. (р.1.8)

6.4.1. Комплект расширения ДОЛЖЕН содержать проверяемый manifest с версиями
расширения и API, архитектурой/ABI, транзитивными зависимостями, перечнем файлов
и контрольными суммами, местами постоянного хранения, ресурсами временных стадий
потребностью RAM при старте/работе и порядком запуска после загрузки системы. Неопределённые обязательные данные
означают отказ допуска до изменения установленной системы. `[N]` (р.1.8)

6.4.2. Ответственность за дополнительные зависимости ДОЛЖЕН нести пакет:
возможно распространяемые зависимости включаются в автономный комплект как
частные файлы или совместимые IPK. Каждая оставшаяся зависимость должна быть
явно объявлена и подтверждена как установленная в постоянном хранилище;
отсутствие сети не может быть скрытым условием успешной установки/запуска. `[N]` (р.1.8)

6.4.3. Служба установки ДОЛЖНА до запуска установочных скриптов и изменения системы
проверить целостность содержимого,
совместимость полного набора зависимостей и точный ABI модулей ядра; повреждённый,
неполный или несовместимый комплект отклоняется без force-обходов. Проверка
контрольной суммы не доказывает доверенность автора; механизм доверия открыт. `[N]` (р.1.8)

6.4.4. Прогноз ДОЛЖЕН отдельно учитывать пиковую потребность каждой файловой
системы и RAM: загрузку, распаковку, новые файлы/метаданные, временные копии,
сохранение действующей версии/настроек для отката, RAM запуска/работы расширения
и рабочий запас системы.
Размер сжатого IPK или Installed-Size сам по себе недостаточен; места на разных
разделах не суммируются как взаимозаменяемые, пути одного раздела учитываются вместе. `[N]` (р.1.8)

6.4.5. Служба ДОЛЖНА отказывать, если для любой стадии свободный бюджет меньше
прогнозируемого пика плюс настроенный запас, либо оценка не может быть достоверно
получена. Размеры запасов, учёт сжатой ФС, RAM и inode задаются проверяемой политикой,
а не вымышленным универсальным числом. `[N]` (р.1.8)

6.4.6. Служба ДОЛЖНА повторно проверять доступные ресурсы перед изменениями и
защищать бюджет от конкурирующих управляемых установок/загрузок; потеря бюджета
или ошибка записи прекращает операцию с диагностикой. Предварительная оценка
не разрешает игнорировать последующий ENOSPC. `[N]` (р.1.8)

6.4.7. Активация ДОЛЖНА происходить только после проверки полностью размещённого
комплекта; при отказе сохраняются действующее ядро, конфигурация и доступ к
управлению. До разрушительного шага должен быть подготовлен локальный путь
восстановления без сети; незавершённая установка после сбоя питания не считается
успешной и не запускается как целая. Механизм восстановления ещё не реализован. `[N]` (р.1.8)

6.4.8. Допуск ДОЛЖЕН отклонять расширение, которому для заявленного запуска
после reboot нужны невосстановимые файлы из /tmp, кэша загрузок или недоступной
сети. Исполняемые файлы, библиотеки, необходимые медиа и настройки размещаются
постоянно; временные данные создаются при запуске с учётом бюджета RAM. `[N]` (р.1.8)

6.4.9. Установка/откат/удаление ДОЛЖНЫ учитывать владение файлами и зависимости
других пакетов; приватная библиотека не подменяет системную молча, общая зависимость
не удаляется, пока нужна другим потребителям. Конфликт, требующий замены системного
компонента, отклоняется до отдельного согласованного плана обновления. `[N]` (р.1.8)

6.4.10. Приёмка автономной поставки ДОЛЖНА включать запуск в целевом окружении
без сети и прежнего содержимого /tmp после перезагрузки, проверку функций пакета
и сохранности ядра, а также негативные сценарии нехватки места и прерванной
установки. Manifest/прогноз не заменяет эту проверку и не доказывает отсутствие
произвольных ошибок пакета. Аппаратная перезагрузка согласуется отдельно. `[N]` (р.1.8)

## 7. Верификация

### 7.1. Методы и статус

| :---: | :--- |

Наличие TC и ссылки на скрипт не означает PASS. В матрице различаются существующие тесты, частичное покрытие и запланированные проверки. Тест отказа oversized воспроизвёл дефект на исходной реализации и прошёл после исправления. Аппаратные тесты и сборка неизменённой прошивки не выполнялись; прошлые результаты сохранены в CHANGELOG. (р.1.1)

В ревизии 1.2 приняты результаты 09.10.2026 на сборке `0.4.0-1+gee4dabe`: обновление/откат с проверкой файлов, один рестарт ядра, отдельное отключение USB-платы с потерей питания, один RESET MCU с USB-переобнаружением и один reboot роутера. Восстановление core/demo, свежие данные, baseline без новых LED-команд и сохранность настроек проверены. Двухчасовой пассивный прогон: 241 снимок, 1864 события без разрывов; RSS core 1404→1408 KiB, demo 1044 KiB, сегменты не больше 65536 байт. Это ограниченное D-покрытие, не гарантия времени восстановления, отсутствия утечек или всех сценариев TC-12/14/17. У рестарта ядра был пробел замеров ресурсов из-за ошибочного использования `started_at`; первый USB-опыт затронул хаб и повторён отдельно. Подробные границы и эксплуатационные выводы: [VALIDATION.md](../VALIDATION.md). (р.1.2)

### 7.3. Порядок приёмки

Сначала выполняются инспекция и локальные тесты, затем согласованные аппаратные проверки. `make all` не запускает сборку Arduino или живые тесты. Изолированный `scripts/test-handlers-router.sh` также требует разрешения использовать роутер, но не открывает рабочий tty. Lifecycle-тесты и отключение USB требуют отдельного согласования и восстановления настроек. Непокрытые сценарии не получают PASS на основании сходного теста.

## 9. Допущения и открытые вопросы

### 9.1. Допущения

9.1.1. Администратор и Lua-файлы доверенные; к управлению роутером нет доступа недоверенных пользователей. Система не обеспечивает криптографическую аутентификацию USB Modbus.

9.1.2. Прототип испытывается без опасных исполнительных нагрузок. Нулевые стартовые уставки не являются согласованной политикой fail-safe; физическое состояние выводов до `setup()` не нормировано.

9.1.3. Файлы runtime находятся на исправном доступном для записи tmpfs. Атомарный rename отдельных файлов не даёт транзакционности между кэшем, журналом, seq и реестром топиков.

## Приложение E. Исправление границ и прогноз установки (информативно)

Ревизия 1.8 исправляет принадлежность требований ревизий 1.6/1.7, не отменяя
принятую аудиополитику: она находится в schoolbell 1.3. Прежние упоминания
общего audio provider в истории/приложениях отражают старый проект, а не текущую
архитектуру. Служба установки — отдельная системная функция, не аудио API.

Для каждой ФС f оценивается максимум дополнительного места по стадиям P(f);
допуск требует free(f) >= P(f)+reserve(f). Для tmpfs дополнительно проверяется
общий безопасный бюджет RAM с учётом процессов, распаковщика и остальных tmpfs.
Числа и алгоритм оценки сжатия ещё не выбраны. Пока их нет, новый механизм
нельзя считать реализованным. Обычный opkg/manual SSH остаётся вне гарантии
будущей управляемой установки. Один успешный запуск madplay из /tmp не является
проверкой автономной поставки после reboot. (р.1.8)

## Приложение G. Статус транспорта и оптимизации (информативно)

Ревизия 1.10 фиксирует принятый профиль, не выпуск runtime/API.
request_timeout_ms уже существует: 500 мс, диапазон 100–2000 мс.
Настраиваемых retry count/delay/общего бюджета пока нет. optimizer.group_registers
существует как helper с max_group_size/max_gap, но bluepill.poll читает четыре
фиксированных блока без его применения; helper не проверяет дробные адреса,
границу 65536, функцию, unit и карту устройства. Он не готов для прямого включения.

Совместимые чтения должны объединяться в пределах доступной карты. Например,
FC04 0..4 и FC04 256..263 нельзя соединять через неизвестные адреса 5..255;
FC01 и FC04 нельзя объединить даже у одного slave. Ошибки объединённого чтения
и retry не меняют согласованную политику неопределённой записи LED.

Текущий modbusd и serial_rtu синхронны; одно увеличение таймаута/числа повторов
увеличивает блокировку. Перед P01 нужен обслуживаемый цикл ожидания с одним
владельцем serial и конечным IPC-бюджетом; реальное время этим не гарантируется.
Примерная верхняя стоимость нескольких попыток включает (1+R)*T плюс паузы,
но общий бюджет операции может завершить её раньше; open/stty/reconnect имеют
собственные затраты и не должны молча выпадать из анализа задержек.

[Памятка профиля API](EVENT_API.md) описывает принятые операции. Плановые
TC-61–71 не пройдены наличием локального IPC-прототипа или make all.
