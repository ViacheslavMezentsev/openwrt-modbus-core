# Контракт транспортов RTU/TCP — принятый профиль

[English](TRANSPORT_CONTRACT.en.md) · [ТЗ ядра 1.20](TECHNICAL_SPECIFICATION.md)

Дата: 12.10.2026. Владелец принял политики и программные пределы р.1.19.
Это целевой контракт, не действующий API core 0.4.0. В р.1.20 добавлена
[изолированная модель состояний](TRANSPORT_STATES.md); runtime не изменён.
Нормативные связи: core 6.8.1–6.8.18. TC-111–115/120/121 имеют частичное
покрытие на хосте; остальные новые проверки и аппаратная приёмка остаются планом.

## 1. Область

Один владелец каждого физического serial, один запрос на RTU-порт и на TCP-
соединение. Прямые RTU-порты используют общий раунд; TCP-точки планируются
независимо от RTU-барьера и не управляют внутренними раундами автономного шлюза.
TCP здесь обычный клиент Modbus, без сервера, TLS, автоматической настройки RNDIS
или сети. Разрешённые функции и карта устройства не расширяются самим транспортом.

## 2. Дедлайны и результат

Все сроки — монотонные. `t0` — принятие операции в очередь; `Dop = t0 +
operation_timeout_ms`, дополнительно ограниченный сроком актуальности потребителя.
В него входят очередь, барьер, open/config/connect, передача, ответ, retry delay,
карантин и reconnect. Повтор, фрагмент или корректировка UTC срок не продлевают.

Попытка начинается перед первой попыткой отправки байтов, после подготовки порта
и межкадровой паузы. `Da = min(Dop, t_attempt + request_timeout_ms)`. Это общий
срок отправки/приёма, не таймер каждого байта. Успех — полный проверенный ответ,
обработанный при `now < Da`; при равенстве побеждает timeout, даже если байты
уже были в буфере ОС. До каждой побочной операции заново проверяется срок.
Open/config/connect имеют отдельный срок `min(Dop, now + setup_timeout_ms)`.
Невозможность ограничить системный вызов означает непригодный backend.

Терминальный исход публикуется ровно один раз: `ok`, `expired` (до отправки),
`timeout`, `io_error`, `protocol_error`, `modbus_exception`, `desynchronized`,
`cancelled`, `config_error`. Отказ до принятия очереди — `busy` без операции.
Результат содержит logical_device_id, transport_id, operation_id, attempts,
монотонные start/end, exception_code при наличии и write_outcome:
`not_sent`, `confirmed`, `unknown`. Для чтения write_outcome отсутствует.

Любая возможная частичная/полная отправка записи без корректного подтверждения
означает unknown. Ни retry, ни reconnect, ни readback не доказывают, что команда
не исполнялась. Readback — отдельное наблюдение, не изменение исхода записи.
Ошибка снимает valid, сохраняя прежний last_success; reconnect не делает кэш valid.

## 3. Повторы

`read_retries=R` означает не больше `1+R` попыток; ноль — одна попытка. Ошибки
подготовки/соединения также расходуют этот бюджет, иначе безуспешный connect
создал бы скрытый неограниченный цикл. Диагностика различает attempts и число
попыток с отправленными байтами. Короткие write/read и EAGAIN продолжают текущую
попытку, EINTR требует перепроверки срока; нулевой TCP read означает EOF.

Повтор разрешён только FC01/02/03/04 с явным признаком `safe_read` в карте:
некоторые регистры меняют состояние при чтении. Первый профиль повторяет timeout,
ошибку соединения/I/O и RTU CRC/framing error только после допустимого восстановления.
Все Modbus exceptions (включая busy 06), неверные параметры/карта, неожиданный
TCP протокол, запись и отмена терминальны. Расширение exception retry — отдельно.
Повтор начинается после retry_delay и безопасного восстановления, до Dop;
нет остатка времени — завершаем операцию. Длительный карантин может исчерпать Dop.

## 4. Поздние RTU-ответы

RTU не несёт transaction ID. Ответ чтения не возвращает начальный адрес: два
чтения одного unit/FC/размера могут быть неразличимы. Flush, reopen и тишина t3.5
не отменяют ещё вычисляемый ответ. Требуется один master и отсутствие произвольных
передач ведомых; это не защита от злонамеренного устройства.

`resync_policy=manual` — default нового транспорта. После отправки запроса и
таймаута/обрыва/CRC/framing error порт становится `desynchronized`. Операция
завершается, следующие не отправляются, другие порты продолжают работу.
Автоматический reopen/restart процесса не является доказательством синхронизации.
Возобновление требует подтверждённого сброса линии/устройства либо профиля с
доказанной границей позднего ответа; событие оператора фиксируется. Неизвестная
исходная синхронизация при первом открытии также требует такого подтверждения.
Сам контракт не разрешает ядру автоматически сбрасывать оборудование.
Отмена или истечение Dop после возможной отправки применяет ту же resync-политику;
терминальный результат операции не означает готовности линии к новому запросу.

`resync_policy=bounded` допустим только с `late_response_bound_ms=B` и ссылкой
`timing_profile` на проверенный профиль устройства/адаптера. B ограничивает
поступление ВСЕХ байтов ответа на хост после последнего успешного write запроса,
включая TX/RX очереди, задержки USB/ОС и обработку устройством. Замер одного
среднего или максимального наблюдения не является доказанной верхней границей.
На общей линии профиль покрывает каждое ведомое. B не имеет универсального default.

После полностью переданного запроса карантин заканчивается не раньше
`t_last_write+B` и межкадровой тишины после последнего принятого байта. Все байты
в карантине отбрасываются ограниченными порциями без обновления данных. Если
байты приходят позже заявленной границы, профиль считается нарушенным и порт
переходит в desynchronized. Нет завершения до Dop — операция завершается,
порт остаётся в карантине и не удерживает барьер; до готовности не участвует.

Частично отправленный запрос либо неизвестный остаток TX всегда требуют manual
resync в первом профиле. Flush не доказывает отсутствие запроса в адаптере.
Новая сессия драйвера не стирает desynchronized; при рестарте/переподключении
bounded startup допускается лишь если timing_profile покрывает также этот случай,
иначе требуется подтверждение. После успешного обмена профиль исключает дубликаты
ответов; неожиданные байты вне операции также вызывают desynchronized.

## 5. TCP framing и восстановление

Принимается MBAP с protocol_id=0, Length 2..254 (Unit + PDU), итого ADU до
260 байт. Полный ответ проверяется по connection_generation, transaction_id,
Unit ID, FC (либо FC|0x80) и семантике/длине PDU. Чтение ОС не равно одному ADU:
фрагменты накапливаются, склеенные кадры разбираются по Length. RX-буфер 520 байт;
read ограничивается оставшейся ёмкостью, переполнение/неверная длина закрывают канал.

ID выдаются 0..65535 один раз на соединение. Перед повторным использованием
ID соединение закрывается и создаётся новая generation; callbacks старого fd
не принимаются новым. При timeout, отмене после возможной отправки, EOF, частичной отправке с ошибкой или нарушении
протокола соединение закрывается; безопасный read может повторяться новым ID
нового соединения в пределах общего бюджета. Ошибка MBAP/Unit/FC/ID в первом
профиле терминальна для операции; неизвестный ответ никогда не завершает запрос.
Несколько кадров в одном read разбираются ограниченно: только ожидаемый может
завершить операцию, лишний вызывает закрытие и не откатывает уже выданный результат.
Это преднамеренно строгая политика клиента, не требование TCP ко всем серверам.

## 6. Параметры и очереди

Числа ниже — принятые программные пределы, не измеренные гарантии MR3020.
Все времена — целые мс, без NaN/дробей/переполнения; неизвестные поля отклоняются.

| Поле | Default | Допустимо |
| --- | --- | --- |
| request_timeout_ms | 500 | 100..2000 (сохраняет существующую настройку) |
| operation_timeout_ms | 10000 | request_timeout_ms..60000 |
| setup_timeout_ms | 1000 | 100..5000, также ограничен Dop |
| read_retries | 0 | 0..3 |
| retry_delay_ms | 100 | 0..5000 |
| reconnect_delay_ms | 1000 | 1000..30000, без автоматического обхода RTU resync |
| late_response_bound_ms | отсутствует | 1..60000; обязателен только для bounded |
| queue_limit | 32 | 1..128 ожидающих операций на транспорт |
| io_quantum_ms | 10 | 1..100, глобальный максимальный poll sleep |

До трёх активных RTU и четырёх TCP-точек, до 32 логических устройств всего.
RTU RX не больше 256 байт, TCP RX не больше 520 байт. Один active отдельно от
queue_limit; retry удерживает active, не добавляет новую очередь. Очередь FIFO;
истёкшие удаляются до выбора. Циклический опрос имеет не более одной ожидающей
операции на одинаковый план чтения: пропущенные периоды не накапливаются.

После группировки для операции берутся минимальные исходные Dop; объединяются
только одинаковые safe_read/политики повторов, совместимые карты и функции.
Все исходные подписчики учитываются в квоте, группировка не обходит queue_limit.
Запись/readback не объединяются с обычным polling и сохраняют порядок.

В проходе — не больше 8 переходов состояний и 512 RX+TX байт на транспорт;
затем обслуживание остальных транспортов и IPC. Порядок первого транспорта
циклически сдвигается. IPC получает вызов обслуживания в каждом проходе с
собственным конечным лимитом; точный wire-бюджет задаётся этапом Event API.
Ожидание до ближайшего дедлайна/готовности/quantum; истёкший срок даёт poll=0,
но пустая система ожидает событие вместо busy loop. Quantum не гарантирует
задержку ОС, Lua callback или внешнего процесса: они измеряются отдельно.

## 7. Конфигурация портов и устройств

Целевые новые секции UCI в modbus-rtu-core: `transport <id>` и `device <id>`.
ID: `[a-z0-9][a-z0-9_-]{0,31}`, глобально уникальные в пределах своего типа.
`transport`: enabled (0/1, default 1), type (rtu/tcp), role (modbus-client),
параметры времени/очереди из таблицы. Другие роли отклоняются в этом профиле.

RTU: path обязателен, абсолютный /dev/ttyACM<number> либо /dev/ttyUSB<number>;
baudrate обязателен из 9600/19200/38400/57600/115200, data_bits=8, parity=N,
stop_bits=1, flow_control=none. Это принятый стендовый 8N1, не заявление полного
соответствия serial guide с другими форматами. BluePill допускает только
115200/8N1. RS-485 DE/RE обязан обеспечивать проверенный адаптер; GPIO-управления
направлением в этом этапе нет. Скорость общая для линии, не меняется между unit.
Реальный char-device и major/minor проверяются перед open; две ссылки на один
порт запрещены. Фиксированный path не обещает устойчивой USB-идентификации:
до такого resolver автоматическое переподключение после hotplug новой конфигурации
требует проверки привязки оператором. Настройка устаревшего номера tty не считается
подтверждением модели/серийника платы.

TCP: address — обязательный числовой IPv4 (DNS/IPv6 позже), port=502 default,
1..65535; дубликат address/port запрещён, несколько unit используют одну точку.
IP/маршруты/firewall не создаются. unit у device: RTU 1..247; TCP 0..255 как
явный маршрут, без трансляции в RTU broadcast; поддержку unit подтверждает сервер.
`device` содержит transport (существующий ID), unit, map (зарегистрированный профиль).
Повтор одной пары transport/unit запрещён. Библиотека карт и safe_read — отдельный
контракт; произвольные пути/исполняемый код не принимаются из этих полей.

Пример целевой схемы, НЕ конфигурация для текущего modbusd:

```uci
config transport 'line_a'
    option type 'rtu'
    option role 'modbus-client'
    option path '/dev/ttyACM0'
    option baudrate '115200'
    option resync_policy 'manual'
    option read_retries '0'

config device 'board_a'
    option transport 'line_a'
    option unit '1'
    option map 'bluepill-v2'

config transport 'gateway_a'
    option type 'tcp'
    option role 'modbus-client'
    option address '192.0.2.10'
    option port '502'

config device 'room_a'
    option transport 'gateway_a'
    option unit '11'
    option map 'room-sensor'
```

map здесь иллюстративные имена, не утверждение наличия loader. Неизвестная карта
отклоняется до запуска. Новые device_id адресуют `/devices/<id>/...` и ключ кэша;
unit хранится отдельно в метаданных. При отсутствии новых секций legacy core.main
сохраняется как прежний путь; его старые топики/кэш не переименовываются. Это
совместимость, не обещание новой строгой resync-политики существующего backend.
Смешение активных legacy device/profile и новых секций отклоняется. Автомиграции
нет: переход явный, в maintenance, без активных операций, с backup. Изменение
конфига валидируется целиком до активации; удаление/перепривязка active не разрешены.

## 8. Раунды и критерии

Набор RTU фиксируется после группировки: FIFO-head готовых свободных портов.
Включённая операция может ждать несколько попыток/карантин в пределах Dop.
Быстрый порт отдаёт результат сразу, но ждёт терминального результата всех
участников перед новым раундом. Новый запрос не расширяет начатый раунд.
Offline/backoff/desynchronized порты исключены; каждый запрос всё равно истекает
по собственному Dop. TCP обслуживается в том же ограниченном цикле, но независимо
от RTU-барьера. Отдельный round_timeout не нужен: предел выводится из Dop участников.

- TC-111: очередь/open/частичные кадры/UTC скачок; успех только до Da, ровно Da — timeout, Dop не сдвигается.
- TC-112: 0/3 retries, setup failures, unsafe read, exceptions и потерянный ACK записи; никакого скрытого повтора.
- TC-113: одинаковые unit/FC/count, другой адрес и поздний старый ответ; manual блокирует всю линию, соседи работают.
- TC-114: bounded до/после B, повторные байты, partial TX, рестарт; B без доказательного профиля не включается, valid не обновляется из карантина.
- TC-115: TCP каждый split MBAP/PDU, склеенные кадры, Length 1/255, RX capacity, чужой Unit/ID, wrap ID и callback старой generation.
- TC-116: дубли endpoint/tty, неизвестная карта/поля, неверные значения, mixed legacy/new; отказ до открытия порта и сохранение старой конфигурации.
- TC-117: три порта 10/20/500 мс; публикации в 10/20 мс, следующий раунд не раньше 500 мс при идеальном backend; retry остаётся в том же раунде.
- TC-118: медленный RTU, готовый TCP, очередь IPC и шум; проверка конечных порций/чередования, без обещания аппаратной задержки 10 мс.
- TC-119: очередь заполнена, coalescing опроса и объединённые read; FIFO и сроки не нарушаются, лимит подписчиков не обходится.
- TC-120: поздняя запись/отмена/обрыв; unknown не превращается в not_sent, один терминальный результат, readback отдельно.
- TC-121: расчёт пауз по baudrate, USB chunking и ожидание выхода TX; неподтверждённые timing-возможности не объявляются поддержкой строгого RTU.
- TC-122: legacy однопортовый режим сохраняет адреса/поведение, новый ID не смешивает одинаковые unit; аппаратная регрессия отдельно после разрешения.

## 9. RTU timing и границы доказательства

Для линии учитывать t3.5: до 19200 включительно — 3.5 длительности символа;
выше — 1.75 мс по serial guide. Для принятого 8N1 символ — 10 бит; 9600 даёт
не менее 3.646 мс, 19200 — 1.823 мс; округление только вверх. Профиль может
увеличить паузу, не уменьшить. Начало следующей передачи — после подтверждённого
конца предыдущего TX/RX и паузы. Нельзя блокировать весь цикл вызовом tcdrain:
backend предоставляет ограниченно проверяемый TX completion либо доказанную
верхнюю оценку выхода очереди. При отсутствии такой возможности профиль не готов.

USB CDC отдаёт порции, а не достоверные wire timestamps каждого байта. Нельзя
объявлять t1.5-проверку линии по промежуткам между read() на роутере. Полученные
кадры проверяются по ограниченной длине, CRC, unit/FC и ожидаемому ответу;
строгое соблюдение пауз при RX — обязанность документированного адаптера/шлюза
либо отдельного аппаратного доказательства. Модель 16 тестов этого не проверяет.

Основания протокола: [Modbus Serial Line V1.02](https://www.modbus.org/file/secure/modbusoverserial.pdf),
[Modbus TCP Implementation Guide V1.0b](https://www.modbus.org/file/secure/messagingimplementationguide.pdf).
Manual/bounded, бюджеты, строгая TCP-политика и UCI — проектные решения этого
документа (приняты владельцем), не цитаты или предписания Modbus Organization.
