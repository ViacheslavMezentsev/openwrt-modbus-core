# Карта безопасных диапазонов и объединение чтений

[English](READ_GROUPING.en.md) · [Состояния и раунды](TRANSPORT_STATES.md)

Принятый контракт, core 4.7 и 6.8. Хостовая реализация:
[read_groups.py](../../scripts/read_groups.py),
[20 тестов](../../scripts/test_read_groups.py). Команда:
`python3 scripts/test_read_groups.py`; также make all/ci-core.
Исходная Python-модель не меняла runtime/IPK; Lua-этап р.1.30 описан ниже.

## Карта

Неизменяемая ReadMap содержит ReadRange. Конструкторы отклоняют неизвестные поля,
нецелые значения/bool вместо числа, выход за адресное пространство и пересечения
одной функции. Соседние диапазоны остаются отдельными границами объединения.
Адреса — протокольные, от нуля, а не обозначения 40001. Количество — биты для
FC01/02 и 16-битные регистры для FC03/04. Разные функции имеют разные пространства.

| Поле | Смысл и предел |
| --- | --- |
| function | 1..4 |
| start, count | 0..65535; положительное количество без выхода за 65536 |
| safe_read | Default false; отсутствие побочных эффектов и допустимость повтора |
| mergeable | Default false; совместное чтение разрешено, требует safe_read |
| max_count | Default 1; 1..2000 для FC01/02, 1..125 для FC03/04, может быть ниже по устройству |
| max_gap | Default 0; число незапрошенных адресов между нужными, только внутри диапазона |

Пример Python для теста (это не UCI/JSON loader):

```python
ReadMap([ReadRange(function=3, start=100, count=20,
                   safe_read=True, mergeable=True, max_count=20, max_gap=0)])
```

Профиль привязан к logical device, не к потребителю. Scheduler берёт safe_read из
карты, а не доверяет флагу клиента. Неизвестное устройство/адрес отвергается до enqueue.
Если карта включена, все чтения требуют карты; прежние тесты без карт сохраняют
свой изолированный режим. Карта чтений не разрешает записи: существующая FC06-проба
модели сохранена, настоящий write allowlist остаётся отдельной задачей.

## Объединение и разбиение

Выбирается только совместимое начало FIFO: то же устройство/unit/транспорт,
функция, диапазон карты и политика повторов (в модели задаётся транспортом).
Перекрытия и дубли допускаются; промежуток не больше max_gap и весь блок лежит
в одном безопасном диапазоне. Запрос, который не помещается или несовместим,
останавливает группу: следующие за ним не извлекаются ради оптимизации.

Запись, включая повторную запись того же значения, не объединяется и не удаляется.
Явный readback также останавливает группу с обеих сторон. Он может разбиваться
по max_count только как безопасное чтение, без объединения с polling.
Будущие FC15/16 не добавлены этим этапом.

Слишком большое безопасное логическое чтение разбивается на последовательные
wire-запросы; с другими потребителями оно в этой версии не объединяется.
Небезопасное чтение больше max_count отвергается: автоматическое разбиение может
изменить его побочные эффекты. Все фрагменты сохраняют общий исходный Dop и порядок.
Допустимые повторы ограничены отдельно на каждом wire-запросе; статистика результата
суммирует попытки всех фрагментов. Modbus exception завершает всю операцию;
дробления или повторов как реакции на exception нет.

RTU-фрагменты остаются внутри исходной операции раунда, соблюдают паузу линии;
остальные транспорты обслуживаются. Общий срок действует также между фрагментами.
Разбитое чтение не является атомарным снимком устройства. Даже один wire-ответ
сам по себе не доказывает атомарное обновление регистров внутри устройства.

## Результат и квоты

Группа использует минимальный Dop. Каждый потребитель получает исходные ID/start,
общий момент завершения и свою часть данных. Битовые ответы перепаковываются от
нулевого бита потребителя с нулевым padding. При ошибке любой части payload пуст
для всех затронутых потребителей; valid снят, last_success полного чтения сохранён.
Данные промежуточных фрагментов не публикуются как успешное полное чтение.

Группировка не освобождает квоты исходных потребителей: суммарно active + ожидающие
не больше queue_limit + 1. У группы не появляется неограниченный список подписчиков.
Старый срок не продлевается ожиданием дополнительных запросов.

Р.1.23 вводит [загрузчик и принятые лимиты](DEVICE_PROFILES.md): 64 диапазона
на профиль, 1024 байта результата, 16 фрагментов/потребителей и резерв сборок 8 КиБ.
Wire-запросы создаются по мере выполнения; данные упакованы. Эти лимиты заменяют
прежние широкие пределы хостового прототипа, но не ограничивают весь RAM процесса.

Частичное покрытие TC-69–71/119: границы/дыры/функции, max_gap, FIFO/write/readback,
дедлайны, квоты, дубли, битовые смещения, split и ошибка фрагмента. Production Lua loader,
карты оборудования, IPC и аппаратное подтверждение безопасности остаются планом.

## Изолированная Lua-композиция (р.1.30)

Модули [read_groups.lua](../../pkg/usr/lib/modbus/read_groups.lua) и
[transport_scheduler.lua](../../pkg/usr/lib/modbus/transport_scheduler.lua)
теперь реализуют этот контракт на Lua 5.1.
[26 групп тестов](../../scripts/test_read_groups.lua) включены в make all/ci-core:
границы/дыры, FC01–04, FIFO/write/readback, раздача битов и слов, deadlines,
лимиты, memory wait, отмена/ошибка/повторы и RTU-барьер. Это TC-133 и частичное
покрытие TC-69–71/119/125/126; реальный backend и modbusd не подключены.

Внутренний API scheduler.new(transports, options) дополнен options.profiles —
снимком, полученным от device_profiles store:activate/current. Поддельная таблица
отвергается; device_profiles.is_snapshot проверяет происхождение представления.
Scheduler сохраняет снимок: последующая активация store не меняет его карту.
Даже пустой явно переданный снимок запрещает чтение неизвестных устройств.
Без profiles сохраняется изолированный режим одиночных wire-запросов прежних тестов.
Произвольные таблицы карт и горячая замена не поддерживаются.

enqueue проверяет логический размер (до 8192 бит / 512 слов), нахождение внутри
одного диапазона и число фрагментов до изменения очереди. safe_read берётся из
профиля, а не от клиента. Сам transport_state:admit по-прежнему принимает только
wire-размеры. validate_request(request, kind, logical) с logical=true используется
только для предварительной проверки логического запроса.

Группа выбирает до 16 совместимых потребителей начала FIFO. Общий размер
active consumers + pending остаётся не больше queue_limit + 1; все исходные
operation_id сохраняются и проверяются на дубли, включая промежутки фрагментов.
Повторы действуют на отдельный wire-запрос, attempts/sent_attempts суммируются.
После промежуточного успеха оба представления valid/last_success — endpoint и
samples[device] — отражают только последнее полное чтение, valid=false.
При последующей ошибке не сохраняется timestamp успешного промежуточного фрагмента.

options.assembly_pool может содержать read_groups.pool(limit), 1–8192 байта;
по умолчанию создаётся собственный пул 8192. Методы used(), acquire(owner, bytes),
release(owner) предназначены для доверенного ядра/тестов. Один пул можно разделить
между scheduler для моделирования дефицита. Резервируется весь логический payload
до dequeue/начала RTU-раунда; memory_blocked отражает отказ в текущем проходе.
Повторная проверка идёт при step, ожидание ограничено quantum/deadline и не крутится
с нулевым next_wait только из-за нехватки памяти. Освобождение общего пула может
сопровождаться внешним пробуждением, но отдельного callback пула пока нет.

cancel(endpoint) отменяет всю активную группу, включая паузу между фрагментами,
и возвращает boolean. Результаты/освобождение резерва выдаёт следующий step.
Это внутренний механизм очистки, не новый публичный API отмены одного потребителя.
Ожидающие очереди метод не отменяет. Вызывающий должен продолжать step до
терминального результата; простое отбрасывание scheduler с общим пулом не cleanup.

Сборка хранит упакованную Lua-строку; следующий wire-запрос вычисляется по индексу.
Список всех фрагментов и таблица всех битов не сохраняются.
При склейке строк одновременно живут старый и новый payload; битовая перепаковка
использует временную таблицу байтов, fan-out создаёт строки результатов.
При 7 транспортах payload сборок не превышает 7168 байт, но эти копии, метаданные,
JSON, RX/TX, результат step и память, ожидающая GC, не входят в резерв 8192 байта.
Размер IPK/предел payload не доказывает пик RAM или задержку GC на MR3020.

Следующий этап — отдельный контракт и реализация ограниченного native I/O;
измерение суммарной Lua RAM остаётся обязательной задачей до интеграции.
Реальные профили устройств, UCI, installer и modbusd этим этапом не изменены.
