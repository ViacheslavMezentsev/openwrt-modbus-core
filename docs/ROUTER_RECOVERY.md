# TL-MR3020 v3.30: загрузка, диагностика и восстановление

Актуальная подготовка первого OEM TFTP-опыта для EU v3.30: [паспорт и памятка Pages](../site/devices/tl-mr3020-eu-v3.30.html). Исходный Build250625 сохранён; приём файла загрузчиком ещё не проверен. Отдельный OEM recovery-выпуск не обязателен; необходимость преобразования исходного BIN пока не установлена.

[English](ROUTER_RECOVERY.en.md) · [Документация](README.md)

Дата проверки источников: 2026-10-12. Это эксплуатационная памятка, не изменение
целевой платформы ядра. У владельца работает OpenWrt 19.07.9; более новые образы
ранее не загружались, но причины по UART ещё не установлены. Описанный ниже
порядок не проверен заново на стенде v3.30. Прошивка, перезапуск и изменение
сети выполняются владельцем либо после отдельного согласования.

## 1. Что подтверждено и что ещё проверить

OpenWrt публикует профиль `tplink_tl-mr3020-v3`, target `ramips/mt76x8`:
8 МиБ Flash, 64 МиБ RAM. Отдельного профиля v3.30 в проверенных каталогах нет.
TP-Link имеет отдельную страницу V3.30. Это не доказывает тождественность её
загрузчика, распиновки и формата OEM-образа ранней v3. См. источники S1–S3.

Для документированного загрузчика v3 компьютер является TFTP-сервером:
`192.168.0.225/24`, запрашиваемое имя `tp_recovery.bin`. Роутер сам скачивает
файл при запуске с Reset. В S1 указаны примерно 6–7 секунд до начала запроса,
в S2 — удержание 20–30 секунд до окончания передачи. Ориентир для нашего опыта:
UART и фактический TFTP-запрос, а не один таймер. Передача не доказывает успешную
запись Flash или загрузку ОС. Не прерывать питание во время записи.

До опыта v3.30 фиксируем регион/аппаратную ревизию с наклейки, маркировку PCB,
версию загрузчика, его запрос имени/IP и журнал загрузки. Не подменяем отсутствие
этих данных универсальными командами стирания или советами для MR3020 v1.

## 2. Три разных пути

| Состояние | Путь | Файл |
| --- | --- | --- |
| OpenWrt загружается | Штатный sysupgrade после проверки и backup | `*-squashfs-sysupgrade.bin` |
| ОС не загружается, recovery загрузчика работает | Роутер скачивает файл с TFTP-сервера Windows | `*-squashfs-tftp-recovery.bin`, под именем `tp_recovery.bin` |
| Диагностика через UART | Сначала только запись лога; загрузка в RAM зависит от меню/команд загрузчика | `*-initramfs-kernel.bin`, если есть и подтверждён способ запуска |

`initramfs` не следует автоматически переименовывать в recovery: TFTP recovery
может записать полученное содержимое во Flash. RAM-запуск не является гарантированно
доступным пунктом меню; команды и адреса определяем по конкретному загрузчику.
Не применять `erase`, `cp`, `sf write`, `mtd write`, `saveenv` по чужому примеру.
Failsafe OpenWrt требует запуска ядра и не заменяет recovery загрузчика.

## 3. Подготовка отката и выбор версии

До смены ОС сохранить вне роутера конфигурацию, обработчики, список/версии пакетов,
совместимые IPK с зависимостями, образы возврата и их SHA-256. Архив настроек
sysupgrade не содержит установленные программы и не является полным образом Flash.
Для нашего проекта материалы остаются локально в новом нумерованном исследовании
`docs/research/NN-router-recovery/` и `tests/manual/NN-router-recovery/`.
Не добавлять в Git образы, дампы, логи, реальные MAC/серийники и ключи.

Read-only инвентаризация через WSL Ubuntu-20.04:

```sh
ssh openwrt 'ubus call system board; cat /proc/mtd; uname -a; opkg list-installed; df -h'
```

Сохранить вывод в локальный каталог опыта. Резервное чтение разделов Flash требует
сначала изучить именно этот `/proc/mtd`; номера из старой wiki не переносить.
Сохранять загрузчик и радиокалибровки; эта памятка не даёт команд их перезаписи.

Кандидаты с официальными образами (S4): 19.07.9 — исходная проверенная ОС;
19.07.10 — соседний выпуск; затем 21.02.7, 22.03.7, 23.05.6 по одному опыту.
Наличие файла не означает PASS v3.30. Старые ветки — варианты диагностического
сравнения, а не обещание актуальной поддержки безопасности.

Перед использованием скачать образ и `sha256sums` из одного каталога выпуска,
проверить имя модели/target и контрольную сумму, по возможности подпись списка.
Сохранить источник и дату. Хэш, самостоятельно вычисленный от неизвестного файла,
не доказывает происхождение. Пакеты/kmod старой ОС не переносить в новую:
нужны её архитектура, ABI и точная версия ядра.

Между основными ветками проверять чистую конфигурацию, вручную возвращая только
нужные настройки. При штатном обновлении предварительно выполнить `sysupgrade -T`
на выбранном sysupgrade-файле. Отказ не обходить `-F`. Запись запускается отдельным
действием после готового отката; здесь автоматической команды записи нет.

## 4. UART: узнать, почему нет загрузки

S2 указывает для ранней v3 TP2=TX, TP1=RX; S3 — UART 3,3 В, 115200 8N1.
На v3.30 сначала сверить площадки/землю; маркировку нельзя считать проверенной.
Нужен USB–TTL адаптер уровня 3,3 В, не RS-232 и не 5 В. Подключить общий GND,
TX роутера к RX адаптера; для первоначального чтения TX адаптера оставить свободным.
VCC адаптера не подключать: роутер питается штатно. Подключения делать без питания.

Открыть терминал на COM-порту: 115200, 8 бит, без чётности, 1 стоп-бит,
без flow control. Включить запись полного лога до подачи питания. Это UART
самого роутера, не `/dev/ttyACM0` платы Modbus; последний не открывать параллельно ядру.

| Последнее наблюдение | Что выяснить следующим |
| --- | --- |
| Нет символов | Питание, GND, RX/TX, уровень, COM и скорость; это ещё не доказательство повреждённого bootloader |
| Есть bootloader, отвергает образ | Тип/заголовок/контрольная сумма/регион, полный текст отказа |
| Начинается Linux и panic | Сохранить полный panic: Flash-разметка, mount rootfs, память, драйверы |
| Перезапуск цикла | Питание/watchdog/crash; сравнить момент и текст, не объявлять причину без данных |
| Есть shell, но нет сети | Загрузка состоялась; исследовать сеть отдельно |

Результат диагностического этапа — полный лог и точная последняя успешная стадия.
Перед RAM-загрузкой или вводом команд в загрузчик отдельно согласовать действия.

## 5. Windows: простой сервер, который ждёт роутер

Практический вариант — Tftpd64 из репозитория автора (S5). Он ждёт запрос и отдаёт
файл; цикл ping и многократный `tftp put` не нужен. Встроенный Windows `tftp.exe`
является клиентом, а нам нужен сервер (S6). Сервер запускается непосредственно
в Windows: так не требуется пробрасывать UDP через WSL2 NAT. Рабочий SSH проекта
по-прежнему выполняется через WSL.

1. Использовать отдельный Ethernet/USB–Ethernet адаптер и прямой кабель к роутеру.
   Лучше закрепить этот адаптер за восстановлением, чтобы не менять рабочую сеть.
2. Зафиксировать его текущие IPv4, DHCP, DNS, маршруты и имя/индекс. В свойствах
   IPv4 назначить `192.168.0.225`, маску `255.255.255.0`, без шлюза и DNS.
   Убедиться, что нет другого интерфейса/маршрута в ту же подсеть. Не отключать
   все адаптеры или firewall целиком.
3. В Tftpd64 выбрать именно `192.168.0.225` в Server interfaces и отдельный Current
   Directory с единственным разрешённым образом `tp_recovery.bin`. Выключить
   ненужные серверы, особенно DHCP. Ограничить доступ каталогом и чтением.
4. Разрешить входящий UDP для выбранного исполняемого файла только на recovery-
   интерфейсе и локальном адресе, из `192.168.0.0/24`, с учётом профиля Windows.
   Не ограничиваться только портом 69: передача TFTP использует отдельный UDP-порт.
5. Сервер готов до включения роутера. Запустить UART-log; зажать Reset и подать
   питание. Следить за запросом, передачей и последующей записью/перезагрузкой.
6. Если запроса нет — проверить link, привязку сервера/firewall и сообщения UART.
   Не подставлять другие образы наугад и не считать отсутствие ping отказом TFTP.
7. После загрузки закрыть сервер, убрать созданное правило firewall, восстановить
   прежнюю конфигурацию адаптера, если он не выделен для recovery. Проверить
   доступность обычной сети. У новой ОС адрес может отличаться от recovery.

Обычный switch между ПК и роутером может сохранить link ПК при перезапуске роутера;
это вариант диагностики задержки поднятия интерфейса, а не обязательное оборудование.

### Помощник подготовки файла

[prepare-router-recovery.ps1](../scripts/windows/prepare-router-recovery.ps1)
работает в Windows PowerShell 5.1+, без администратора. Остановить TFTP-сервер
перед подготовкой. Пример с переменными, которые заполняет оператор:

```powershell
& .\scripts\windows\prepare-router-recovery.ps1 `
    -Image $DownloadedRecoveryImage `
    -ExpectedSha256 $HashFromOfficialChecksums `
    -OutputDirectory $NewEmptyRecoveryDirectory
```

Скрипт принимает только именованный OpenWrt recovery v3, проверяет SHA-256,
создаёт новый каталог и копирует файл как `tp_recovery.bin`, проверяя копию.
Существующий каталог не перезаписывает. Проверены локально синтетическая копия,
неверный хэш, существующий каталог и отказ для sysupgrade (PowerShell 7);
Windows PowerShell 5.1 отдельно ещё не запускался. Он не скачивает, не выбирает прошивку,
не определяет ревизию платы, не меняет сеть, не запускает сервер и не шьёт роутер.
Если подготовка прервана, каталог не использовать до проверки; повторить в новом.
Выбрать полученный каталог в Tftpd64 — ожидание и передача принадлежат серверу.

При запуске из UNC WSL политика RemoteSigned может потребовать подпись скрипта.
Не менять политику системы: после просмотра исходника можно использовать его
локальную копию в Windows; проверка Git-подписи не является Authenticode-подписью.
В управляемой среде соблюдать её правила выполнения скриптов.

Полная автоматизация сети — следующий отдельный этап: preflight, снимок состояния,
явный выбор адаптера/образа, узкое временное правило firewall, журнал и восстановление
из сохранённого состояния даже после аварийного завершения. Один `finally` не
гарантирует откат после отключения питания ПК. Microsoft предупреждает: добавление
адреса через `New-NetIPAddress` отключает DHCP (S7); удалить адрес недостаточно
для восстановления исходной сети. Такой сетевой helper пока не реализован.

## 6. Возврат заводской прошивки

Скачать OEM только для региона устройства и V3.30 (S8). Заводской web-update файл
не считать автоматически пригодным для TFTP. Не срезать произвольное число байт,
не использовать старые инструкции v1/v3.0 и не писать загрузчик целиком.
Для конкретного OEM-файла сначала установить формат, допустимый путь восстановления
и ограничения downgrade по документации TP-Link и выводу загрузчика. Если данных
нет — возврат OEM остаётся нерешённым; использовать ранее проверенный OpenWrt recovery.
Например, страница S8 предупреждает о запрете downgrade у 1.10.0 Build 260303.
Это свойство конкретного OEM-выпуска, не универсальное правило всех v3.30.
Помощник намеренно не принимает OEM-образы и ничего не конвертирует.

## 7. Критерии проверки и следующий опыт

Передача TFTP, успешная запись, запуск ядра, доступ по сети и работа приложений —
пять разных результатов. Записать SHA-256, UART/TFTP-логи, версии ОС/ядра, свободные
Flash/RAM; затем Ethernet, Wi-Fi, USB-хаб, ACM/RNDIS, аудио и накопитель по составу
стенда. Только после этого проверять core/demo и Modbus. Никакого PASS по одному ping.

Следующий согласуемый опыт: собрать UART-log неудачной загрузки конкретного образа
и подтвердить параметры recovery v3.30. Проверку скрипта без оборудования не считать
проверкой восстановления. Документ не меняет целевую OpenWrt 19.07.9 проекта.
