# Разработка и согласование

[English](DEVELOPMENT.en.md)

## Этап

1. Проверить статус Git и актуальный main; выбрать ветку `<агент>/<задача>`.
2. Согласовать область, требования и критерии готовности. Для нового поведения
   сначала подготовить или обновить русское ТЗ, затем реализацию и тесты.
3. Выполнить доступные проверки, отметить пропуски и риски; аппаратный PASS
   не выводится из CI. Обновить RU/EN публичные документы, TODO и CHANGELOG.
4. Подготовить английский Conventional Commit с настроенной подписью. Не
   отключать подпись ради коммита. Без настройки оставить изменения владельцу.
5. Владелец выполняет push. CI запускается на push любой ветки, без PR.
6. Только после PASS CI текущего HEAD владелец выполняет land: fast-forward
   main, push main, удаление рабочей ветки. При изменившемся main и невозможном
   fast-forward сначала согласовать интеграцию, затем снова проверить новый HEAD.

Исторические PR сохраняются; новые PR и merge-коммиты не являются новым рабочим
циклом. Агент не делает push, land, теги или релизы без отдельного поручения.

Пример команд владельца (имя заменяется точной текущей веткой):

```sh
git push -u origin codex/project-workflow
gh run list --branch codex/project-workflow
gh run watch <RUN_ID> --exit-status
# Сверить headSha запуска с git rev-parse HEAD.
# Только после успешного CI и при настроенном git land:
git land codex/project-workflow
```

В рабочем окружении подписанные коммиты выполняются Windows Git через путь
к репозиторию WSL; ключ в Linux не копировался. В WSL настроен alias `git land`:
fetch, fast-forward main и рабочей ветки, атомарный push main с удалением удалённой
ветки, затем удаление локальной ветки. Alias запрещает land для main, но CI
сам не проверяет: сначала владелец проверяет успешный запуск для точного HEAD.
Эти настройки локальные, Git-репозиторий их не распространяет. Без helper
эквивалентные действия владельца после CI:

```sh
git fetch origin
git switch main
git merge --ff-only origin/main
git merge --ff-only codex/project-workflow
git push origin main
# Только после успешного push main:
git branch -d codex/project-workflow
git push origin --delete codex/project-workflow
```

Рабочее дерево перед переключением должно быть чистым; незавершённое не
удаляется и не откатывается. Чужие ветки не удалять. Никаких force-push.

## Проверки и оборудование

`make all` проверяет пакеты, shell, метаданные и доступные локальные тесты.
Lua требует Lua 5.1, тест кнопки - g++; сообщения skipped фиксируются отдельно.
Arduino-путь: `sh scripts/build-bluepill.sh` с закреплёнными зависимостями.
Скриптовые IPK не требуют OpenWrt SDK, компилятора ядра или сборки прошивки роутера.

`sh scripts/test-handlers-router.sh` запускает Lua-регрессии в отдельном `/tmp`
на роутере, без живого serial и подмены событий рабочего журнала.
`make test-bluepill-router` и `make test-topics-router` проверяют живую систему.
Установка/lifecycle-тесты меняют роутер: согласовать действия, резервные копии
и восстановление. Сохранить kmod-usb-acm, switch_position и сетевые настройки.
При работающем ядре не запускать отдельный Modbus master на том же tty.

Исследования идут только локально: описание в `docs/research/NN-name/`,
стенд в `tests/manual/NN-name/`. Шаблоны/отчёты/логи не добавляются в Git.
Принятый контракт, код и штатные тесты публичны и не ссылаются на локальные отчёты.

## Методика ТЗ

Принята [embedded-tech-spec](https://github.com/ViacheslavMezentsev/demo-stm32-skills/tree/main/embedded-tech-spec).
Изучены SKILL.md, шаблон и правила разделов; навык не установлен глобально и
его код не скопирован в проект. [ТЗ](TECHNICAL_SPECIFICATION.md), ревизия 1.1,
подготовлено по существующему коду и остаётся черновиком для согласования.
Проверки структуры и ссылки на тесты не означают утверждения или аппаратного PASS.

- Русское ТЗ содержит реквизиты, платформу, ревизию/статус, историю, область и
  границы, функциональные/интерфейсные/ресурсные требования, верификацию,
  матрицу прослеживаемости, открытые вопросы и приложения констант/расхождений.
- Одно требование - одно проверяемое утверждение; номер `X.Y.Z` постоянный.
  Удалённые номера остаются с отметкой «исключено». Происхождение: `[R]` из
  реализации/подтверждённого поведения, `[N]` новое, `[U]` уточнённое.
- Для каждого требования указать реализацию либо отсутствие и проверку:
  A (анализ), T (тест), I (инспекция), D (оборудование). Тесты имеют ID `TC-NN`.
- Начать с черновика 1.0 по коду main. Не превращать RTC/RS-485, безопасные
  состояния выходов или требования реального времени в молчаливые допущения.
  Интервал опроса 200 мс сейчас не гарантирует максимальную задержку реакции.
- Следующая ревизия сохраняет номера, обновляет дату, историю, изменения,
  затронутые требования, тесты, матрицу и вопросы. Статус «утверждено» задаёт владелец.
- Перед новой редакцией прочитать актуальный навык и нужные разделы
  `references/sections.md`. Его `scripts/check_spec.py` запускать из локальной
  копии после просмотра кода: `python3 <SKILL_DIR>/scripts/check_spec.py <SPEC> --strict`.
  Утилита проверяет структуру, не заменяет техническое согласование.

## CHANGELOG

Новые заметные изменения заносить в `[Unreleased]` сразу в CHANGELOG.md и
CHANGELOG.en.md. Использовать только непустые категории:
Добавлено/Added, Изменено/Changed, Устарело/Deprecated, Удалено/Removed,
Исправлено/Fixed, Безопасность/Security. Описывать поведение, а не каждый коммит.
Владелец переносит записи в версию с датой при фактическом выпуске.
Версия Makefile/IPK сама по себе не означает релиз. История старых этапов
сохранена отдельно; не переписывать прежние проверки как выполненные сегодня.
