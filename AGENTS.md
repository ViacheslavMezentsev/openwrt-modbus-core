# AGENTS.md

Правила для агентов и участников **openwrt-modbus-core**.
English workflow: [DEVELOPMENT.en.md](docs/DEVELOPMENT.en.md).

## Рабочий цикл

1. Прочитайте README, TODO, Unreleased в CHANGELOG и
   [порядок разработки](docs/DEVELOPMENT.md). Проверьте `git status`.
   Не откатывайте чужие изменения; не добавляйте всю папку `docs/` автоматически.
2. Работайте в ветке `<агент>/<задача>` от актуального `main`, для Codex:
   `codex/<задача>`. Подходящую незавершённую ветку можно продолжать.
3. Новые PR не используются. Push, land, теги и релизы выполняет владелец.
   Агент не запускает их без отдельного явного поручения. После этапа сообщите
   точное имя ветки и команды push, затем отдельно land только после успешного
   CI именно её текущего HEAD. Не обходите проверки и не делайте force-push.
4. Коммиты: Conventional Commits на английском, с настроенной подписью GitHub
   Signing Key, без идентификаторов сессий агента. Если подпись не настроена
   или не работает, не отключайте её и не делайте неподписанный коммит:
   сохраните изменения и сообщите владельцу. Не создавайте ключи самостоятельно.
5. README, CHANGELOG и новые публичные памятки ведите в RU/EN вместе.
   ТЗ ведите только на русском. Старые проектные заметки не требуют полного
   перевода при каждой правке. Локальные исследования можно вести на русском.
6. Целевая система: OpenWrt 19.07.9, MR3020 v3, kernel 4.14.267, Lua 5.1.
   Разработка и SSH к роутеру идут через WSL Ubuntu-20.04. Скриптовые `.ipk`
   собирайте напрямую через `make`/`tar`, без сборки OpenWrt или SDK.
7. Прошивка: WeAct BluePill Plus v1.1 STM32F103C8T6, Arduino Core STM32.
   PA0/PB2 зарезервированы под системную кнопку/LED. Единственный владелец
   USB RTU при работе системы - ядро. Не запускайте параллельные serial-клиенты.
8. Проверки: `make all`, `sh scripts/build-bluepill.sh` для прошивки;
   `sh scripts/test-handlers-router.sh` для изолированных Lua-тестов;
   `make test-bluepill-router` и `make test-topics-router` для живой системы.
   Пропущенный тест не считается успешным. CI не заменяет аппаратные проверки.
9. Не устанавливайте инструменты сборки на роутер. Согласуйте влияющие на
   оборудование операции; сохраняйте настройки и путь восстановления.
   Не трогайте `kmod-usb-acm`, `switch_position`, сеть и option bytes без поручения.
   После тестовых установок удаляйте временные `.ipk` и кэш opkg, не настройки.
10. Не коммитьте ключи, реальные серийники, персональные пути, BIN/HEX/ELF,
    дампы памяти, резервные копии, логи оборудования, скачанные инструменты
    и кэши. Для примеров используйте переменные и синтетические значения.
11. Обновляйте затронутые требования/тесты ТЗ, TODO, CHANGELOG и RU/EN памятки.
    Завершайте этап результатом, ограничениями, следующим шагом и Git-командами.

## Техническое задание

Используйте методику [embedded-tech-spec](https://github.com/ViacheslavMezentsev/demo-stm32-skills/tree/main/embedded-tech-spec)
при создании и изменении ТЗ: реквизиты/ревизии, постоянные номера требований,
происхождение `[R]`/`[N]`/`[U]`, тесты `TC-NN`, матрица реализации и проверок,
открытые вопросы и ограничения. Подробный цикл - в DEVELOPMENT.
Не выдавайте черновик за утверждённый контракт. Новое поведение сначала
согласуется через требования и проверяемые критерии; неизвестное остаётся вопросом.
`docs/core/TECHNICAL_SPECIFICATION.md` содержит ревизию 1.6, черновик для согласования.
Не считать его утверждённым; перед работой проверяйте ревизию, вопросы и матрицу.

## Локальные исследования

1. Прочитайте `docs/research/README.md`, `HISTORY.md` и актуальную сводку.
   Старые результаты не объявляйте повторно проверенными.
2. Используйте `docs/research/NN-short-name/` для описания и
   `tests/manual/NN-short-name/` для прототипов/логов/образов. Номера не
   переиспользуйте; короткому опыту достаточно README. Корень не служит стендом.
3. До опыта запишите цель, оборудование, версии, условия и ожидаемый результат;
   после - команды, факты, ограничения и следующий шаг. SHA-256 образов и
   идентификаторы оборудования храните локально. Сохраняйте исходные FAIL/ERROR.
4. Начните с тестов без оборудования. До экспериментальной записи/стирания
   согласуйте устройство, диапазон и операции; сохраните и проверьте исходную
   затрагиваемую память/конфигурацию. После временного опыта восстановите и
   проверьте её. Если пригодной копии нет, запись не начинайте. Плановую
   установку принятой версии отличайте от временного опыта: отдельно согласуйте,
   что новая версия остаётся на устройстве, и подготовьте откат.
5. Обновляйте локальный HISTORY новыми записями сверху. Исследования и ручные
   стенды исключены Git; не применяйте `git add -f`. Принятые результаты
   переносите в код, штатные тесты и публичные документы без ссылок на локальные
   отчёты. Не подключайте прототип к CI автоматически.

Новые каталоги: lowercase-kebab-case.

## Владельцы требований

- Ядро: `docs/core/`; demo: `docs/packages/demo/`; schoolbell: `docs/packages/schoolbell/`.
- Каждый компонент ведёт своё русское ТЗ, README и CHANGELOG RU/EN.
- Номера требований/TC локальны документу; в комментарии указывать имя компонента.
- Общий API принадлежит ядру, прикладная политика — пакету. В ТЗ пакета фиксировать
  версию/базовый контракт ядра, не копировать требования ядра. Не выдавать ревизию
  ТЗ за версию API; пока API не выпущен, зависимость явно отмечать нерешённой.
- Исходники и общий runner пока остаются на прежних путях; разделение документации
  не означает выпуск отдельных проектов или успешную аппаратную проверку.
